A Fault-Tolerant Lead Pipeline

Synthesis. You are given a client brief: a lead-capture-to-CRM pipeline that must survive a flaky downstream API, duplicate webhook deliveries, and a traffic spike. Before you start

What this module is, and isn't

Every prior module taught one idea in isolation. This one teaches nothing new, it asks whether you can put seven ideas together under one brief without dropping any of them, which is the actual job. There's no new theory here, no new proofs, just the same rigor applied to a single realistic scenario end to end.

How grading works here

This module replaces the usual multiple-choice checkpoint with three real deliverables, graded from what you actually submit, not from boxes you tick yourself. Part 1 inspects the actual text of your design document for the specific technical content each section needs. Part 2 runs real automated tests against code you write, including a genuine concurrent-duplicate-request test. Part 3 checks your diagnosis of a real bug against the actual failure mode. Part 4 combines all three into one score.

How to work through it

  1. Read the brief carefully, twice, most real design failures come from missing a stated requirement, not from getting the theory wrong.
  2. Write your design document directly into Part 1's fields, then check it, and fix whatever comes back flagged.
  3. Complete the implementation in Part 2 and run the tests until they pass. A red test tells you exactly which behavior is wrong.
  4. Diagnose the bug in Part 3, then compare against the reference solution outline afterward, not to copy it, but to see how the same requirements can be satisfied a different valid way.

The brief

Client brief: Northstar Realty Group

Northstar runs paid ad campaigns across three platforms that each send a webhook to your system whenever someone submits a "request a callback" form. Your system must capture the lead, enrich it via a third-party CRM API, score it, and hand it off to a sales rep, exactly the Module 1 pipeline shape.

Three things are explicitly called out as risks in the brief, because they've each caused a production incident with Northstar's previous vendor:

  • A flaky downstream API. The CRM enrichment API has a documented 2% error rate and occasional multi-second latency spikes under its own load.
  • Duplicate webhook deliveries. All three ad platforms document at-least-once webhook delivery, with retries on their side if they don't get a fast 200 response.
  • Traffic spikes. Northstar runs occasional viral campaigns that can 8x their normal lead volume for a few hours with no advance warning.
What the brief is actually testing: every one of those three risks maps directly to a module you've already completed. A flaky downstream API is Module 3 (circuit breakers, retries). Duplicate webhook deliveries is Modules 2 and 5 (idempotency keys, HMAC verification). A traffic spike is Module 4 (queueing, the utilization cliff) and Module 3 again (bulkheading so the spike doesn't take down unrelated work). The brief isn't hiding the answer, it's telling you exactly which tools to reach for, the skill is recognizing the mapping.

Deliverable 1: the design specification

A complete design specification names the pipeline's shape (Module 1), every non-idempotent operation and how it's made safe (Module 2), and every external dependency's failure-handling strategy (Module 3). It should be readable by someone who hasn't seen the brief and still understand exactly what happens at each step and why.

What "complete" means here, concretely

A DAG or FSM diagram (or both, per Module 1's Section 6, use whichever fits each part), with every node labeled by what it does and what it depends on. For each node with a real-world side effect, a stated idempotency approach. For each node calling an external service, a stated retry and circuit-breaker policy, including what "fails" means for that specific call.

Practice check

The "receive webhook" step and the "enrich via CRM API" step both need failure-handling strategies, but not the same one. Why might they differ?

Check your answer
"Receive webhook" is you accepting a request, its main failure-handling concern is idempotency and authenticity (was this delivery genuine, and have we already processed it), from Modules 2 and 5. "Enrich via CRM API" is you calling someone else's flaky service, its main concern is retry behavior and failing fast if that dependency is down, from Module 3. Different roles in the pipeline face different failure modes, a good spec doesn't apply one generic "add retries" policy everywhere, it reasons about each step's actual risk.

Deliverable 2: idempotency, retry, and dead-letter handling

This is the "working implementation of the critical path" the brief asks for, the part that actually has to run, not just be described.

The critical path, concretely

1. Webhook received, HMAC signature verified (Module 5) before anything else happens, an unverified payload is never trusted. 2. An idempotency key derived from the platform's own event ID is checked via an atomic unique-constraint insert (Module 2), not a check-then-insert race. 3. The CRM enrichment call is wrapped in a circuit breaker (Module 3): normal retries with backoff and jitter while the breaker is Closed, fail-fast with no call attempted while Open. 4. A job that exhausts its retries goes to a dead-letter queue instead of being silently dropped, a durable record of "this needs a human," rather than a job that just vanishes.

Dead-letter handling, defined: when a job fails every retry attempt, don't discard it, write it to a separate durable store (a "dead-letter queue") with the failure reason and enough context to retry it manually or investigate it later. This is what turns "we silently lost some leads during the outage" into "we have a list of exactly which 40 leads need manual follow-up," a categorically different conversation with a client.
Practice check

Why does HMAC verification (step 1) need to happen before idempotency-key checking (step 2), rather than after?

Check your answer
Because an unverified payload's claimed event ID can't be trusted at all, an attacker could send junk with a fabricated ID designed to collide with or pollute your idempotency store. Verify authenticity first, so that only genuine events ever reach the logic that assumes their contents are trustworthy. Checking order matters: idempotency protects against duplicates from a legitimate sender, it isn't a substitute for verifying the sender is legitimate in the first place.

Deliverable 3: the SLO document

The brief asks for "a one-page SLO document you could hand directly to a client," which means it needs to be honest, specific, and grounded in the architecture you actually specified, not aspirational numbers, exactly Module 7's Section 3 process.

What belongs on that one page

An SLI tied to real business outcome ("percentage of leads that reach a rep within 5 minutes of form submission," not "server uptime"). An SLO with a stated time window. The error budget that implies. A one-line acknowledgment of the traffic-spike risk and how the design handles it (referencing your Module 4 capacity math). A one-line statement of the webhook contract's delivery/ordering/replay guarantees, Module 6's Section 4, so Northstar's own team knows what to expect if they ever build something downstream of your system.

Practice check

Why would "percentage of leads that reach a rep within 5 minutes" be a better SLI for this brief than "API uptime"?

Check your answer
Because API uptime can be 100% while leads still silently fail to reach a rep, stuck behind a circuit breaker that's open, or lost to an unhandled edge case, or delayed past the point of being useful. The SLI needs to measure the actual business outcome Northstar cares about, a lead in front of a rep, not a proxy metric that can look perfect while the real promise is being broken, exactly Module 7 Section 3's first rule: pick an SLI that reflects real user-facing behavior, not internal plumbing.

Reference solution outline

Not the only valid answer, a valid one. Compare your design's reasoning against this, not its exact wording.

Pipeline shape
Receive Webhook → Verify HMAC → Check Idempotency Key → Enrich (circuit-breaker wrapped) → Score → Assign, a DAG for one lead's processing run, plus a separate FSM for the lead's overall lifecycle (New → Enriching → Scored → Assigned → Contacted → Won/Lost), exactly the Module 1 pattern of using both models for what each is suited to.
Idempotency & duplicates
Idempotency key = the ad platform's own event ID, stored in a table with a UNIQUE constraint, inserted via INSERT ... ON CONFLICT before any processing begins. A duplicate delivery's insert fails the constraint, and the handler returns the original result instead of reprocessing.
Flaky dependency
The CRM enrichment call is wrapped in a circuit breaker: 5 consecutive failures trips it Open for 30 seconds, then Half-Open allows one probe. Retries within the Closed state use exponential backoff with full jitter, capped at 3 attempts before the job is written to a dead-letter queue with the failure reason and original payload.
Traffic spikes
Capacity math (Module 4) against historical peak volume shows normal utilization around ρ=0.6; a viral 8x spike would push that well past 1, so ingestion is decoupled from processing via a queue, accepting webhooks fast (returning 200 immediately after signature verification and idempotency check) and processing enrichment asynchronously, so a spike produces a longer queue, not failed webhook deliveries. The enrichment worker pool is bulkheaded separately from any other integration's worker pool.
SLO document
SLI: "% of leads reaching a rep within 5 minutes of submission." SLO: 98% over a rolling 7 days (conservative, given the flaky third-party dependency this design doesn't fully control). Error budget: 2%. Webhook contract: at-least-once delivery, ordering not guaranteed (sequence field provided), replay accepted up to 24 hours, consumers must be idempotent.
