Module 01

Formal Models of Workflow Execution

Every automation platform you have ever used, whether it admits it or not, is executing a directed acyclic graph or a state machine underneath its drag-and-drop interface. This module makes that structure explicit, so you can reason about correctness instead of trusting the tool.

Learning objectives
  • Model a business process as a directed acyclic graph (DAG) and compute a valid execution order
  • Explain why a cycle in a dependency graph makes a workflow unschedulable, and how that failure is detected
  • Specify a state machine with guarded transitions and trace a valid execution path through it
Before you start

What this course is

Automation Engineering is an 8-module course on the ideas that every workflow tool, no-code or otherwise, is built on top of. The goal isn't to teach you a specific product's UI, it's to give you the small set of computer-science models (graphs, state machines, delivery guarantees) that let you predict how any automation system will behave before you build it, and diagnose it correctly when it doesn't.

What this module does

Module 1 introduces the two models the rest of the course builds on: the DAG (for "what order do these steps run in, and what can happen at once") and the finite state machine (for "what state is this record in, and what's allowed to happen to it next"). Later modules, idempotency, retries, distributed state, all assume you can read and reason about both. That's the entire reason this module exists: everything after it is easier once these two are second nature.

What's assumed

No prior computer science theory. Every term (vertex, in-degree, guard, transition) is defined the first time it's used.
Comfort with basic logic (if/then, true/false) is helpful but not required, the definitions are self-contained.
If a proof section feels dense on first read, that's normal, skim it once for the shape of the argument, then come back after the interactive below it.

How to work through it

  1. Read the definition, then the short proof or explanation under it, proofs are there to show why a rule is true, not just to assert it.
  2. Run the live interactive for that concept, it's the same logic as the definition, just executing in front of you.
  3. Answer the practice check that follows, these are ungraded and self-scored, their only job is to catch whether the idea actually stuck before you move on. Do them, don't skip to the reveal.
  4. Finish with the graded checkpoint at the end of the module.
1

Workflows as graphs

A workflow is a set of tasks with dependencies between them. Formally, this is a graph G = (V, E) where V is the set of tasks and a directed edge (u, v) ∈ E means "task u must complete before task v can begin." For a workflow to be schedulable at all, that is, for there to exist any valid order to run the tasks in, the graph must be a directed acyclic graph: a graph with no directed cycles.

Definition: topological order

A topological order of a DAG is a linear ordering of its vertices such that for every directed edge (u, v), u appears before v in the ordering. A DAG can have more than one valid topological order; a graph with a cycle has none.

Below is a real pipeline: a lead comes in, gets validated, then two independent enrichment steps run (they don't depend on each other), and both must finish before the lead can be assigned to a rep. This is exactly the branching structure of the Lead Capture & Follow-Up system.

Why this matters beyond correctness: a topological order is rarely unique, and that's not a curiosity, it's the whole reason production schedulers exist. In the pipeline below, Enrich Data and Score Lead both depend only on Validate and neither depends on the other, so they form an antichain: a set of nodes with no path between any pair of them. Any two nodes in an antichain can run concurrently without violating a single dependency. A scheduler that only knows "some valid order exists" and runs steps one at a time is leaving that parallelism on the table; a scheduler that understands the DAG structure can identify the widest antichain at each layer and fan work out across workers. This is precisely what tools like Airflow, Temporal, and Dagster are doing under the hood when they say a DAG run has "parallel tasks", they're computing layers of the same graph you're about to run Kahn's algorithm on.

You just watched Kahn's algorithm run to completion without getting stuck. That wasn't luck, and it isn't specific to this particular graph. It's guaranteed, for every finite DAG, no matter its shape, and it's worth seeing exactly why before moving on, because the "why" is what tells you the algorithm can be trusted on a graph you've never seen.

Claim: every finite DAG has at least one topological order

Proof sketch, by induction on |V| = n.

  1. Base case (n = 1). A graph with a single vertex and no edges trivially has a valid order: itself.
  2. Inductive hypothesis. Assume every DAG with fewer than n vertices has a topological order.
  3. A vertex with in-degree zero must exist. Take a DAG G with n vertices. If every vertex had at least one incoming edge, you could walk backward along incoming edges forever; in a finite graph that walk must eventually repeat a vertex, which is a cycle, contradicting acyclicity. So some vertex v has in-degree zero, this is exactly the "ready" state you watched nodes enter in the simulation above.
  4. Remove it and recurse. Removing v and its outgoing edges leaves a graph with n − 1 vertices that is still a DAG (deleting a vertex cannot create a cycle). By the inductive hypothesis, it has a topological order.
  5. Reassemble. Prepend v to that order. Every edge out of v now points to something later in the sequence, and every other edge is unaffected, so the result is a valid topological order of G. ∎

This is exactly the argument Kahn's algorithm executes mechanically: repeatedly strip off an in-degree-zero vertex. The proof isn't just decorative, it's a certificate that the algorithm you just ran cannot get stuck on a true DAG. If it ever does get stuck, that's not a bug in the algorithm, it's proof the input wasn't acyclic, exactly what Section 3 turns into a detection technique. Run to completion, Kahn's algorithm does exactly one constant-time visit per vertex and one decrement per edge, so it runs in O(V + E) time, linear in the size of the graph.

Practice check

Without scrolling back up: what property must a vertex have for Kahn's algorithm to be allowed to remove it next? And in the proof above, what goes wrong if no vertex in a nonempty graph has that property?

Check your answer
In-degree zero, no remaining unprocessed dependency. If no vertex in a nonempty graph has in-degree zero, the "walk backward along incoming edges" argument in the proof forces a repeated vertex, which is a cycle. So a nonempty DAG is guaranteed to always have at least one in-degree-zero vertex; if you ever see a nonempty graph with none, it isn't a DAG.

3

Why cycles break scheduling

Kahn's algorithm, which the simulation above just ran, repeatedly removes any node with in-degree zero (no remaining unprocessed dependencies) and appends it to the order. If at any point no node has in-degree zero but nodes remain, the graph contains a cycle, no valid order exists, and the algorithm halts with an unschedulable result rather than looping forever.

This is precisely how you should detect a misconfigured workflow before deploying it: if step A waits on step B, and step B (transitively) waits on step A, no scheduler, however clever, can run it. The fix is architectural, not algorithmic.

Claim: Kahn's algorithm terminates with fewer than |V| nodes in the order if and only if a cycle exists

(⇐) If the algorithm outputs fewer than |V| nodes, a cycle exists.

  1. Suppose it halts having emitted k < n nodes. The remaining n − k nodes all have in-degree ≥ 1 within the remaining subgraph, that's the only reason the algorithm would stop early.
  2. Pick any remaining node v₀ and walk backward along one of its incoming edges to some v₁, which is also remaining and also has in-degree ≥ 1. Repeat.
  3. Since the remaining set is finite, this backward walk must eventually revisit a node. The segment of the walk between the two visits is a directed cycle. ∎

(⇒) If a cycle exists, the algorithm cannot emit all n nodes.

  1. Every node on a cycle has at least one incoming edge from another node on that same cycle.
  2. For any node on the cycle to reach in-degree zero, every node on the cycle would need to have already been removed first, including itself, that's circular by construction.
  3. So no node on the cycle can ever be removed, and the algorithm halts with those nodes stuck. ∎

A second, independent way to detect the same condition is depth-first search with a "currently on stack" marker: if DFS ever follows an edge into a node that is still on the current recursion stack (as opposed to merely already visited), that back-edge is a cycle. Both approaches run in O(V + E) time, Kahn's because each vertex and edge is processed exactly once as in-degrees are decremented, DFS-based detection because it's a single traversal. In practice, Kahn's algorithm is usually preferred for scheduling because it produces the valid order as a byproduct of detection; DFS-based detection is preferred when you only need a yes/no answer and want to report the exact cycle, since the recursion stack at the point of the back-edge is the cycle.

Common failure in practice: a "retry" step that re-triggers an earlier stage of the same pipeline on failure looks harmless in a visual builder, but it introduces exactly this kind of cycle if not handled as a distinct recovery path with its own termination condition. Module 3 covers the correct pattern.
A second real-world example: two independent systems, a CRM and a billing platform, are each configured to "sync on change" from the other: the CRM pushes an update to billing whenever a deal closes, and billing pushes an update to the CRM whenever an invoice status changes, and each of those pushes is itself modeled as a change that triggers the other side again. Drawn as a graph, CRM → Billing → CRM is a two-node cycle. Unlike the retry case, there's no visual builder here at all, the cycle exists purely in the interaction between two systems that were each individually reviewed and looked fine. This is why cycle analysis has to be done at the level of the full dependency graph across systems, not per-system.
Practice check

Take the pipeline graph from Section 1 and add a single new edge from Assign to Rep (E) back to Validate (B). Which nodes would Kahn's algorithm still be able to place in the order, and which would it get stuck on?

Check your answer
A (Receive Lead) still has in-degree zero and gets placed first. Workflows as state machines

The DAG view describes task dependencies. A complementary view describes the lifecycle of a single unit of work, in this case, one lead, as it moves through the system. This is a finite state machine: a set of states, and a set of guarded transitions between them.

Formal definition: finite state machine

A finite state machine is a 5-tuple (S, Σ, δ, s₀, F) where S is a finite set of states, Σ is a finite set of actions (the input alphabet), δ: S × Σ → S is the transition function, s₀ ∈ S is the initial state, and F ⊆ S is the set of terminal states. For the lead lifecycle used throughout this module (the same one you'll run in Section 5), S = {New, Validating, Validated, Enriching, Scored, Assigned, Contacted, Rejected, Won, Lost}, s₀ = New, and F = {Rejected, Won, Lost}. Note that Assigned is not terminal, a lead that's assigned still has to be contacted and closed before the lifecycle ends.

Full state graph, all ten states and every transition at once. Lime border = start state, violet border = terminal (in F). This is the whole machine; the interactive in Section 5 walks it one transition at a time.
Definition: guarded transition

A transition (s₁, action, s₂) moves the system from state s₁ to state s₂ when action occurs, but only if the transition's guard (a boolean condition) holds. A lead can only move from Scored to Assigned if the guard score ≥ 70 is satisfied; otherwise the Scored → Lost transition applies instead.

Two things are worth being precise about here, because they're the two ways this model breaks in production. First, determinism: the formal δ: S × Σ → S definition maps each (state, action) pair to exactly one next state, that's what makes the system predictable. In the guarded version we're actually using, the same action from the same state can have multiple candidate transitions (Scored →Assigned, Scored → Lost, both triggered by the same "score computed" event), and determinism is recovered only if the guards are mutually exclusive (no two guards can be true at once) and jointly exhaustive (at least one guard is always true). If you add a third outcome later, say, "needs manual review", and forget to also tighten the existing score ≥ 70 guard to exclude that new band, you've silently created a state where two transitions are simultaneously legal, and which one fires becomes an implementation detail rather than a specified behavior. That is a live bug class, not a hypothetical.

Second, note that a strict automata-theory FSM only accepts or rejects a sequence of actions, it has no side effects. What we're actually modeling, a machine that performs work (send an email, write a CRM record) on each transition, is more precisely a Mealy machine (output attached to the transition) or Moore machine (output attached to the state). Almost every workflow engine you'll touch professionally, Stripe's subscription lifecycle, AWS Step Functions, a CRM's deal pipeline, is a Mealy machine wearing an FSM diagram. The distinction matters when debugging: if an action seems to have "not fired," check whether you're looking for it on the transition (Mealy) or expecting it to persist as long as you're in the resulting state (Moore).

Practice check

Write out the 5-tuple (S, Σ, δ, s₀, F) for a simple traffic light that cycles Red → Green → Yellow → Red, with no other transitions. What is F?

Check your answer
S = {Red, Green, Yellow}. Σ = {timer expires} (the only action, in this simplified version). δ(Red, timer expires) = Green, δ(Green, timer expires) = Yellow, δ(Yellow, timer expires) = Red. s₀ = Red (or whichever the light starts on). F = ∅, the empty set, because this machine never terminates, it cycles forever. That's a legitimate FSM: terminal states are optional, not every machine needs one.

6

Combining the two models

The DAG and the FSM are not competing descriptions of the same thing, they answer different questions and a real system needs both. The DAG answers: for one execution, what order must these steps run in, and what can run in parallel? It's scoped to a single run and typically completes in seconds. The FSM answers: where is this particular lead right now, in a lifecycle that may span days or weeks and involve waiting on a human? It's scoped to one long-lived entity and has no notion of "finishing" in the DAG sense, Assigned and Lost are both valid resting points, not "success" and "failure" of a computation.

Concretely, in the Lead Capture & Follow-Up system: each time a lead moves through Validate → Enrich → Score, that's one DAG execution, scheduled and run to completion in milliseconds. The result of that DAG run (a score) is what fires a guarded transition in the lead's FSM. The FSM doesn't re-run the DAG logic and the DAG doesn't track history across leads, they're composed, not merged. This is also why the two failure modes look different: a cycle in the DAG is a static configuration error you can catch before deploying (as in Section 3), while an invalid FSM transition is a runtime error you only catch by attempting an action from a state that doesn't permit it, which is exactly what the guard-checked buttons in Section 5 were preventing you from doing.

Rule of thumb: if the question is "what order" or "what can happen at the same time," you're modeling a DAG. If the question is "what state is this record in" or "what's allowed to happen next," you're modeling an FSM. Reaching for the wrong one is the single most common structural mistake in workflow design, using an FSM for step ordering produces a combinatorial explosion of states (one state per subset of completed steps), and using a DAG for entity lifecycle loses the ability to represent "waiting indefinitely for a human."
Practice check

For a customer onboarding process: is "has the welcome email been sent" better modeled as a step in a DAG or a state in an FSM? Justify in one sentence using the rule of thumb above.

Check your answer
It depends on scope, and that's the actual lesson. If it's one action within a single onboarding run that completes in seconds ("send welcome email" as a task with dependencies before/after it), it's a DAG step. If "welcome email sent" is a durable fact about a customer record that other, later, independent processes need to check days or weeks afterward ("has this customer been welcomed yet, regardless of how"), it's better modeled as a boolean or state on the customer's FSM. The tell is persistence and reference from outside the original run.

Before the checkpoint: what you should now be able to do

A short consolidation before you're graded on it. If any of these feel shaky, that's a signal to scroll back to the relevant section, not a reason to skip ahead.

  • State what a topological order is, and explain, without looking it up, why every finite DAG is guaranteed to have at least one.
  • Trace Kahn's algorithm by hand on a small graph, and explain what its failure to place every vertex tells you about that graph.
  • Given any two nodes in a DAG, determine whether they're forced into a fixed order or free to run in parallel (i.e., recognize an antichain).
  • Write out the 5-tuple (S, Σ, δ, s₀, F) for a small state machine you're given, including identifying which states are terminal.
  • Spot a guard-design bug: two transitions off the same state, triggered by the same event, whose guards overlap or leave a gap.
  • Decide, for a given piece of workflow logic, whether it belongs in a DAG or an FSM, and justify the choice by scope (single-run vs. long-lived record).

Further reading

This module's DAG treatment follows the standard algorithms-course presentation. If you want to go deeper than the browser can take you:

  • A. B. Kahn, "Topological sorting of large networks," Communications of the ACM, 1962, the original paper describing the algorithm you ran in Section 2.
  • Cormen, Leiserson, Rivest & Stein, Introduction to Algorithms (CLRS), Chapter 22, for the DFS-based topological sort and formal cycle-detection proofs in full rigor.
  • David Harel, "Statecharts: A visual formalism for complex systems," Science of Computer Programming, 1987, the paper that extended flat FSMs to the hierarchical and concurrent states used by most real workflow engines.
  • In production, the ideas here show up directly in Apache Airflow and Dagster (DAG scheduling), and in Temporal, AWS Step Functions, and Stripe's subscription/billing state machines (guarded FSM transitions).

Glossary

Every term below was defined in place the first time it appeared, this is just a lookup table for later, when you're three modules ahead and need a one-line reminder.

vertex / node — a single task (in a DAG) or a single state (in an FSM).
in-degree — the number of edges pointing into a vertex; in-degree zero means no unmet dependencies.
DAG — directed acyclic graph; a graph with directed edges and no cycles, the structure that makes scheduling possible at all.
topological order — a linear ordering of a DAG's vertices consistent with every edge's direction; may not be unique.
antichain — a set of vertices with no path between any pair; an antichain is exactly the set of steps safe to run in parallel.
Kahn's algorithm — repeatedly remove an in-degree-zero vertex and append it to the order; O(V + E); failing to place every vertex proves a cycle.
finite state machine (FSM) — a 5-tuple (S, Σ, δ, s₀, F): states, actions, transition function, start state, terminal states.
guard — a boolean condition attached to a transition that must hold for the transition to fire.
determinism — exactly one legal next state per (state, action) pair; with guards, this requires the guards to be mutually exclusive and jointly exhaustive.
Mealy / Moore machine — an FSM with side effects: Mealy attaches output to the transition, Moore attaches it to the state.
