Module 03

Failure Handling & Retry Theory

Naive retry loops synchronize into thundering herds and take down the service they were trying to reach. This module derives exponential backoff with jitter mathematically, then covers circuit breakers and bulkheads as the two remaining primitives every resilient integration needs.

Learning objectives
  • Derive and implement exponential backoff with decorrelated jitter, and explain why plain exponential backoff still fails under load
  • Design a circuit breaker state machine (closed / open / half-open) with correct transition conditions
  • Apply bulkheading to prevent one failing integration from starving the whole system
Before you start

What this module assumes

Module 2 established that duplicate delivery is unavoidable and retries are how clients cope with uncertainty. This module assumes that's settled, and asks the next question: if retrying is mandatory, how do you retry without making the outage you're retrying against worse?

The thundering herd

A downstream service goes down, a deploy, a database failover, a certificate expiring. Every client currently calling it gets an error at roughly the same moment, because they were all calling it at roughly the same rate before. If every one of those clients retries using the same fixed delay, say, "wait 2 seconds and try again," they all retry at roughly the same moment too. The service, which may have just come back up and is still warming caches or reconnecting its own dependencies, gets hit by the full pre-outage load in a single instant instead of a gradual ramp. This can knock it back down, at which point every client fails again, waits the same fixed delay again, and retries again in the same synchronized wave. The retry logic that was supposed to help recovery is now the thing preventing it.

Definition: thundering herd (retry storm)

A failure mode where a large number of clients, having failed at approximately the same time, retry at approximately the same time, because their retry logic is deterministic and synchronized. The herd's arrival can exceed the recovering service's capacity even though the herd's steady-state load was well within that capacity.

The counterintuitive part: the problem isn't that clients retry, retrying is correct and necessary, as Module 2 established. The problem is that they retry in sync. A system that spreads the exact same number of retry attempts across a wider window can survive an outage that a perfectly synchronized version of itself cannot, with zero change to how many requests are eventually sent.
Practice check

Without looking back: why does a service recovering from an outage sometimes fail again immediately, even though the load it's receiving is, on average, no higher than what it normally handles?

Check your answer
Because "on average" hides the shape of the arrival pattern. If the same total number of requests arrives spread evenly over a minute versus all in the first second, the service sees wildly different peak concurrency even though the average is identical. Synchronized retries concentrate load into a spike at exactly the moment the service is least able to absorb it, right as it's coming back up.

Run "No backoff" and "Exponential, no jitter" back to back and compare the peak concurrent-attempts number. Both are deterministic strategies, does exponential backoff alone fix the synchronized spike? Why or why not?

Check your answer
No. Every client that failed at tick 0 computes the exact same delay sequence under plain exponential backoff, because the formula has no randomness in it, so they all land on the same retry ticks as each other. Exponential backoff changes when the synchronized spikes happen and how far apart they are, but it doesn't stop them from being synchronized. Only adding randomness (jitter) spreads clients across different ticks instead of the same ones.
3

Deriving exponential backoff

The starting intuition is right: don't retry immediately, wait longer after each successive failure, so a client that's failing repeatedly backs off and gives the service room to recover instead of hammering it. The standard formula:

Definition: exponential backoff

delay(n) = min(cap, base × 2ⁿ), where n is the number of consecutive failures so far (0-indexed), base is the initial delay, and cap is a maximum delay so the wait doesn't grow unbounded. With base = 1s: attempt 0 waits 1s, attempt 1 waits 2s, attempt 2 waits 4s, attempt 3 waits 8s, and so on until the cap.

This solves a real problem: it reduces the total request rate a struggling service receives from any single persistently-failing client, and it reduces how long a client hammers a service that's genuinely down versus one having a brief blip. But as the practice check above should have made concrete, it does not solve the thundering herd, because it's entirely deterministic. If two clients fail at the same tick, they compute the same delay at every subsequent step and retry together, forever.

Claim: any deterministic backoff function preserves synchronization

Proof. Suppose clients A and B both experience their first failure at the same time t₀, and both use the same deterministic function delay(n) with no randomness. By induction on n: if A and B's n-th retry happens at the same time tₙ (true for n=0, both retry at t₀ + delay(0)), and both retries fail (the service is still down), then both compute delay(n+1), the same value since the function is deterministic and both have failed the same number of times, and so both schedule their next retry at tₙ + delay(n+1), again identical. By induction, A and B remain synchronized at every retry for as long as the outage lasts. ∎

The only way to break this induction is to make delay(n) not purely a function of n, to introduce randomness so that two clients with an identical failure history compute different delays anyway. That's jitter.

Practice check

The proof above assumes both clients fail at exactly the same tick to begin with. In reality, could two clients that first failed at slightly different times still end up retrying at the same tick under plain exponential backoff? What does that imply about how robust the "just stagger the initial failures" idea is?

Check your answer
Yes, easily, because delay(n) only depends on n, not on wall-clock time, two clients whose failures are offset by a few milliseconds still compute delays that round to the same tick in any discretized system, and worse, delays can coincidentally realign later even if they start apart (e.g., one client's coarser retry cadence catches up to another's). Relying on "failures probably won't be perfectly simultaneous" is fragile, it only takes approximate alignment to reproduce the spike, which is exactly why jitter needs to be built into the delay function itself, not assumed away by initial conditions.
4

Jitter: breaking the synchronization

Jitter adds randomness to the delay so that clients with identical failure counts still schedule different retry times. Not all jitter strategies are equally good, three are standard, of increasing quality:

Three jitter strategies

Full jitter: delay(n) = random(0, min(cap, base × 2ⁿ)). Simple and effective at desynchronizing, but the expected wait is only half of plain exponential backoff's value, and a client can get unlucky with a near-zero delay repeatedly.

Equal jitter: delay(n) = half + random(0, half) where half = min(cap, base × 2ⁿ) / 2. Guarantees at least some backoff every time, trading off some of full jitter's desynchronizing power for a floor on the wait.

Decorrelated jitter: delay(n) = min(cap, random(base, prev_delay × 3)), each delay is randomized based on the previous actual delay, not just the attempt count. AWS's applied-engineering literature (Brooker, 2015) found this performs best in practice: it retains an increasing trend on average like exponential backoff, but the randomization compounds across attempts instead of resetting each time, spreading retries wider the longer an outage persists.

Why "full jitter" being simpler doesn't make it worse in every case: for a single outage of unknown length, full jitter is a completely reasonable default and is what most HTTP client libraries implement out of the box. Decorrelated jitter earns its complexity specifically at large scale, thousands of clients, long-lived outages, where its wider spread and increasing trend measurably reduce peak concurrent load compared to full jitter. Don't reach for it on a project with ten integrations calling one API; reach for it when you've measured that full jitter isn't enough.
Practice check

Go back to the Section 2 interactive and run "Exponential + full jitter" three or four times. Does the peak concurrent-attempts number stay exactly the same across runs, the way it does for the deterministic strategies? What does that tell you about jitter's guarantee?

Check your answer
No, it varies run to run, because jitter is random by design. That's the honest tradeoff: jitter doesn't guarantee zero spike, it reduces the expected and typical peak by spreading attempts probabilistically. A truly unlucky draw could still cluster several clients on the same tick. What jitter buys you is a much lower expected peak and a much lower chance of the worst case, not a mathematical impossibility of any clustering at all.

Build a production retry function

You've watched backoff and jitter work in a simulation. Now you implement the actual function, and five real tests run against it, including checking that your delays genuinely respect the cap and genuinely vary under jitter, not just that your function eventually returns a value.

Code exercise · runs in your browser

Complete retryWithBackoff(operation, options, sleep). operation is an async function that may reject. options is { maxRetries, baseDelay, maxDelay, jitter }. Call the provided sleep(ms) between attempts, don't use your own timer, the tests measure exactly what you pass to it.

Stuck? Hints
Hint 1 — conceptual
You need a loop that tries the operation, and on failure waits before trying again, with the wait growing each time. What has to stop the loop from waiting forever: a max number of attempts, or a max delay, or both?
Hint 2 — specific
Compute the capped delay as Math.min(options.maxDelay, options.baseDelay * 2 ** attempt). options.jitter is a boolean, not a number, when it's true, use "full jitter": a random value between 0 and that capped delay, not the capped delay itself. Call await sleep(delay) with that number, don't use setTimeout directly.
Hint 3 — near-solution
Wrap the whole thing in a for-loop up to options.maxRetries + 1 attempts. Try/catch each call to operation(); on success return immediately. On failure, if you're on the last allowed attempt, rethrow the error instead of sleeping again, otherwise compute the capped delay, then if jitter is true replace it with Math.random() * capped (never above the capped value, never negative), and await sleep(delay) before the next loop iteration.
Solution — run your code at least once first
async function retryWithBackoff(operation, options, sleep) {
  const { maxRetries, baseDelay, maxDelay, jitter } = options;
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await operation();
    } catch (err) {
      if (attempt === maxRetries) throw err;
      const capped = Math.min(maxDelay, baseDelay * 2 ** attempt);
      const delay = jitter ? Math.random() * capped : capped;
      await sleep(delay);
    }
  }
}
Practice check

Test 4 checks that every recorded delay stays at or below maxDelay. Which line of your implementation is responsible for that, and what would happen to Test 4 specifically if you forgot it?

Check your answer
The Math.min(maxDelay, ...) (or equivalent cap) applied to the computed exponential delay before it's passed to sleep. Without it, delay(n) grows unbounded as n increases, base × 2ⁿ, so a handful of retries would produce delays in the tens of thousands of milliseconds, and Test 4 would catch a recorded delay value exceeding maxDelay and fail specifically on that assertion, not on whether your function eventually succeeds.

Circuit breakers: stopping the call before it happens

Backoff and jitter make retries spread out and slow down, but they don't stop a client from attempting a call to a service that's confirmed, repeatedly, to be down. A circuit breaker adds a layer above retries: after enough consecutive failures, it stops attempting the call at all for a while, failing immediately without touching the network, then cautiously tests whether the dependency has recovered before fully resuming.

Formal definition: circuit breaker as a finite state machine

Three states, exactly the formalism from Module 1: S = {Closed, Open, Half-Open}, s₀ = Closed. Closed: requests flow through normally; failures are counted. Open: requests fail immediately without being attempted, "fail fast." Half-Open: a single probe request is allowed through to test recovery.

Guarded transitions: Closed → Open when the failure count reaches a threshold within a window (e.g., 5 consecutive failures). Open → Half-Open when a cooldown timer elapses. Half-Open → Closed when the probe request succeeds. Half-Open → Open when the probe request fails.

Four transitions total: the short curve is Half-Open → Open on probe failure, re-arming the cooldown; the long curve is Half-Open → Closed on probe success, the recovery path.
Why Half-Open matters, not just Closed and Open: without it, the only options are "hammer a dead service" (no breaker) or "wait a fixed time then fully reopen the floodgates" (Closed/Open only), which just reproduces the thundering herd from Section 1 at the moment the breaker resets. Half-Open lets exactly one request test the waters, so a still-broken dependency gets one failed probe instead of a full traffic spike, and a recovered dependency gets confirmed before the breaker fully trusts it again.
Practice check

A circuit breaker is Half-Open and its single probe request succeeds. Should it immediately jump to sending 100% of traffic through as Closed, or is there a case for something more gradual? (There's no single correct answer graded here, reason it through.)

Check your answer
The basic three-state model does jump straight to Closed on one success, and that's a legitimate, simple design. But one success is a small sample, some real implementations add a gradual ramp (e.g., allow a slowly increasing percentage of traffic through while still Half-Open-like, only fully closing after several consecutive successes) specifically because a dependency can pass one probe and then immediately buckle under full load again. This is the same thundering-herd logic from Section 1 applied to the recovery side: a single success is weak evidence, and dumping full load on weak evidence risks re-triggering the exact failure you were protecting against.

Build a circuit breaker

You've clicked through a circuit breaker's transitions by hand. Now you implement the state machine itself, and five tests verify it actually enforces the guarded transitions, not just that it has three state names.

Code exercise · runs in your browser

Complete createCircuitBreaker(options, clock), returning { call(fn), getState() }. options is { failureThreshold, cooldownMs }. clock.now() returns the current time in ms, use it instead of Date.now() so tests can control time precisely. call(fn) should invoke fn() when Closed or probing Half-Open, and reject immediately without calling fn at all when Open and the cooldown hasn't elapsed.

Stuck? Hints
Hint 1 — conceptual
You need to track two things across calls: how many consecutive failures have happened, and what state you're in (Closed, Open, Half-Open). Closed→Open happens on the threshold. Open→Half-Open happens on elapsed time, not on a new call arriving.
Hint 2 — specific
In call(fn), first check: if state is Open and clock.now() - openedAt < cooldownMs, reject immediately without calling fn. If the cooldown HAS elapsed, move to Half-Open and allow exactly one trial call through.
Hint 3 — near-solution
On a successful call while Half-Open, reset the failure count to 0 and go back to Closed. On a failed call while Half-Open, go straight back to Open and record a new openedAt = clock.now(). On a failed call while Closed, increment the failure count, and if it reaches failureThreshold, transition to Open.
Solution — run your code at least once first
function createCircuitBreaker(options, clock) {
  const { failureThreshold, cooldownMs } = options;
  let state = "CLOSED", failures = 0, openedAt = 0;
  return {
    getState(){ return state; },
    async call(fn) {
      if (state === "OPEN") {
        if (clock.now() - openedAt < cooldownMs) throw new Error("circuit open");
        state = "HALF_OPEN";
      }
      try {
        const result = await fn();
        state = "CLOSED"; failures = 0;
        return result;
      } catch (err) {
        failures++;
        if (state === "HALF_OPEN" || failures >= failureThreshold) {
          state = "OPEN"; openedAt = clock.now();
        }
        throw err;
      }
    },
  };
}
Practice check

Test 3 checks that a call while Open never invokes the wrapped function at all, not that it invokes it and gets an error back. Why does that distinction matter for what a circuit breaker is actually for?

Check your answer
The entire point of Open, per Section 6, is to fail fast without touching the network or tying up any resource waiting on a call that's very likely to fail anyway. If your implementation calls fn() and then discards or catches its result while Open, you've built a breaker that still pays the full cost of every call, timeouts, threads, connections, it just ignores the outcome. That's not a circuit breaker, that's a circuit breaker-shaped wrapper that does nothing. Test 3 is checking the mechanism, not just the label.

Bulkheads: containing the blast radius

Backoff, jitter, and circuit breakers all describe how a client behaves toward one dependency. Bulkheading is about what happens when that one dependency is misbehaving and your system talks to several dependencies at once.

Definition: bulkhead

Partitioning shared resources (thread pools, connection pools, queues) so that one integration's failures can only exhaust its own partition, not the resources every other integration also depends on. Named after ship bulkheads: a hull breach floods one compartment, not the whole vessel.

Without bulkheading, a common failure looks like this: your system has one shared pool of 50 worker threads, used for calling the CRM API, the email provider, and the SMS provider. The SMS provider starts timing out slowly instead of failing fast, each call ties up a worker thread for 30 seconds before giving up. If SMS traffic is even a modest fraction of total calls, enough workers get tied up waiting on a slow SMS provider that CRM and email calls, which have nothing to do with SMS, start queuing behind them and missing their own deadlines. One degraded dependency degrades everything.

The fix: give each dependency its own bounded pool, e.g., 15 threads for SMS, 15 for CRM, 15 for email, with 5 held in reserve. Now a fully-saturated SMS pool can only ever block SMS-related work. CRM and email keep running at full capacity, unaware anything is wrong. Combined with a circuit breaker on the SMS integration specifically, the system detects and isolates the failure instead of slowly bleeding out across every feature.
Practice check

A system with a shared connection pool across three integrations experiences one integration going slow. Without bulkheading, why does this eventually cause errors on the other two integrations, even though nothing about them changed?

Check your answer
Because the shared pool has a fixed size, and connections tied up waiting on the slow integration are connections unavailable to the healthy ones. Once enough connections are stuck, the healthy integrations start failing purely from resource starvation, not because anything about their own dependency changed, but because they're competing for a resource that a different, unrelated failure is monopolizing.

Module 2 established that duplicate requests are unavoidable and must be handled idempotently. How does that interact with the retry material in this module, does adding retries make the idempotency requirement more important, less important, or unrelated?

Check your answer
More important, and directly so. A system with great backoff strategy but no idempotent handling on the receiving side still double-charges the card, it just does it on a nicer schedule. Retry theory and idempotency aren't separate concerns, retries are exactly what makes idempotency non-optional in the first place.

Glossary

thundering herd — many clients retrying in synchronization, overwhelming a recovering service despite normal average load.
exponential backoff — delay(n) = min(cap, base × 2ⁿ); grows the wait after each consecutive failure.
jitter — randomness added to a backoff delay so clients with identical failure counts still desynchronize.
full / equal / decorrelated jitter — three standard jitter formulas trading off simplicity, minimum wait guarantees, and spread under sustained outages.
circuit breaker — a 3-state FSM (Closed/Open/Half-Open) that stops attempting calls to a confirmed-failing dependency and cautiously tests recovery.
bulkhead — partitioned resource pools so one dependency's failure can't exhaust resources shared with unrelated work.
