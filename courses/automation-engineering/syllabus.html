Course description

Most automation courses teach you which buttons to click in a drag-and-drop builder. This one does not. It teaches the theory that makes automation systems correct and reliable under real-world failure, the same material a distributed-systems engineer would study, applied specifically to the workflow-automation domain: lead pipelines, integration chains, and event-driven business logic.

You will finish able to design a workflow system from a formal specification, reason rigorously about failure modes before they happen in production, and defend your architectural decisions to a technical client, not just assemble one from a template.

Why this bar, not a tutorial bar: tutorials teach a tool. Tools get replaced. The theory in this course, idempotency, exactly-once semantics, queueing behavior, retry mathematics, does not expire when the next automation platform launches. It is the actual engineering knowledge that separates a $50/hr template-assembler from an automation engineer clients trust with revenue-critical systems.
Prerequisite: comfortable writing code (any language) Prerequisite: basic HTTP / REST familiarity No prior automation-platform experience required

Learning outcomes

Formal reasoning

Model any workflow as a directed graph or state machine and prove properties about it: reachability, termination, valid execution orders.

Failure-first design

Design for exactly-once delivery, idempotent operations, and graceful degradation before a single failure happens in production.

Capacity reasoning

Apply queueing theory to predict whether a workflow system will keep up under load, and where it will break first.

Secure integration

Implement OAuth2 flows and HMAC-signed webhooks correctly, understanding the cryptographic reasoning, not just copy-pasting a library call.

Module sequence

Each module pairs a formal concept with an interactive simulation you manipulate directly, and closes with a graded problem set. Module 1 is open for preview.

MODULE 01

Formal Models of Workflow Execution

Week 1 Preview open →

Every workflow is a directed acyclic graph or a state machine, whether the tool that built it admits this or not. This module formalizes that claim: nodes, edges, topological ordering, and the state-machine semantics that govern valid transitions in a running pipeline.

You will be able to
  • Model a business process as a DAG and compute a valid execution order via topological sort
  • Distinguish a workflow that can deadlock from one that provably cannot
  • Specify a state machine with guards and prove which transitions are reachable
▶ interactive: DAG execution-order simulator + state-machine walker
MODULE 02

Idempotency & Exactly-Once Semantics

Week 2

Networks fail mid-request. Clients retry. Without idempotency, a retried "charge the card" becomes two charges. This module derives idempotency key design from first principles and distinguishes at-most-once, at-least-once, and exactly-once delivery, and why the third one is usually a lie your tooling tells you.

You will be able to
  • Design an idempotency-key scheme that survives concurrent duplicate requests
  • Explain why "exactly-once" is achieved via at-least-once delivery plus idempotent handling, not a magic transport guarantee
  • Identify non-idempotent operations in an existing workflow and fix them
▶ interactive: duplicate-request race simulator
MODULE 03

Failure Handling & Retry Theory

Week 3

Naive retry loops synchronize into thundering herds and take down the service they were trying to reach. This module derives exponential backoff with jitter mathematically, then covers circuit breakers and bulkheads as the two remaining primitives every resilient integration needs.

You will be able to
  • Derive and implement exponential backoff with decorrelated jitter, and explain why plain exponential backoff still fails under load
  • Design a circuit breaker state machine (closed / open / half-open) with correct transition conditions
  • Apply bulkheading to prevent one failing integration from starving the whole system
▶ interactive: backoff-strategy comparison under simulated outage
MODULE 04

Queueing Theory for Job Systems

Week 4

Will your workflow queue keep up at 10x lead volume, or fall over? This module introduces the M/M/1 queue model and Little's Law, giving you the actual math to answer that question before it happens to a client in production.

You will be able to
  • Apply Little's Law to relate arrival rate, service rate, and queue length
  • Compute utilization and expected wait time for a single-server job queue
  • Recognize when a system is approaching the utilization cliff where wait times explode
▶ interactive: live queue simulator, adjustable arrival/service rate
MODULE 05

Authentication & Secure Integration

Week 5

OAuth2 is not one protocol, it is a family of flows for different trust models, and most integration bugs come from choosing the wrong one. This module covers the authorization-code and client-credentials flows in full, JWT structure and verification, and HMAC request signing for webhook authenticity.

You will be able to
  • Choose the correct OAuth2 flow for a given integration (user-delegated vs. service-to-service)
  • Decode and verify a JWT's signature manually, understanding what each claim protects against
  • Implement and verify HMAC-signed webhook payloads, and explain the timing-attack risk in naive comparison
▶ interactive: JWT decoder/verifier, HMAC signature workbench
MODULE 06

API Contract Design

Week 6

A workflow is only as reliable as the contracts between its steps. This module covers idempotent HTTP method semantics, webhook delivery guarantees, and schema versioning strategy so an upstream change doesn't silently break every client running your system.

You will be able to
  • Design REST endpoints whose idempotency matches their HTTP method semantics
  • Specify a webhook contract with delivery, ordering, and replay guarantees stated explicitly
  • Version an API schema without breaking existing integrations
▶ interactive: contract-breaking-change detector
MODULE 07

Observability & SLOs

Week 7

You cannot fix what you cannot see, and you cannot promise a client reliability you haven't defined numerically. This module covers SLIs, SLOs, and error budgets as a rigorous framework, plus structured logging and distributed tracing basics for diagnosing a failure across a multi-step pipeline.

You will be able to
  • Define an SLI/SLO/error-budget triplet for a real client system and justify the numbers
  • Design structured log events that make a specific failure diagnosable in under five minutes
  • Trace a single business event across every step of a multi-stage pipeline
▶ interactive: trace-the-failure diagnostic exercise
MODULE 08

Capstone: A Fault-Tolerant Lead Pipeline

Week 8

Synthesis. You are given a client brief: a lead-capture-to-CRM pipeline that must survive a flaky downstream API, duplicate webhook deliveries, and a traffic spike. You submit a formal design (DAG or state machine), an idempotency and retry strategy, and an SLO definition, graded against a rubric, not vibes.

Deliverable
  • A written design specification applying every prior module
  • A working implementation of the critical path (idempotent ingestion + retry + dead-letter handling)
  • A one-page SLO document you could hand directly to a client
