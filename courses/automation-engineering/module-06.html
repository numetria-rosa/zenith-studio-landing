Module 06

API Contract Design

A workflow is only as reliable as the contracts between its steps. This module covers idempotent HTTP method semantics, webhook delivery guarantees, and schema versioning strategy so an upstream change doesn't silently break every client running your system.

Learning objectives
  • Design REST endpoints whose idempotency matches their HTTP method semantics
  • Specify a webhook contract with delivery, ordering, and replay guarantees stated explicitly
  • Version an API schema without breaking existing integrations
Before you start

What this module assumes

This module is where Modules 2 and 5 combine into a design discipline. Module 2 gave you idempotency, Module 5 gave you webhook authenticity. This module asks: how do you write those guarantees down as an explicit contract, and how do you change an API later without silently breaking everyone already depending on it?

1

What a contract actually is

An API contract is every promise a consumer can reasonably rely on: the shape of a request, the shape of a response, what happens if you call something twice, whether an event will arrive more than once, in what order, and whether it can be resent later. Most of that is never written down explicitly, it's just however the API happens to behave today. That's the problem this module addresses: undocumented behavior that consumers depend on anyway is still part of the contract, whether you intended it to be or not.

Definition: breaking change

Any change to an API that causes a client which was working correctly against the previous version to stop working correctly, without that client changing anything. Note this is defined from the consumer's perspective, not the provider's, a change the provider considers a minor cleanup can still be breaking if any real consumer depended on the old behavior.

Why this matters for automation specifically: a workflow automation is exactly the kind of consumer most likely to break silently. It has no human watching a UI notice something looks wrong, it just keeps calling the API the same way it always has, and either gets errors it doesn't know how to handle or, worse, gets a response it misinterprets without erroring at all.
Practice check

A provider removes a field from an API response that they consider "internal debug data nobody should be using." Is this necessarily safe to remove without a version bump? Why or why not, based on the definition above?

Check your answer
Not necessarily. The definition of breaking change is about what consumers actually depend on, not what the provider intended for them to depend on. If even one real integration happens to read that "internal" field, removing it is a breaking change for that consumer, regardless of the provider's intent. The only way to know for sure is usage data or an explicit deprecation period, intent alone doesn't make a removal safe.

HTTP method semantics: safe vs. idempotent

Module 2 defined idempotency in general. HTTP methods have a second, related but distinct property worth separating out clearly.

Definition: safe method

A method that causes no side effects at all, it only retrieves data. A safe method can be called any number of times, including zero, with no effect on server state whatsoever.

Definition: idempotent method

From Module 1: repeating it produces the same end state as doing it once. Every safe method is automatically idempotent (no side effects to accumulate), but not every idempotent method is safe, DELETE has a real side effect (something gets deleted) yet is still idempotent (deleting an already-deleted resource leaves the same end state).

PATCH is the trap: whether PATCH is idempotent depends entirely on what the patch document says. PATCH {"status": "active"} (set a value) is idempotent, running it five times leaves the same end state. PATCH {"op": "increment", "field": "credits"} (a relative change) is not, running it five times adds five times as much. The HTTP spec doesn't save you here, the endpoint's own design does.
Practice check

Is every safe method idempotent? Is every idempotent method safe? Give the reasoning, not just yes/no.

Check your answer
Every safe method is idempotent: with zero side effects, there's nothing to accumulate no matter how many times you call it, so the end state is trivially the same every time. But not every idempotent method is safe: DELETE changes server state (a real side effect) yet is still idempotent, because that one side effect, once applied, doesn't compound on repetition. Safety is the stronger property; idempotency is the weaker, more general one.

Run both PATCH variants. Both are "PATCH," the same HTTP method, same idempotency guarantee on paper. Do they behave the same after two calls?

Specifying a webhook contract

A webhook contract needs to state three things explicitly, because a consumer that assumes the wrong default for any of them will eventually break, usually silently.

Delivery guarantee

State it plainly: at-least-once (the honest default per Module 2's proof that exactly-once transport is impossible), or best-effort (may be silently dropped). If you say "at-least-once," every consumer must be built idempotently, exactly the Module 2 lesson, applied here as a contract obligation rather than a suggestion.

Ordering guarantee

Webhooks sent over independent HTTP requests can arrive out of order, a retry of an earlier event can land after a later event that succeeded on the first try. If you don't guarantee order, say so, and consumers must include a sequence number or timestamp in the payload and use it to detect and discard stale updates, rather than trusting arrival order.

Replay policy

Many providers let a customer manually replay old webhook events (for recovery after an outage). If replay is supported, state how far back, and remind consumers, again, this is why idempotent handling isn't optional: a replayed event from three days ago must be as safe to process as a live one.

A concrete contract statement, the kind worth actually writing down: "Events are delivered at-least-once. Ordering between events for the same resource is not guaranteed; consumers must use the sequence field to detect stale updates. Events can be replayed by the customer for up to 7 days after original delivery; consumers must handle replayed events idempotently using the event_id field." That's short, explicit, and tells every consumer exactly what defensive code they need to write.
Practice check

A consumer's webhook handler updates a "lead score" field directly from whatever value is in the incoming event, with no check against what it already has stored. Given the ordering guarantee above, what can go wrong?

Check your answer
A retried, earlier event can arrive after a later event that already succeeded, overwriting the correct, newer score with a stale, older one. Since ordering isn't guaranteed, "whatever arrived most recently" is not the same as "whatever happened most recently." The fix is exactly what the contract statement recommends: check the event's sequence number against what's already stored, and discard the update if it's older than what's already applied.

Run "Making a required request field optional" (relax). The detector should mark it non-breaking. Why does loosening a constraint never break existing clients, while tightening one (the scenario above it) does?

Check your answer
Every existing client was already satisfying the old, stricter requirement (they were sending the field, since it was required), so they automatically satisfy the new, looser requirement too, nothing they were already doing stops working. Tightening does the opposite: clients that were valid under the old, looser rule (not sending an optional field) are now invalid under the new, stricter rule. Relaxing a constraint can only ever keep old behavior valid or make more things valid, never less.
6

Versioning without breaking anyone

The detector in Section 5 runs on a simple, defensible rule set worth stating explicitly, since it's the actual test to run mentally before shipping any API change.

The compatibility rules

Safe (non-breaking): adding an optional field (request or response), relaxing a required field to optional, adding a new endpoint entirely.

Breaking: removing any field, renaming a field (equivalent to remove + add), changing a field's type, tightening an optional field to required, changing a field's meaning without changing its name or type.

Versioning strategy, in order of preference: (1) prefer additive-only changes within the same version whenever possible, new optional fields cost nothing and break nothing. (2) When a breaking change is unavoidable, introduce it behind a new version (URL path /v2/, or a version header) while keeping the old version fully functional. (3) Deprecate the old version with a stated sunset date, giving consumers a real window to migrate, rather than breaking them with no notice. Removing a field "after deprecation," as in the last scenario in Section 5, is still technically a breaking change by the rules, deprecation doesn't make it non-breaking, it makes the breakage planned and communicated instead of silent.
Practice check

A team wants to change a response field's type from a string date ("2026-01-15") to a Unix timestamp integer, to make it easier to work with. Using the rules above, is this safe to ship as an in-place change? What's the non-breaking way to make this improvement available?

Check your answer
Not safe in place, changing a field's type is on the breaking list, every consumer currently parsing a string date will fail or silently misbehave when it suddenly receives an integer. The non-breaking approach: add a NEW field (e.g., a separate timestamp field) alongside the existing string field, which is purely additive, then deprecate the old string field on its own timeline once consumers have had a chance to migrate to the new one.

Before the checkpoint: what you should now be able to do

A short consolidation before you're graded on it.

  • Classify any HTTP method as safe, idempotent, both, or neither, and explain why PATCH requires special care.
  • Write an explicit webhook contract statement covering delivery, ordering, and replay.
  • Explain why an unordered, at-least-once, replayable webhook stream requires idempotent, sequence-aware consumers.
  • Classify a schema change as breaking or non-breaking using the compatibility rules, and justify it from the consumer's perspective.
  • Describe the non-breaking path for shipping a change that would otherwise be breaking.
Cross-module check

Suppose a future API version wants to change how idempotency keys work, from a client-supplied header to a server-generated key. Using this module's compatibility rules, is that a safe in-place change, or does it need a new version?

Check your answer
It needs a new version. Existing clients built their whole idempotent-retry strategy (Module 2) around supplying their own key and expecting the server to honor it, silently switching to a server-generated key changes the meaning of that field without changing its name, which is exactly the "breaking" case from Section 6, even though no field was removed or renamed. This is a good example of why the compatibility rules need to be applied to BEHAVIOR, not just to field names and types, a contract can break by changing what a field means while it keeps looking identical on paper.

Further reading

If you want to go deeper than the browser can take you:

  • RFC 7231, "HTTP/1.1 Semantics and Content," Section 4.2, the specification defining safe and idempotent methods.
  • RFC 5789, "PATCH Method for HTTP," which explicitly does not guarantee PATCH idempotency, the source of Section 2's warning.
  • Stripe's API versioning documentation, a widely-cited real-world example of header-based versioning with a long deprecation runway.
  • In production, this shows up as OpenAPI/JSON Schema diff tools used in CI pipelines to catch breaking changes before they ship, exactly the algorithm Section 5's detector runs by hand.

Glossary

API contract — every promise a consumer can reasonably rely on, documented or not.
breaking change — any change that stops a previously-working, unmodified client from working correctly.
safe method — an HTTP method with no side effects at all.
idempotent method — repeating it leaves the same end state as doing it once; weaker than safety.
webhook contract — explicit statement of a webhook's delivery, ordering, and replay guarantees.
additive-only change — a schema change that only adds optional fields or relaxes constraints; always non-breaking.
deprecation / sunset date — a communicated, scheduled breaking change, versus an unannounced one.
