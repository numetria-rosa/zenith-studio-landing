Module 02

Idempotency & Exactly-Once Semantics

Networks fail mid-request. Clients retry. Without idempotency, a retried "charge the card" becomes two charges. This module derives idempotency-key design from first principles and distinguishes at-most-once, at-least-once, and exactly-once delivery, and why the third one is usually a lie your tooling tells you.

Learning objectives
  • Design an idempotency-key scheme that survives concurrent duplicate requests
  • Explain why "exactly-once" is achieved via at-least-once delivery plus idempotent handling, not a magic transport guarantee
  • Identify non-idempotent operations in an existing workflow and fix them
Before you start

What this module assumes

Module 1 gave you the DAG and the FSM, the two shapes workflows come in. This module assumes you're comfortable with both, because the bug this module is about hides inside individual steps of a DAG or individual transitions of an FSM: a step that looks correct in isolation but silently breaks when the network does something a demo environment never does, delivers the same request twice.

What this module does

It answers one question in full rigor: when a client doesn't get a response, was the request never processed, or was it processed and only the response lost? The client cannot tell the difference. That single fact is the root of almost every duplicate-charge, duplicate-email, duplicate-order bug you will ever debug in production automation. This module derives, from that fact, why retries are unavoidable, why "exactly-once" as a network guarantee is impossible, and what you build instead.

What's assumed

No networking background required. "Request," "response," and "timeout" are used in their everyday sense and nothing more technical is assumed.

1

The problem retries create

A client sends a request: "charge this card $50." The server receives it, charges the card, and sends back a response: "done." But the response is lost, a dropped packet, a proxy timeout, a server restart mid-response, doesn't matter which. The client, having sent a request and received nothing back, has exactly one fact available to it: no response arrived. It does not know whether the server never received the request, or received it, processed it, and only the acknowledgment was lost.

Those two situations look identical from the client's side. And a client that wants to be reliable has to do something about a request that appears to have failed, the only reasonable option is to retry. So it does: it sends "charge this card $50" again. If the first charge actually went through, the card is now charged twice, for one purchase.

Definition: idempotent operation

An operation f is idempotent if applying it more than once produces the same effect as applying it exactly once: f(f(x)) = f(x). "Set the account balance to $500" is idempotent, running it five times leaves the balance at $500. "Add $500 to the account balance" is not, running it five times adds $2,500.

Idempotency doesn't stop the duplicate request from arriving, nothing can, as Section 3 proves. What it does is make the duplicate harmless: if "charge the card" is handled idempotently, the second, retried request either does nothing or safely returns the same result as the first, instead of charging the card again.

Practice check

Without looking back: what two facts are indistinguishable to a client that sent a request and received no response? And why does that ambiguity force the client toward retrying rather than giving up?

Check your answer
The client can't tell whether the request was never received, or was received and processed but the response was lost. If it assumes "never received" and does nothing, it risks silently dropping a request that actually succeeded on the surface but that the client never confirmed, and it risks a request that genuinely failed being lost forever with no retry. Since giving up risks silently losing real work, a client that cares about reliability has to retry, which is exactly what creates the duplicate-request problem this module is about.

Nothing about the network changed, the response is still lost and the client still retries, that part is unavoidable (see Section 3). 3

Why "exactly-once" delivery is impossible

It's tempting to think a good enough network protocol could just solve this: have the server wait for the client to confirm receipt of the response, and not consider the request complete until then. But watch what happens to that confirmation.

Claim: no protocol over an unreliable network can guarantee a message is delivered exactly once

Proof sketch (this is the classical Two Generals Problem, Akkoyunlu, Ekanadham & Huber, 1975).

  1. Suppose client C sends request R to server S. S processes R and sends acknowledgment A back to C.
  2. The network can drop any message, including A. If A is dropped, C is in exactly the same state as if R itself had been dropped: no response arrived.
  3. Suppose C, to be sure S got the acknowledgment that C got A, sends a confirmation back to S. That confirmation can also be dropped, and now S doesn't know whether C received A.
  4. This chain has no end. Whatever the last message in any proposed protocol is, it can be dropped, and its sender can never have proof it arrived. There is no finite exchange of messages that gives both sides simultaneous certainty.
  5. Therefore, C can never be certain whether R was processed exactly once, zero times, or more than once, using network information alone. C's only defensible choice under uncertainty is to retry, which means duplicate delivery is always possible. ∎

This isn't a limitation of current technology, it's a property of any communication over a channel that can lose messages, TCP included. TCP guarantees your bytes arrive in order within one connection; it says nothing about whether the application on the other end had already processed your logical request from a connection that TCP itself gave up on.

Formal definitions: delivery guarantees

At-most-once: for a given logical message, the number of times it is processed is 0 or 1, it is never duplicated, but it may be silently lost.

At-least-once: the number of times it is processed is 1 or more, it is never silently lost, but it may be duplicated.

Exactly-once (as a transport guarantee): the number of times it is processed is exactly 1. The proof above shows this cannot be achieved by the transport alone.

Effectively-once (what you actually build): at-least-once delivery, combined with an idempotent handler, so that even though the message may arrive more than once, its effect happens exactly once. This is what every system that advertises "exactly-once" is actually doing.

Why this matters: if a vendor's documentation says their queue provides "exactly-once delivery," read that as a claim about their idempotency handling, not their network. The proof above applies to them too. The honest version of that claim is "at-least-once delivery, with deduplication we've already done for you." That's still valuable, it means you don't have to build the dedup yourself, but it's a different claim than the marketing copy, and knowing the difference is what lets you ask the right question when it doesn't seem to be working: "what's the dedup window?"
Practice check

A payment provider's docs say their webhook system delivers "exactly once." Based on the proof above, what is almost certainly actually true, and what's the one follow-up question worth asking their support team?

Check your answer
Almost certainly true: they deliver at-least-once and deduplicate on their end using some kind of event ID, so you experience it as exactly-once. The proof means they cannot literally guarantee single delivery over the network, so "exactly once" is describing the net effect after their deduplication layer, not the transport. Worth asking: what's the deduplication window, and is the event ID they dedupe on stable and available to you, so you can also dedupe defensively on your side in case their window is shorter than you assumed.
4

Idempotency keys, and the race condition that breaks naive ones

The standard fix is an idempotency key: the client generates a unique identifier for a logical operation (not per network attempt, per operation, "charge this specific cart," not "this specific HTTP call") and sends it with every attempt, including retries. The server stores results keyed by that identifier. On any request carrying a key it's seen before, it skips the operation and returns the stored result.

Definition: idempotency key

A client-generated identifier, unique per logical operation, attached to every request (and every retry) representing that operation. It lets the server distinguish "this is a retry of something I already handled" from "this is a genuinely new request."

That sounds like it fully solves the problem. It doesn't, not in the naive implementation, because the check and the write are two separate steps:

The naive (broken) version: 1. SELECT WHERE key = ? — if a row exists, return its stored result. 2. Otherwise, process the operation and INSERT a row with this key and its result. This works perfectly for sequential retries. It fails for concurrent duplicate requests, two attempts arriving close enough together that both run step 1 before either has finished step 2. Both find nothing, both conclude "this is new," both proceed, both charge the card.
Claim: check-then-insert is not safe under concurrent execution; an atomic unique constraint is

Counterexample trace for check-then-insert. Two requests, A and B, both carrying key K, arrive close together:

  1. A: SELECT WHERE key = K → no rows.
  2. B: SELECT WHERE key = K → no rows (A hasn't inserted yet).
  3. A: processes the charge, INSERT key = K.
  4. B: processes the charge (it already decided this was new), INSERT key = K.
  5. Result: two charges, despite an idempotency key being present and checked correctly on both requests. The bug isn't a missing check, it's the gap between checking and writing.

Why a unique constraint closes the gap. A database-enforced UNIQUE constraint on the key column makes the insert itself the check, there is no separate read step to race against. If A's insert lands first, the column now holds K. B's insert, attempting to write the same K, is rejected by the database as a constraint violation, atomically, as part of the single insert operation, not as a separate step B could race around. B's handler catches that specific error and returns A's stored result instead of treating it as a real failure. ∎

Practice check

Why does adding a unique constraint fix the race, when the idempotency key check was already present in the broken version too?

Check your answer
The key wasn't the missing piece, atomicity was. In the broken version, "check" and "write" are two separate operations with a gap between them where another request can slip through. A unique constraint collapses check-and-write into one atomic operation performed by the database, there is no window during which two requests can both believe they're first, because only one insert can ever actually succeed for a given key. The fix isn't "add a key," it's "make the key's enforcement atomic."

Run the race simulation in naive mode several times in a row. Does the outcome vary, or does it reliably double-charge every single time these two requests genuinely overlap? What does that imply about why this bug survives testing?

Check your answer
It reliably double-charges every time, once two requests are genuinely concurrent, both starting their check before either finishes its write, the bad interleaving isn't a coin flip, it's guaranteed by the timing. What actually varies in a real system isn't whether the bug fires when two requests truly overlap, it's how often true millisecond-level overlap happens at all. Most manual testing never produces that, you click a button once, wait, look at the result, so the code can pass a hundred manual tests and still fail the first time a real retry happens to fire while the original request is still mid-flight. The bug was never probabilistic, your testing process was just never fast enough to trigger it.

Implement it: an idempotent request handler

You've watched the race condition happen and watched it get fixed. Now you write the fix yourself, and five real tests run against your actual code, including the exact concurrent-duplicate race from Section 5.

Code exercise · runs in your browser

Complete processRequest(request, store). request is { key, payload }. store gives you: store.insertKey(key) (atomic, returns {inserted:true} the first time a key is used, or {inserted:false, cached} after), store.releaseKey(key) (call this if processing fails, so a retry can actually try again instead of being stuck), store.setResult(key, result) (store the result once processing succeeds), and await store.process(payload) (does the actual work, may throw).

Stuck? Hints
Hint 1 — conceptual
Think about the lifecycle in three parts: reserve the key, do the work, record the result. Which of those three steps has to happen atomically before you touch anything else, and what should happen to the reservation if the work itself fails partway through?
Hint 2 — specific
Call store.insertKey(key) first, always, before doing any work. If inserted comes back false, someone already owns this key, in that case you return the cached result and stop, you never call store.process again.
Hint 3 — near-solution
Once insertKey confirms you own the key, wrap await store.process(payload) in a try/catch. On success, call store.setResult(key, result) and return the result. On failure, call store.releaseKey(key) before re-throwing, otherwise the key stays permanently reserved and a legitimate retry can never actually try again.
Solution — run your code at least once first
async function processRequest(request, store) {
  const { key, payload } = request;
  const { inserted, cached } = store.insertKey(key);
  if (!inserted) return cached;
  try {
    const result = await store.process(payload);
    store.setResult(key, result);
    return result;
  } catch (err) {
    store.releaseKey(key);
    throw err;
  }
}
Practice check

Test 5 checks that a failed request can be successfully retried with the same key. If you forget to call store.releaseKey(key) in your catch block, what specifically will Test 5 observe go wrong?

Check your answer
The retry will come back with undefined instead of actually reprocessing, because the key is still marked as "reserved" from the failed attempt (insertKey sees it already exists and returns the cached, empty result rather than allowing a fresh attempt). The failure is permanent even though the underlying cause might have been transient. This is exactly why the naive check-then-insert story from Section 4 isn't the only place atomicity-adjacent bugs hide, forgetting to release a reservation on failure is a different bug with the same flavor: state that should be temporary becomes permanent by accident.

Which operations need this, and which don't

Not every operation needs idempotency-key machinery, some are already naturally idempotent, and forcing keys onto them is wasted complexity. The useful skill is fast classification.

Reference: HTTP method idempotency

GET, PUT, and DELETE are defined by the HTTP specification to be idempotent: PUT /user/5 {email: "a@b.com"} run five times leaves the same end state as running it once, it sets a value. DELETE /order/9 run five times leaves order 9 deleted, same as once. POST and PATCH are not guaranteed idempotent by spec, POST /charges conventionally creates a new resource each time, which is exactly the double-charge failure mode. This is precisely why idempotency keys are a standard, explicit feature on payment-provider POST endpoints, the spec's default behavior is the dangerous one.

Quick test: ask "if I run this exact operation twice in a row with no other changes to the system, is the end state different from running it once?" Setting a value, deleting a specific record, or upserting by a stable key all pass. Incrementing a counter, appending to a log, sending an email, or creating a new row with no uniqueness constraint all fail, those need either a redesign (e.g., "set counter to N" instead of "increment") or an idempotency key.
Practice check

A workflow step does INSERT INTO notifications_sent (lead_id, channel) every time a follow-up email is sent, with no uniqueness constraint on (lead_id, channel). Is this operation idempotent? If a retry hits it, what happens, and what's the one-line fix?

Check your answer
Not idempotent, a retry inserts a second row and, if this table drives whether an email actually gets sent, a second email. The one-line fix: add a unique constraint on (lead_id, channel) and use an upsert (insert-or-do-nothing-on-conflict) instead of a plain insert, exactly the pattern from Section 4, turning the check-then-act race into a single atomic operation the database enforces.

Question 5 of 5 · design (self-check, not auto-graded)
A new scenario, distinct from anything else in this module: a payment request is sent to your POST /orders endpoint. The network times out before the client sees a response. The client retries. Your server may or may not have already fully processed the original payment when the retry arrives, possibly even at the exact same instant. Design a complete scheme by specifying all six of the following: (1) the idempotency key, what it's derived from and who generates it; (2) the storage strategy, where and how the key and its result are persisted; (3) the request lifecycle, the order of operations from request received to response sent; (4) duplicate handling, what happens on a sequential retry; (5) concurrency behavior, what happens if two copies of the same request arrive at nearly the same instant; (6) response behavior, exactly what the losing request gets back. Write your answer before revealing the model answer.
▸ Compare against a model answer
A complete answer, one dimension at a time: (1) Idempotency key, the client generates a UUID per checkout attempt (not per HTTP call, so a retry reuses the same key) and sends it as an Idempotency-Key header. (2) Storage strategy, an idempotency_keys table with a UNIQUE constraint on the key column, storing the key, the resulting order ID, and the response payload to return on replay. (3) Request lifecycle, attempt INSERT ... ON CONFLICT DO NOTHING on the key as the very first action, before touching payment logic at all; only on insert success does the handler proceed to actually charge and create the order. (4) Duplicate handling, a sequential retry's insert fails the constraint, the handler looks up the existing row and returns the stored result, no reprocessing. (5) Concurrency behavior, two simultaneous copies both attempt the insert, the database's constraint enforcement (not application code) guarantees only one can succeed, exactly the atomic mechanism from Section 4, the other's insert fails immediately and it falls into the same duplicate-handling path as a sequential retry. (6) Response behavior, the losing request gets back a 200 with the original order ID and payment result, not an error, since from the client's perspective this is the same logical request succeeding once, not failing twice.

Glossary

idempotent operation — f(f(x)) = f(x); repeating it changes nothing further.
idempotency key — a client-generated identifier, stable across retries, that lets a server recognize a duplicate of an operation it already handled.
at-most-once — processed 0 or 1 times; never duplicated, may be lost.
at-least-once — processed 1 or more times; never lost, may be duplicated.
effectively-once — at-least-once delivery combined with idempotent handling, so the observable effect happens exactly once even though delivery may not.
Two Generals Problem — the classical proof that no finite message exchange over an unreliable channel gives both parties simultaneous certainty of receipt.
race condition — a bug where the outcome depends on the relative timing of concurrent operations; here, the gap between checking and writing.
unique constraint — a database-enforced rule that makes a column's insert-or-reject decision atomic, closing the check-then-insert race.
