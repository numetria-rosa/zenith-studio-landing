Module 05

Authentication & Secure Integration

OAuth2 is not one protocol, it is a family of flows for different trust models, and most integration bugs come from choosing the wrong one. This module covers the authorization-code and client-credentials flows in full, JWT structure and verification, and HMAC request signing for webhook authenticity.

Learning objectives
  • Choose the correct OAuth2 flow for a given integration (user-delegated vs. service-to-service)
  • Decode and verify a JWT's signature manually, understanding what each claim protects against
  • Implement and verify HMAC-signed webhook payloads, and explain the timing-attack risk in naive comparison
Before you start

What this module assumes

Modules 1–4 covered how workflows behave, correctly, resiliently, and at scale. This module asks a question those don't touch at all: who is allowed to trigger any of it, and how do you prove a request is genuinely from who it claims to be? Get this wrong and the rest of the course doesn't matter, an attacker who can forge requests doesn't need your queue to be well-behaved.

What's new

Both interactives in this module run real cryptography in your browser, using the Web Crypto API, not a simulation dressed up to look like one. When you verify a JWT signature or compute an HMAC, that's an actual SHA-256 computation happening locally, the same primitive production systems use.

What's assumed

Modules 1–4 completed. No prior cryptography background, HMAC and signatures are defined from scratch.
Comfort with the idea of a "secret" shared between two parties and nothing more advanced than that.

1

OAuth2 is a family, not a protocol

"We use OAuth2" doesn't fully specify how an integration authenticates, any more than "we use HTTP" specifies what a website does. OAuth2 defines several distinct grant types (flows), each suited to a different trust model. Picking the wrong one is the single most common integration security bug, not because the wrong flow is insecure in the abstract, but because it's insecure for the situation it's used in.

The one question that determines the flow

Is there a human user, present in the moment, delegating access to their own account or data? If yes, you need a flow that involves that human authenticating and consenting, the authorization code flow. If the integration is purely service-to-service, your backend calling a partner's API with no user in the loop, you need the client credentials flow. Using client credentials when a human should be consenting means your system can silently act as any user without their knowledge. Using authorization code for a pure service integration means building unnecessary user-facing consent screens for something that isn't the user's action at all.

Practice check

A workflow automation needs to read a specific customer's calendar to schedule a meeting, with that customer's explicit permission granted once during setup. Which trust model does this fit: user-delegated, or service-to-service?

Check your answer
User-delegated. The calendar belongs to a specific human, and access is only legitimate because that human consented to it. Even though the actual meeting-scheduling call later happens automatically with no human present in the moment, the authorization itself was delegated by a real user, so it needs the authorization code flow, most likely with a stored refresh token for the ongoing automated calls after the initial consent.
2

Authorization code flow (user-delegated)

This is the flow behind every "Sign in with Google" or "Connect your CRM" button. Its defining feature is an indirection step, a short-lived code, that exists specifically so the long-lived access token never has to pass through the user's browser.

1
The client redirects the user's browser to the authorization server's login page, with the client's identity and requested scopes in the URL.
2
The user authenticates with the authorization server directly (the client never sees their password) and approves the requested access.
3
The authorization server redirects back to the client with a short-lived, single-use authorization code in the URL.
4
The client's backend (not the browser) exchanges that code, plus its own client secret, for an access token, this exchange happens server-to-server, never exposed to the browser.
5
The client uses the access token to call the resource server (the actual API) on the user's behalf.
Why the code exists at all, instead of returning the token directly at step 3

Step 3's redirect happens through the user's browser, browser history, referrer headers, and server logs can all potentially expose whatever's in that URL. A short-lived, single-use code minimizes the damage if it leaks, it can only be exchanged once, and only by a client that also knows the client secret, which never travels through the browser at all. If the actual access token were put in that URL instead, anyone who captured it could use it directly, for as long as it remained valid.

PKCE (Proof Key for Code Exchange): for clients that can't safely hold a secret, mobile apps, single-page apps, the client secret in step 4 isn't available. PKCE replaces it: the client generates a random secret locally before step 1, sends a hash of it, then presents the original secret at step 4. Even if the authorization code is intercepted, an attacker without that original locally-generated secret can't complete the exchange.
Practice check

Why is exchanging the authorization code for an access token done from the client's backend rather than directly from the user's browser via JavaScript?

Check your answer
Because that exchange requires the client secret, and a client secret embedded in browser-side JavaScript isn't secret at all, anyone can view it. Keeping the exchange server-side means the one piece of information that proves "I am the legitimate client, not an impersonator" never leaves a system the client actually controls.
3

Client credentials flow (service-to-service)

When there's no user to delegate anything, a backend job that syncs data with a partner API on a schedule, the flow collapses to something much simpler: the client authenticates directly with its own credentials and gets a token back.

1
The client sends its client ID and client secret directly to the authorization server's token endpoint, no redirect, no browser, no user involved.
2
The authorization server validates the credentials and returns an access token scoped to the client itself, not to any user.
3
The client uses the token to call the resource server, acting as itself, with whatever permissions its own account was granted.
The security implication of skipping steps, not adding them: client credentials is simpler precisely because there's no user consent to obtain, which is exactly why it's wrong to use it as a shortcut around building proper user consent when a real user's data is actually at stake. The flow being easier to implement is not a reason to use it for something that needs delegation.
Practice check

A nightly job pulls aggregate, non-user-specific analytics from a partner platform using the automation agency's own registered API account. Which flow, and why?

Check your answer
Client credentials. There's no user delegating anything, the agency's own account is what's authorized, and the call happens on a schedule with no human present. Building an authorization-code consent flow here would be solving a problem that doesn't exist, there's no user whose permission is being represented.
4

JWT structure and what each claim protects against

Access tokens from either flow are often issued as a JWT (JSON Web Token), a compact, self-contained format that lets a resource server verify a token's authenticity without calling back to the authorization server for every request.

Structure: header.payload.signature

Three base64url-encoded segments joined by dots. The header states the algorithm used (e.g., HS256). The payload holds claims, statements about the token, like who it's for and when it expires. The signature is a cryptographic proof, computed over the header and payload, that only someone holding the signing secret could have produced.

What the standard claims protect against

exp (expiration): without it, a stolen token would be valid forever. Short expiration limits the damage window of a leaked token.

aud (audience): without it, a token legitimately issued for Service A could be replayed against Service B, if B doesn't check that the token was actually meant for it, it might accept it anyway.

iss (issuer): without it, or without verifying it, a resource server has no way to confirm the token came from an authorization server it actually trusts.

The single most important fact about JWTs: the payload is encoded, not encrypted. Base64url is not a secret transformation, anyone can decode a JWT's header and payload with no key at all. The signature proves the claims weren't tampered with after issuance, it does nothing to keep them confidential. Never put a secret value in a JWT payload expecting it to stay hidden.
Practice check

A developer puts a user's raw password hash in a JWT payload, reasoning "it's signed, so it's secure." What's wrong with that reasoning?

Check your answer
Signing provides integrity (proof it wasn't altered), not confidentiality (proof it can't be read). Anyone who intercepts the token, or anyone the token is ever shown to, can base64url-decode the payload and read the password hash directly, no key required. "Signed" and "secret" are unrelated properties, and this is exactly the mistake the callout above warns about.

Practice check

Decode the token, verify it (should succeed), then click "Tamper with payload" and verify again. The header and most of the payload look completely normal both times, so what specifically causes verification to fail after tampering?

Check your answer
The signature was computed over the ORIGINAL header and payload bytes. Tampering changes the payload's bytes but the signature attached to the token is still the old one, computed for the old content. Verification recomputes what the signature should be for the current content and compares it to the attached signature, since the content changed but the signature didn't, they no longer match. This is the entire point of a signature: it's not that tampering is prevented, it's that tampering is detected.
6

HMAC-signed webhooks

A webhook is a request from someone else's server to yours, an inbound flow, not one you control end to end the way an outbound API call is. Anyone who knows or guesses your webhook URL can send you a POST request that looks exactly like a real event. HMAC signing solves this: it proves a payload really came from the party who holds the shared secret, and wasn't altered in transit.

Definition: HMAC (Hash-based Message Authentication Code)

A cryptographic function that takes a secret key and a message, and produces a fixed-length signature. The sender computes HMAC(secret, payload) and includes it as a header. The receiver, who also holds the secret, recomputes the same HMAC over the payload it received and checks whether the two match. Changing even one byte of the payload produces a completely different signature, there's no way to predict how a change will affect it without knowing the secret.

Practice check

Compute the signature, note it down, then flip one byte and compute again. How different is the new signature from the old one, roughly half the characters changed, or nearly all of them? What property of HMAC does that demonstrate?

Check your answer
Nearly all of them change, a single-bit difference in the input typically flips roughly half the output bits, which at the character level looks like an almost entirely different string. This is the avalanche effect: a secure hash function is designed so that small input changes cause large, unpredictable output changes, which is exactly why a receiver can trust that a matching signature means the payload truly wasn't altered, even by one byte.
7

The timing-attack risk in naive comparison

Computing the HMAC correctly isn't the whole job, comparing it to the received signature safely matters just as much. The obvious way to compare two strings, signature === received in most languages, is a security bug when either value is secret-derived.

Claim: naive equality comparison leaks information via timing

Argument. A standard string-equality check compares characters left to right and returns false the instant it finds a mismatch, it does not keep checking the rest of the string. That means a comparison against a signature that's correct for the first 3 characters takes measurably longer than one that's wrong at character 1, because the correct-prefix case does more work before bailing out. An attacker who can send many forged signatures and precisely measure response time can, in principle, guess the signature one byte at a time: try all 256 possibilities for byte 1, keep whichever took longest, move to byte 2, repeat. This turns a brute-force problem that's computationally infeasible (guessing a whole 32-byte signature at once) into a linear one (guessing 32 bytes one at a time), each with only 256 possibilities.

The fix: a constant-time comparison function, one that always compares every byte regardless of where the first mismatch occurs, so the time taken reveals nothing about how many bytes matched. Every mainstream language's crypto library provides one (e.g., crypto.timingSafeEqual in Node.js, hmac.compare_digest in Python). The fix is one function call, the vulnerability is invisible until someone specifically looks for it, which is exactly why it's worth knowing to look.
Honesty about this demo: a real timing attack requires statistical measurement over many requests to filter out network jitter and noise, it is not something you can reliably observe from a single comparison in a browser tab, and browsers deliberately reduce JavaScript timer precision for exactly this security reason. The interactive above uses ordinary comparison for simplicity since nothing secret is actually at stake in a learning demo. The vulnerability described here is real and well-documented in production systems, verifying it live isn't something this page can responsibly claim to do.
Practice check

Why does a constant-time comparison function need to check every byte even after it's already found a mismatch, isn't that wasted work?

Check your answer
It's wasted computation but necessary security, the entire vulnerability comes from the amount of work varying based on secret-dependent information (how many leading bytes matched). A constant-time function deliberately does the "wasteful" full comparison every single time, correct or not, so its execution time carries no signal about the input at all. Trading a small, fixed amount of extra computation for eliminating an information leak is the right tradeoff whenever you're comparing anything secret-derived.

Implement it: write the verification function

Everything so far has been you watching this page compute HMACs and comparisons. This section reverses that: you write the verification logic yourself, and real test cases run against your actual code, not a canned answer.

Code exercise · runs in your browser

Two helpers are already available to your code: await computeHmacHex(secret, message) returns the real HMAC-SHA256 hex digest (Web Crypto, same as Section 6), and constantTimeEqual(hexA, hexB) is a real constant-time comparison (Section 7's fix, already implemented for you). Complete verifyWebhook so it returns true only when receivedSignatureHex is the correct signature for payload under secret.

Stuck? Hints
Hint 1 — conceptual
Verification means: compute what the signature SHOULD be from the payload and secret, then compare that to what was actually sent. Both helper functions you need already exist, you're wiring them together, not implementing crypto yourself.
Hint 2 — specific
Call await computeHmacHex(secret, payload) to get the expected signature. Then compare it to receivedSignatureHex, but not with ===.
Hint 3 — near-solution
Use constantTimeEqual(expectedHex, receivedSignatureHex) for the comparison, that's exactly what it's there for, and return its result directly.
Solution — run your code at least once first
async function verifyWebhook(payload, receivedSignatureHex, secret) {
  const expectedHex = await computeHmacHex(secret, payload);
  return constantTimeEqual(expectedHex, receivedSignatureHex);
}
Practice check

Before running your code: if you wrote return receivedSignatureHex === await computeHmacHex(secret, payload); instead of using constantTimeEqual, would the test suite below catch that mistake?

Check your answer
No, and this is worth sitting with. All four tests only check whether the function returns the *correct boolean*, valid signatures pass, invalid ones fail, both versions produce identical results on every test case here. The timing vulnerability from Section 7 is about how *long* the comparison takes depending on the input, not what it returns, so a correctness-only test suite is structurally blind to it. This is a real limitation of automated testing in general, not just this exercise: passing tests proves the code does the right thing on the cases you thought to test, it doesn't prove the code is secure. That's exactly why Section 7's reasoning, not just a green checkmark, is the part you actually need to retain.

Secure the webhook handler

The code below shipped to production. It looks reasonable at a glance, it even checks the signature. It has three real vulnerabilities. Find and fix all three, then run the tests, each vulnerability has its own test specifically designed to catch it.

Code exercise · runs in your browser

Fix handleWebhookSecure(rawBody, receivedSignatureHex, secret, timestamp, now, seenIds). Available: computeHmacHex, constantTimeEqual. timestamp is the claimed send time (ms), now is the current time (ms), reject anything older than 5 minutes (300000ms). seenIds is a Set you should check and update using the payload's event_id.

Stuck? Hints
Hint 1 — conceptual
There are exactly three separate bugs, matching the three checklist items from Section 5's cheat sheet: something happens in the wrong ORDER, something is compared the wrong WAY, and something isn't checked for FRESHNESS/uniqueness at all. Find each independently, don't assume fixing one fixes another.
Hint 2 — specific
Bug 1: the code reads and acts on fields from the parsed body before the signature has been verified, move verification to the very first thing that happens, before JSON.parse. Bug 2: find the signature comparison and check whether it's using constantTimeEqual or plain ===. Bug 3: nothing currently checks timestamp against now, or checks seenIds for the payload's event_id.
Hint 3 — near-solution
Order your function as: (1) verify the signature over the raw body with constantTimeEqual, reject immediately if it fails, (2) only then attempt JSON.parse(rawBody), inside a try/catch, a malformed body must be rejected gracefully, not thrown, (3) reject if now - timestamp > 300000, (4) reject if seenIds.has(payload.event_id), otherwise add it to seenIds and proceed.
Solution — run your code at least once first
async function handleWebhookSecure(rawBody, receivedSignatureHex, secret, timestamp, now, seenIds) {
  const expectedHex = await computeHmacHex(secret, rawBody);
  if (!constantTimeEqual(expectedHex, receivedSignatureHex)) {
    return { ok: false, reason: "invalid signature" };
  }
  let payload;
  try {
    payload = JSON.parse(rawBody);
  } catch (e) {
    return { ok: false, reason: "malformed payload" };
  }
  if (now - timestamp > 300000) {
    return { ok: false, reason: "stale timestamp" };
  }
  if (seenIds.has(payload.event_id)) {
    return { ok: false, reason: "replay detected" };
  }
  seenIds.add(payload.event_id);
  return { ok: true, payload };
}
Practice check

The starter code calls JSON.parse(rawBody) before checking the signature at all. Even if the signature check afterward is written perfectly, what's already gone wrong by the time it runs?

Check your answer
The parser has already run on completely untrusted, unverified bytes, and whatever the parsed object triggers downstream (logging it, passing fields to other code, even just the parser's own behavior on adversarial input) has already happened before you know whether the sender was legitimate. Verification needs to be the first thing that happens to untrusted input, not a check you run after you've already acted on it. This is the same ordering lesson as the Module 8 capstone's critical path: verify, then parse, then process, never the reverse.

A short consolidation before you're graded on it.

  • Determine whether an integration needs user-delegated (authorization code) or service-to-service (client credentials) authentication, and explain why the wrong choice is a security problem, not just a style choice.
  • Explain why the authorization code flow uses a short-lived code instead of returning the access token directly.
  • Decode a JWT's header and payload without a key, and explain why that's expected behavior, not a bug.
  • Explain what exp, aud, and iss each protect against.
  • Explain how HMAC verification works and why naive string comparison of signatures is a timing-attack vulnerability.
Cross-module check

A webhook arrives with a valid HMAC signature, but it's a genuine duplicate delivery (the platform retried after not getting a fast 200). Does signature verification (this module) do anything to prevent double-processing that duplicate? What module actually handles that?

Check your answer
No, and this is a common confusion. HMAC verification only answers "is this really from who it claims to be," a genuinely duplicate delivery from the real sender has a perfectly valid signature every time, since it's the same authentic payload resent. Preventing double-processing of that valid duplicate is Module 2's job, idempotency keys, not this module's. The two are complementary and both necessary: verify authenticity first (this module), then deduplicate (Module 2), exactly the order used in the Module 8 capstone's critical path.

Question 5 of 5 · design (self-check, not auto-graded)
Design a webhook verification scheme for an endpoint that must resist both payload tampering and replay attacks (an old, legitimately-signed request being resent later by an attacker who captured it). Specify what gets signed, what the receiver checks, and how comparison should be implemented. Write your answer before revealing the model answer.
▸ Compare against a model answer
A reasonable answer: sign the concatenation of a timestamp and the raw request body (not just the body alone), using HMAC-SHA256 with the shared secret, sent as a header alongside the timestamp. The receiver recomputes the HMAC over the received timestamp and body and compares it using a constant-time comparison function (protects against tampering and forgery). Separately, the receiver rejects any request whose timestamp is more than a few minutes old, even if the signature is valid (protects against replay, since a captured old request's signature is still technically correct, only the freshness check catches it). Both checks are necessary, the signature alone can't detect replay, and the timestamp alone, unsigned, could be forged.

Glossary

authorization code flow — OAuth2 flow for user-delegated access; a short-lived code stands in for the access token during the browser redirect.
client credentials flow — OAuth2 flow for service-to-service access; no user, direct exchange of client ID and secret for a token.
PKCE — Proof Key for Code Exchange; lets public clients (that can't hold a secret) safely use the authorization code flow.
JWT — JSON Web Token; header.payload.signature, base64url-encoded, self-contained and verifiable without a callback.
exp / aud / iss — expiration / intended audience / issuer claims; each closes a specific forgery or replay gap.
HMAC — Hash-based Message Authentication Code; proves a message came from a holder of the shared secret and wasn't altered.
timing attack — extracting secret information from how long an operation takes, not from its output.
constant-time comparison — a comparison whose execution time doesn't depend on how much of the input matches, closing the timing-attack channel.
