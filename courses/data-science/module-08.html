Module 8 of 9

Dashboards & Business Communication

A correct analysis that nobody acts on is a wasted analysis. This module is about the last, hardest step: turning a real number into a report a busy stakeholder reads in 30 seconds and knows exactly what to do with.

By the end of this module you'll be able to
  • Build headline KPIs from a real, messily-formatted dataset
  • Catch a dashboard number that's silently wrong before you ship it (the "you can't just sum this" trap)
  • Translate a pattern into a dollar-denominated business impact, with a defensible method
  • Structure a report as DATA → FINDING → BUSINESS IMPACT → RECOMMENDATION → ACTION, not methodology-first
  • Write a real recommendation, using your own computed numbers, that a stakeholder could act on today
8.0

Lead with the answer, not the method

A technical audience wants to see your work first. A business audience wants the answer first, then enough of your work to trust it. Almost every report that gets ignored made this mistake.

What most first drafts look like"I pulled the quarterly P&L data and grouped it by period after standardizing the date formats, then computed a trailing average to establish a baseline for comparison, which showed..."
What a stakeholder actually needs, first"Q3 revenue has dipped below trend three years running, costing roughly $127K total. Recommend: investigate Q3 demand drivers before this year's Q3."
The five parts, in this order

DATA (the number) → FINDING (the pattern in the number) → BUSINESS IMPACT (why it matters, in dollars or another concrete unit) → RECOMMENDATION (what to do) → ACTION (the specific next step, with an owner or timing if you can name one). Methodology, if anyone asks, goes in an appendix, not the opening line.

8.2

The trap: a dashboard number that's silently wrong

The dataset: inventory_supply.csv, 144 rows of stock across 3 warehouses.

The trap: the same SKU can be stocked in case units at one warehouse and each units at another, 27 of the 77 SKUs here do exactly that. A dashboard tile that does SUM(stock_qty) across all rows silently adds cases to eaches as if they were the same thing, the total it shows is a real number that means nothing.
Pattern

Before any KPI touches a quantity column, check whether the unit is consistent. If it isn't, either convert to one unit first or report per-unit totals separately, never a blended sum.

Exercise 2 · real data, real Python, graded

Write reorder_risk(df): return {"negative_stock_rows": n, "below_threshold_rows": n, "skus_with_mixed_units": n}. below_threshold_rows counts rows where 0 <= stock_qty < reorder_threshold (a real reorder need). negative_stock_rows counts rows where stock_qty < 0 (a data error, not a reorder signal, flag separately). skus_with_mixed_units counts distinct SKUs that appear with more than one unit value across warehouses.

8.3

Turning a pattern into a dollar figure

Business question: "The recurring Q3 dip from Module 7, how much has it actually cost us?"

A defensible method, not a precise one: there's no ground truth for "what Q3 would have been." A reasonable, stateable estimate: for each year, average that year's other three quarters as a rough counterfactual for what Q3 "should" have been, then compare. It's an estimate, say so, but it's a real number a stakeholder can reason about, which is more useful than "revenue was lower."
Exercise 3 · real data, real Python, graded

Write q3_dip_cost(df): for each year (2024, 2025, 2026), compute the counterfactual as the average of that year's Q1, Q2, and Q4 revenue, subtract actual Q3 revenue to get that year's gap, then return {"gap_2024": ..., "gap_2025": ..., "gap_2026": ..., "total_gap": ...} (all rounded to 2 decimals).
