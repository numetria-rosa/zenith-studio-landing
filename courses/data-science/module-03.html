3.1

Loading and inspecting an unfamiliar dataset

When someone hands you a file you've never seen, you do the same four things every time, before any analysis. This sequence is a habit worth building now.

The first-look sequence

df.shape, how many rows and columns am I dealing with?
df.head(), what does a row actually look like?
df.dtypes, did each column load as the type I expected? (a number column that loaded as text is a real and common problem)
df.describe(), what's the range of the numbers? Anything absurd?

import pandas as pd

df = pd.read_csv("retail_sales_ledger.csv")
print(df.shape)
print(df.dtypes)
(62, 7) order_id object order_date object region object product_line object units float64 unit_price float64 revenue float64
Read that dtypes output carefully: object means text. Notice order_date loaded as text, not as a date, pandas does not guess dates by default. Until you convert it (section 3.6), you cannot do date maths on it. And notice units is float64 (a decimal) rather than a whole number, which is pandas telling you something: a column of whole numbers becomes a float when it contains a missing value.

3.2

Selecting and filtering

Selecting picks columns. Filtering picks rows that meet a condition. These are the two moves you'll make more than any others.

df["revenue"]              # one column
df[["region", "revenue"]]  # several columns (note the double brackets)
df[df["revenue"] > 50000]  # only rows where the condition is True
df[(df["region"] == "West") & (df["revenue"] > 20000)]  # two conditions
Why the strange & and the extra brackets? In pandas you combine conditions with & (and) and | (or), not the words and/or. Each condition needs its own parentheses. This trips up nearly everyone once, if you get a confusing error about "truth value is ambiguous," this is almost always why.

3.3

Calculated columns and missing values

A calculated column is a new column derived from existing ones. This is where "thinking in whole columns" starts paying off, no loop required.

df["line_total"] = df["units"] * df["unit_price"]  # whole column at once
The missing-value trap: the retail file has one row with a missing units value. Multiply that row and you get NaN ("not a number"), pandas' marker for missing. NaN is contagious: any arithmetic touching it produces NaN. But .sum() and .mean() quietly skip NaN by default. That inconsistency is exactly why you check df.isna().sum() early, so you know it's there before it changes a number you report.
Three honest options for a missing value

Drop it (df.dropna(subset=["units"])), fine when it's rare and random, dangerous when it isn't.
Fill it (df["units"].fillna(0)), only when zero (or the mean, or whatever you choose) is genuinely meaningful for that column.
Leave it and be explicit, often the most honest choice; report the count alongside the result.
Module 4 goes much deeper on how to actually decide. For now, notice that "do nothing" silently makes the choice for you.

3.4

Grouping and aggregating

groupby is the single most useful thing pandas does. It's the pivot table from Module 1, expressed as code: split the rows into groups, compute something per group, collect the answers.

df.groupby("region")["revenue"].sum()   # total revenue per region
df.groupby("region")["revenue"].mean()  # average order size per region
df.groupby("region").size()                # how many orders per region
region East 630432.14 North 311019.81 South 246002.85 West 349244.88
Business framing matters more than the syntax: .sum() answers "where does our money come from?" while .mean() answers "where are the big orders?" and .size() answers "where is the activity?" Those are three genuinely different business questions, and picking the wrong one produces a confident, wrong answer. Deciding which is the analyst's job; typing it is the easy part.

3.5

Merging two datasets

A merge (a join) combines two tables using a shared key column. This is XLOOKUP from Module 1, and SQL's JOIN from Module 6, same idea, three syntaxes.

merged = headcount.merge(overtime, on="employee_id", how="inner")
The four join types, plainly

inner, keep only rows that matched in both. The default choice, and the one that silently drops data.
left, keep every row from the left table, fill blanks where there was no match. Use when the left table is your "source of truth."
right, the mirror image; rarely used, since you can usually just swap the tables.
outer, keep everything from both. Useful for finding what didn't match.

The rule that separates careful analysts from careless ones: always check the row count before and after a merge. If it went up, your key wasn't unique and rows got duplicated. If it dropped sharply, an inner join threw away data you may have needed. Neither raises an error. Both quietly change your answer.

3.6

Working with dates

Remember from 3.1 that order_date loaded as text. Until you convert it, "2026-05-03" is just a string, you can't ask which month it's in, or sort it reliably when formats vary.

df["order_date"] = pd.to_datetime(df["order_date"])
df["order_date"].dt.month   # 1-12
df["order_date"].dt.year
df["order_date"].dt.day_name()
What .dt means: once a column holds real dates, .dt unlocks date-specific accessors on the whole column at once, month, year, weekday, and so on. If you get an error saying .dt isn't available, it means the column is still text and you skipped the to_datetime step.
