Prompt Engineering for Software Engineers

Turn vague requests into reliable engineering instructions for AI coding assistants.

You are not learning magic words that make AI smarter. You are learning how to give an AI coding assistant enough context, constraints, evidence, and success criteria to produce useful engineering work — and how to recognise when your prompt is still underspecified.

A good AI result starts with a good engineering request. Prompting sits inside specification → implementation → testing → review → shipping. It is not a separate trick.

By the end of this module you can
  • Turn a vague ticket into a prompt with context, task, constraints, acceptance criteria, and verification
  • Give the minimum sufficient context, not a whole-repository dump
  • Bound an agent: allowed files, prohibited changes, plan first, stop conditions
  • Catch AI failure modes: missing constraints, test theatre, false confidence, confirmation bias
  • Know when the correct move is to stop prompting and gather evidence yourself

00

What is a prompt?

A prompt is the instruction and context you give an AI system. For software engineering, a useful one often contains context, an objective, relevant files or code, constraints, expected behaviour, acceptance criteria, tests, and output requirements.

Vague prompt

Like a ticket that says \u201cmake the checkout better.\u201d

Strong prompt

Like giving a developer the affected flow, current behaviour, business rule, constraints, acceptance criteria, and tests.

Give the AI the minimum sufficient context required to make a correct decision. Not every prompt must be enormous. Better prompting is not simply more prompting.

Do this now. Take \u201cfix the login bug.\u201d Add one piece of context (which flow) and one acceptance criterion you could check without asking what \u201cfixed\u201d meant.

Go deeper: context windows and indexing (optional)

Models have a finite context window. Repository indexing helps an agent find files, and it still guesses if you do not point at the relevant ones. Structured output (a plan, then a diff) beats a wall of code. Prompt templates are reusable specs, not spells. None of that replaces naming the ticket, the file, and the test.

01

CONTEXT → TASK → CONSTRAINTS → ACCEPTANCE → VERIFY

Use this throughout the rest of the course. Memorise the five words, not a 400-line template.

  • Context — What does the AI need to know? Files, data shape, current behaviour, the error.
  • Task — What exactly should it do? Investigate, plan, implement, or review — pick one.
  • Constraints — What must it not change? API, schema, unrelated files, dependencies.
  • Acceptance — How do we know it is correct? Observable behaviour a stranger could check.
  • Verify — How should the result be tested? Name the case, not the word \u201ctests.\u201d

Do this now. Say the five words out loud, then look at Dan's ticket and name one item for each.

02

Vague vs engineered prompts

Bad

Fix the login bug.

Better

Investigate the login failure in the authentication flow. Identify the likely cause before changing code. Check the login request, response handling, and session creation. Do not modify unrelated authentication behaviour.

Strong

Investigate the login failure in the authentication flow. First inspect the request payload, authentication response, and session creation path. Identify the root cause before editing code. Preserve the existing authentication API and validation behaviour. After the fix, add or update a regression test that reproduces the original failure and verify both successful and failed login paths. Do not claim the issue is fixed until the test passes.

The third is better because it sequences investigation before edits, names the paths to inspect, freezes the API, and refuses a success claim without a regression case. The second is scoped. The first lets the AI invent the bug, the file, and the definition of done.

Do this now. Underline, in the strong prompt, the constraint and the verification sentence. Those two are what stop a rewrite.

03

Context engineering

AI quality depends on what it can see: project structure, relevant files, data models, API contracts, existing tests, error messages, logs, requirements, constraints. Do not dump the entire repository. Provide the smallest relevant context that changes the answer.

Messy bug report: \u201cThe huddle numbers are weird some mornings. Also the site is slow. Can you look at everything?\u201d

Do this now. Before the next lab, list the three files you would @-mention in Cursor for this bug — and one you would leave out.

Go deeper: context management (optional)

If the conversation is long, start a new thread and paste the spec again. Indexing is not understanding. A 2,000-line paste can bury the one stack trace that mattered. Prompt versioning (saving the instruction that worked) is an engineering artefact, same as a runbook.

04

Specification prompting

Make requirements explicit: objective, inputs, outputs, edge cases, constraints, dependencies, acceptance criteria. You already practised this shape in Module 2. Here you learn to send it. Do not require every possible detail if it is irrelevant. Relevant completeness beats a novel.

Do this now. For \u201cadd a dashboard filter,\u201d write one line each: what is filtered, where it happens, empty state. Lab 3 grades the full set.

05

Constraints

Tell the AI what it must preserve: API, database schema, existing behaviour, no new dependencies, mobile layout, accessibility, unrelated files, existing tests. Constraints matter because helpfulness without a fence is a rewrite.

Do this now. Add one constraint to a prompt you wrote this week, even a private one: \u201cDo not modify files outside X.\u201d

06

Acceptance criteria

Bad

Build the form.

Strong

The form must reject an empty email, reject invalid email format, show an accessible error message, preserve valid values after validation failure, submit only when all required fields pass, and include tests for each failure case.

If success cannot be checked, the AI has too much freedom. Criteria must be observable and testable.

Do this now. Rewrite \u201cthe form should work\u201d as one Given / When / Then you could demo on a phone.

07

Prompting for planning

Separate PLAN → IMPLEMENT → VERIFY. Do not start with \u201cbuild this.\u201d First: inspect the existing implementation and propose a plan. Identify affected files, dependencies, risks, and tests. Do not modify code yet. Then implement the approved plan. Then run the relevant tests and report failures. That reduces blind AI changes.

Do this now. Prefix your next agent request with: \u201cDo not modify code yet. Propose a plan.\u201d

Go deeper: planning and verification loops (optional)

Some agents run a plan loop and a tool loop. Your job is to set the checkpoint: plan visible, then permission to edit, then tests. Tool-use boundaries (which commands, which directories) are the same idea as file constraints.

08

Prompting for debugging

Structure: symptom, expected behaviour, actual behaviour, reproduction steps, relevant code, error/log, constraints, verification requirement.

Do this now. Paste a real error from practice into that shape. If you have none, use the TypeError in Lab 4.

09

Prompting for tests

Do not ask \u201cwrite tests for this function\u201d and trust the suite. Ask it to identify intended behaviour and edge cases first, then propose tests for normal input, invalid input, boundary conditions, empty input, and the regression you care about. Do not use assertions that can pass without executing the actual behaviour.

This is the course's anti-hardcode rule applied to prompts: AI can generate tests that look impressive while testing almost nothing.

Do this now. Take a function you wrote in Module 5. Name one case that would stay green if the function always returned [].

10

Prompting for code review

Ask: review for correctness, security, accessibility, maintainability, and test coverage. Do not merely summarise. Identify concrete risks, explain why they matter, recommend verification, distinguish confirmed defects from potential concerns. You will reuse this in the AI Review Lab.

function lineTotal(item) {
  return item.price;
}
function grandTotal(items) {
  return items.reduce((t, i) => t + lineTotal(i), 0);
}

Do this now. Write one review question this sample does not answer: what happens when quantity is 2?

11

Security prompting

Do not ask \u201cis this secure?\u201d Ask the model to evaluate specific threat categories and provide evidence: authentication, authorization, input validation, injection, secrets, XSS, CSRF where relevant, file uploads, exposed APIs, insecure defaults.

Bad

Is this secure?

Better

Review this endpoint for authorization bypass, injection, sensitive-data exposure, and unsafe input handling. For each concern, identify the exact code path and explain how it could fail. Do not claim the endpoint is secure unless each category has been checked.

Do this now. Add two threat names to any \u201creview this\u201d prompt you will use in Module 11.

12

Accessibility prompting

Do not ask \u201cmake it accessible.\u201d Ask: review this form for keyboard use, labels, focus management, validation errors, and semantic structure. Identify specific issues and propose tests. Same philosophy as Module 3: a placeholder is not a label.

Do this now. Name one accessibility check you can perform without a screen reader (Tab order, visible label, focus ring).

13

Prompting agents

Asking AI a question is not the same as giving an AI agent authority to modify a project. Define scope, allowed files, prohibited changes, checkpoints, tests, stopping conditions, and review requirements. The more autonomy the agent has, the more explicit the boundaries should become.

Bounded agent

Work only inside /src/auth. Do not modify the database schema or package dependencies. First inspect and propose a plan. After implementation, run the authentication tests. Stop if the required behaviour conflicts with an existing API contract.

Do this now. Write the stop sentence you will reuse in Lab 5.

Go deeper: agent permissions (optional)

Editor agents may have shell, network, and file tools. Treat permissions like production access: least privilege. A plan-only mode is a checkpoint, not a personality setting.

14

Iterative prompting

Good prompting is often a conversation, not one enormous instruction: understand → plan → implement → test → review → correct → summarise evidence. Do not cram every possible instruction into prompt 1.

Do this now. Split \u201cbuild the dashboard and tests and review it\u201d into three sends.

15

When not to prompt

Sometimes the correct action is to stop asking AI and investigate yourself: unclear business rule, missing production data, ambiguous security requirement, conflicting specs, unexplained test failure, uncertain legal/compliance, AI contradicts observed behaviour. Gather evidence first.

Do this now. Name one question in your own work that an agent cannot answer because only Priya (or your real stakeholder) can.

16

AI failure modes

  • Ambiguity — AI guesses what you meant.
  • Missing context — AI assumes an architecture.
  • Missing constraints — AI changes too much.
  • Missing acceptance — AI decides what \u201cdone\u201d means.
  • Confirmation bias — AI agrees with your wrong assumption.
  • Overly broad scope — unrelated files change.
  • False confidence — success reported without evidence.
  • Test theatre — tests that do not execute the behaviour.
  • Context overload — the relevant line is buried.
  • Prompt overengineering — a huge prompt that still underspecifies the task.

Better prompting is not simply more prompting. A prompt is an engineering specification. The better the AI gets, the more important it becomes to specify, verify, and review its work.
