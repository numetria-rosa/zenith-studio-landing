Module 2 · Ticket NL-002

Give the agent a feature it can actually build

Dan forwarded one sentence and called it a brief. Your job today is not to write booking code. It is to turn that sentence into instructions an AI coding agent can be supervised against — and to reject a plan that quietly does something else.

By the end of this module you can
  • Turn a second-hand complaint into questions that have factual answers
  • Write user stories with a reason clause that can rule solutions out
  • Write acceptance criteria a stranger could check without asking you what you meant
  • Name edge cases and write down what you are not doing
  • Send a structured request, then reject a plan that exceeds it
Do this now

What: Dan said “make booking better.” Why: that is not a requirement. Do: write questions with factual answers, then criteria a stranger can check (Given some starting state, When someone does X, Then something observable happens), then reject the agent plan that adds extras. Success: you can point at in-scope vs out-of-scope. Next: Module 3 (HTML), or the Spec lab for extra reps.

00

Why this matters

The faster your tools can build, the more expensive it becomes to be wrong about what to build. An agent will never ask you what you meant. It will guess, instantly, in four hundred confident lines.
01

Before you touch AI

Dan's message is: "Client says booking is confusing. Can you just make it better?"

There are no requirements in that sentence. There is a symptom, reported second-hand, with a verdict attached. Opening an editor now is how you spend a week building the wrong thing.

Useless question

"What would you like it to look like?" — Priya is not a designer. You are outsourcing your job.

Useful questions

"When someone gets confused, what do they do next?" · "How many bookings come in by phone because the form did not work?" · "Show me the last person who got stuck."

Those questions produce facts: eight people a week call because they could not tell whether the form submitted. That is a requirement in disguise. "Confusing" was not.

02

Ticket breakdown

Interview the request one slot at a time. Each correct answer fills a line of the specification draft. This is not prompt engineering. This is the work you do before a prompt exists.

03

The shapes a reviewer will look for

The breakdown gave you the content. These three shapes are how you write it down so someone else — including an agent — cannot wriggle out of it.

As a [role], I want [capability], so that [outcome].

Given   some starting situation
When    someone does something specific
Then    something specific and observable happens
A story with a reason

As a patient, I want a clear confirmation after I submit a booking request, so that I do not phone the clinic to check whether it went through.

A criterion a stranger can run

Given I have filled in name, email, and a preferred date, when I press Request appointment, then the form is replaced by "Request received — we will call you within one working day".

Not a criterion

"The form should work properly and be user friendly."

The third clause of the story is the one everybody drops. Without so that you cannot tell whether a proposed solution is any good. A fancier submit button does not stop the phone calls. A named confirmation message might.

How to find edge cases without hoping

Walk each criterion and ask what if this is not normal?

  • Empty — nothing filled in. Blank name. Blank date.
  • Wrong — "next tuesday" in a date field. An email with no @.
  • Too many — the same person pressing Request four times because nothing appeared to happen.
  • Impossible — a date in the past. A Sunday, when the clinic is closed.
  • Broken world — the connection drops mid-submit.

Famous edge cases (empty string, null) are free. Domain rules — the clinic is shut on Sunday — are yours. An agent has never met Priya.

Where the agent trips. Ask it to “handle edge cases” and you will get validation for the famous ones. You will not get Sunday is closed, so a Sunday request is a promise you cannot keep.
04

AI coding agent simulation

You now have a spec. The next skill is supervision: send a request an agent can execute, read the plan before any code exists, and reject the ones that wander.

Nothing in this section runs a coding agent. The replies are canned. That is the honest version of practising judgement without pretending Cursor is inside this tab.

05

Where the agent earns its place

None of this means working alone. It means knowing which half is yours.

Choose the better request · labelled simulation
  • Widen the edge-case list — then you cut two thirds of it.
  • Attack your own spec — "read these criteria as a hostile reviewer."
  • Tighten wording — rambling criterion into a crisp Given / When / Then.

Bad uses, all of which produce confident output: asking it to decide what the client needs; asking it to prioritise; accepting thirty edge cases wholesale.
