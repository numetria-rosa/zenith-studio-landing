03

The DOM is not your HTML file

You wrote a file. The browser read it and built something else out of it: a live tree of objects. That tree is the DOM, and it is what is actually on screen.

This distinction matters because they can diverge immediately. JavaScript changes the DOM; the file on disk is untouched. Reload and your changes are gone. Every "why did my change disappear" question is this.

// find things
document.querySelector("#hoursList");      // the first match for a CSS selector
document.querySelectorAll(".row");         // all matches

// read and change
el.textContent = "Closed today";           // the text inside
el.classList.add("is-open");               // add a class
el.hidden = true;                          // hide it

querySelector takes exactly the selectors you learned in Module 4, which is a genuine kindness.

04

textContent versus innerHTML, and why it is a security question

Two ways to put content into an element. They are not interchangeable.

el.textContent = value;   // inserts value as TEXT. tags become visible characters.
el.innerHTML  = value;    // PARSES value as markup. tags become elements.

For content you wrote, innerHTML is fine and often convenient. For anything a user typed, it is a vulnerability:

const name = '<img src=x onerror="alert(document.cookie)">';

el.textContent = name;   // shows those characters on screen. harmless.
el.innerHTML  = name;    // creates a real element and runs the handler.

That is cross-site scripting, in one line, from a name field. The rule is simple: user data goes in with textContent. If you genuinely need markup from user input, that is a real problem requiring a real sanitiser, not a convenient property.

Where the agent trips. Agents reach for innerHTML by default when rendering a list, because it is the shortest way to build rows from data. On a page rendering patient names it is an injection point. This is the single most common security defect you will find in AI-generated front-end code, and it is completely invisible until someone types the wrong thing.
05

Events: reacting to a person

An event is something happening — a click, a keystroke, a form submission. You attach a listener and it runs.

button.addEventListener("click", function () {
  // runs each time it is clicked
});

input.addEventListener("input", function (event) {
  const typed = event.target.value;   // what is in the box now
});

form.addEventListener("submit", function (event) {
  event.preventDefault();   // stop the browser navigating away
  // now handle it yourself
});

event.preventDefault() on a submit handler is the one to remember. The browser's default is to leave the page, which takes your JavaScript with it. Without that line your handler appears not to run at all — it runs, and then everything is thrown away.

Two habits that matter:

  • Attach to real controls. A listener on a <div> only fires for a mouse. Put it on a <button> and Enter, Space, and assistive technology all work for free.
  • Guard against the double press. If nothing visible happens when someone submits, they press again. That is not user error; that is your interface failing to acknowledge them — and it is why NL-002 was really about a confirmation message.
06

Data that arrives late

Ticket NL-006: stop hard-coding the list, read appointments.json. That introduces time.

Fetching a file takes a while — milliseconds on your laptop, seconds on a phone on a train. JavaScript does not wait. It fires the request and keeps going, and the data turns up later.

// Wrong, and the classic first mistake:
const rows = fetch("appointments.json");
console.log(rows.length);   // undefined. nothing has arrived yet.

// Right: await says "pause here until it resolves".
async function loadAppointments() {
  const response = await fetch("appointments.json");
  const rows = await response.json();
  return rows;
}

async marks a function as one that can wait. await is where it waits. Anything depending on the data goes after the await, not before.

And then the part the happy path never exercises. Four states, not one:

  • Loading — the request is out. Say so, or the page looks broken.
  • Success with data — render it.
  • Success with nothing — the file was fine and the list is empty. "No appointments today" is a real, correct, designed state. A blank area is not.
  • Failure — the file is missing, the connection dropped, the JSON is malformed. Say something honest and, if you can, offer a retry.
async function loadAppointments() {
  try {
    const response = await fetch("appointments.json");
    if (!response.ok) return { ok: false, rows: [] };   // 404, 500
    return { ok: true, rows: await response.json() };
  } catch (err) {
    return { ok: false, rows: [] };                     // offline, bad JSON
  }
}

Note that fetch does not throw on a 404. It resolves successfully with a response whose ok is false. Forgetting to check response.ok means your code cheerfully tries to parse an error page as JSON.

Where the agent trips. Ask an agent for data loading and you will get the happy path, correctly. Ask twice and you may get a try/catch. You will almost never get the empty state, because an empty list is not an error and nothing about it looks like a bug — until Priya opens the dashboard on a quiet Tuesday and sees a blank rectangle and calls Dan.

Required exercise · domDataExercise · part 1 of 2

All four states. Write summarise(result) where result is what the loader returns: { ok, rows }, or null while the request is still in flight.

  • null → "Loading appointments..."
  • ok: false → "Could not load appointments."
  • ok: true with an empty list → "No appointments today."
  • ok: true with rows → "4 appointments, 2 still open" — and "1 appointment, 1 still open" for a single row.

Wire it to a real interface. Write wireFilter(root). Inside root there is a <button id="toggle"> and a <ul id="list"> whose <li> elements each carry data-status. Clicking the button hides every row that is not open; clicking it again shows them all. Hide with the hidden property.
