Module 06

Reliability for LLM Systems

Model APIs fail: rate limits, timeouts, transient server errors. Some failures are worth retrying, some never will succeed no matter how many times you try, and treating them the same wastes time, money, and your users' patience.

Learning objectives
  • Distinguish retryable (transient) failures from non-retryable (permanent) ones
  • Explain exponential backoff with full jitter, and why naive fixed-delay retries make things worse under load
  • Explain when and why a system should fall back to a secondary model instead of retrying forever
  • Implement a call wrapper that retries transient failures, fails fast on permanent ones, and falls back exactly once
Before you start

What this module assumes

Every prior module assumed the model call itself succeeds. It won't always. Rate limits, timeouts, and transient server errors are a normal, expected part of calling any external API, model providers included, and a production system needs a deliberate strategy for them, not a bare try/catch that gives up on the first failure.

What's new

This module isn't about the model's output anymore, it's about the reliability of getting a response at all. The logic here (retry, backoff, fallback) applies to the model call layer underneath everything Modules 1-5 built.

What's assumed

Modules 1-5 completed. Comfort with Python's async/await, try/except, and loops.

  3. Finish with the graded checkpoint.
1

Not every failure deserves the same response

When a model API call fails, the error tells you something important: whether trying again could possibly help. A rate limit (429) or a server-side timeout is transient, the exact same request might succeed a second later. A malformed request or an authentication failure is permanent, retrying the identical request will fail identically, every time, forever.

Definition: retryable vs. non-retryable error

A retryable error indicates a temporary condition (rate limiting, timeout, transient server fault) where an identical retry has a real chance of succeeding. A non-retryable error indicates the request itself is invalid or unauthorized, retrying without changing anything will not help.

Getting this classification wrong in either direction is a real cost: retrying a non-retryable error burns time and budget on guaranteed failures, while failing fast on a retryable one throws away requests that a second attempt would have succeeded on.

Practice check

You integrate with a payment processor to charge cards during a flash sale. In the same minute, two calls fail: one returns HTTP 429 ("too many requests", the processor is throttling your API key under the traffic spike), the other returns HTTP 402 ("card declined, insufficient funds"). Which should your wrapper retry, and what's the actual risk of retrying the wrong one here, beyond just wasted time?

Check your answer
The 429 is retryable, your API key got throttled, not rejected, the identical charge attempt has a real chance of succeeding once the window resets. The 402 is non-retryable, the card has insufficient funds right now, and retrying the identical charge won't change the customer's balance. Retrying the 402 doesn't just waste a retry slot, it delays the moment the customer learns they need a different card, and depending on the processor, repeated charge attempts against a declined card can itself look like suspicious activity. Classification here isn't just about efficiency, retrying the wrong kind of failure has a real user-facing cost.

Practice check

Two different users' requests both get rate-limited at the exact same moment. With NO jitter (fixed exponential delay only), what's likely to happen on their simultaneous retries? How does jitter change that outcome?

Check your answer
With no jitter, both requests compute the identical delay and retry at the identical moment, likely colliding with the rate limit again, and any other similarly-timed callers pile on too, a "retry storm" that can make the underlying rate-limit problem worse instead of better. Full jitter spreads retries across a random window instead of a single instant, so simultaneous failures don't produce simultaneous retries, smoothing out load on the API instead of concentrating it.
Practice check

An internal "pricing" microservice gets called by 500 instances of your checkout service. During a traffic spike, pricing starts returning 503s under load. All 500 checkout instances were deployed from the same image at the same time, and all implement exponential backoff with NO jitter. Walk through what happens over the next few retry rounds, and be specific about why "same code, same deploy time" makes this worse than if the 500 instances had staggered start times.

Check your answer
Because all 500 instances share the same code and the same clock-relative starting point, they compute the exact same backoff delay for attempt 1, and all 500 retry in the same instant, hitting the already-overloaded pricing service with another synchronized spike, which fails again, computes the same attempt-2 delay, and repeats, a predictable wave of 500 simultaneous requests at every backoff step instead of a chance for the service to drain its queue. Staggered start times would have accidentally spread the retries out somewhat, but you shouldn't have to rely on accidental staggering, full jitter randomizes each caller's delay independently every round, so even 500 perfectly identical, perfectly synchronized callers end up retrying at 500 different moments instead of one.
3

Fail fast on what retrying can't fix

Retrying a non-retryable error isn't just wasted effort, it actively delays the moment your system (or your user) learns the request failed, and it does so while consuming the same retry budget a genuinely transient failure would have needed. The correct response to a non-retryable error is to stop immediately and surface it.

Retrying blindly hides real bugs. A malformed request retried 5 times with backoff doesn't become valid on attempt 5, it just takes 5 attempts (and the accumulated delay) to fail instead of one. If the bug is in your own request construction, fast, visible failure is what gets it fixed, silent retries just delay the failure without ever preventing it.
Practice check

An error's classification (retryable or not) isn't always obvious from the HTTP status code alone, some providers return the same generic 500 for both a truly transient fault AND a request that will never succeed. What's the practical implication for how conservatively you should classify "unknown" errors?

Check your answer
When classification is ambiguous, treating an error as retryable (with a bounded retry count, never unlimited) is usually the safer default, a spurious retry on a permanent failure costs one bounded extra attempt, while treating a genuinely transient failure as non-retryable throws away a request that a second try would have saved. The key safeguard either way is the SAME bound: a maximum retry count, so an ambiguous classification never turns into an unbounded retry loop.
4

When retries aren't enough: fallback

Sometimes the primary model is down, overloaded, or exhausted its retry budget, and no amount of waiting fixes it in time. A fallback, a secondary model or provider, gives the system a path to still return a result instead of failing the entire request.

Definition: fallback

A secondary call path attempted after the primary path has failed (exhausted retries, or hit a non-retryable error), typically a different model or provider, used to still return a usable result when the primary is unavailable.

Fallback isn't free, it's often a different (sometimes lower-capability, sometimes more expensive) model, and switching to it is itself a decision worth logging and monitoring, a system quietly falling back on every request is a signal something's wrong with the primary path that deserves attention, not just automatic compensation.

Practice check

Should the fallback call itself be retried the same number of times as the primary, if it also fails?

Check your answer
No, not with the same generous budget. If both the primary AND the fallback need extensive retries, the underlying issue is probably broader than one provider's outage, and the request should fail clearly rather than spend a second full retry budget hoping the fallback behaves better. A single fallback attempt (or a much smaller retry budget than the primary got) keeps total latency and cost bounded, the same "don't let a safety net become another unbounded loop" principle from Module 5's step limits.
Practice check

Your customer-facing chatbot's primary LLM provider has a partial outage: primary calls fail with 503s, retries with backoff exhaust the retry budget, and the wrapper falls back to a smaller, cheaper backup model. But the outage is severe enough that most of your traffic is now hitting the backup model at once, and IT starts returning occasional 503s too. Should the wrapper retry the fallback call with backoff the same way it retried the primary?

Check your answer
No. Fallback still gets one bounded attempt, not a second retry cycle, even though the circumstances (a real, severe outage) make it tempting to fight harder for a result. Giving fallback the primary's full retry budget just moves the unbounded-cost risk from one path to the other, and if the fallback is now also under heavy load, retrying it aggressively adds MORE load to a system that's already struggling. The correct response to "even the backup is straining" isn't a bigger retry budget, it's returning a clear failure for that request and treating the fallback's own error rate as a signal (worth alerting on) that something bigger than one provider's outage is happening.
5

Retry, fallback, and bounded cost, together

Put together, a reliable call wrapper has a specific, bounded shape: try the primary, retrying only retryable failures up to a fixed limit; the moment a non-retryable error appears OR the retry limit is hit, stop retrying the primary and attempt the fallback exactly once; if that also fails, return a clear failure. Every path through this logic terminates, nothing loops forever.

Every reliability mechanism in this course bounds something. Module 2 bounded context (a token budget). Module 5 bounded steps (a step limit). This module bounds retries (a fixed retry count) and bounds the safety net itself (fallback tried once, not retried indefinitely). The pattern repeats because unbounded anything, tokens, steps, retries, is the same underlying risk each time.
Cross-module check

An agent loop (Module 5) calls a model at each step. That model call now uses this module's retry-and-fallback wrapper internally. If the wrapper's own retry count and fallback aren't bounded, what happens to the loop's step-limit guarantee?

Check your answer
The step COUNT stays bounded, the loop still only takes maxSteps iterations. But each individual step can now silently take far longer (and cost far more) than expected, since an unbounded retry-and-fallback wrapper inside one step defeats the purpose of bounding the number of steps. A step limit only actually bounds total cost and time if everything INSIDE each step is bounded too, which is exactly why this module's retry and fallback logic has its own hard limits.

Build it: retry with bounded fallback

You've seen the classification (retryable vs. not) and the shape (bounded retries, single fallback attempt). Now implement it, and five real tests run against your actual code.

Code exercise · Python, runs in a real sandboxed Python interpreter (Pyodide)

Complete async def call_with_retry_fallback(primary_call, fallback_call, max_retries). Both primary_call and fallback_call are async functions, resolving on success or raising an Exception that may have a .retryable attribute set to True/False (treat missing/unset as retryable). Retry the primary on retryable failures up to max_retries times (so up to max_retries + 1 total primary attempts). Stop retrying immediately on a non-retryable error. Once the primary path is exhausted or blocked, call fallback_call exactly once. Return {"ok": True, "result": ..., "source": "primary"|"fallback"} or {"ok": False, "error": ..., "source": "fallback"}. Never let this function raise.

Stuck? Hints
Hint 1 — conceptual
This is a loop, not a fixed sequence: try the primary, and if it fails with a retryable error and you haven't hit max_retries, try it again. The loop ends either in success, or by falling through to the fallback path.
Hint 2 — specific
Track an attempt counter starting at 0. Wrap await primary_call() in try/except inside a loop. On success, return immediately. On failure, check getattr(e, "retryable", True) is not False (so unset counts as retryable) AND attempt < max_retries, if both hold, increment attempt and loop again, otherwise break out to the fallback step.
Hint 3 — near-solution
After the primary loop ends (without having returned), wrap a single await fallback_call() attempt in its own try/except. On success return {"ok": True, "result": ..., "source": "fallback"}, on failure return {"ok": False, "error": str(e), "source": "fallback"}. Don't loop the fallback at all, it only ever gets one try.
Solution — run your code at least once first
async def call_with_retry_fallback(primary_call, fallback_call, max_retries):
    attempt = 0
    while True:
        try:
            result = await primary_call()
            return {"ok": True, "result": result, "source": "primary"}
        except Exception as e:
            retryable = getattr(e, "retryable", True) is not False
            if not retryable or attempt >= max_retries:
                break
            attempt += 1

    try:
        result = await fallback_call()
        return {"ok": True, "result": result, "source": "fallback"}
    except Exception as e:
        return {"ok": False, "error": str(e), "source": "fallback"}
Practice check

Test 3 makes primary_call raise a non-retryable error, with max_retries set to 5. If your code checks attempt >= max_retries without ALSO checking retryable first, what happens?

Check your answer
Without checking retryable first, a non-retryable error would keep getting retried until the attempt counter separately reaches max_retries, 6 total calls to a request that was guaranteed to fail on the very first one. The retryable check needs to short-circuit independently of the attempt count, a non-retryable error should stop the primary loop on attempt 1, regardless of how high max_retries is set.

Further reading

If you want to go deeper than the browser can take you:

  • AWS's "Timeouts, retries, and backoff with jitter" architecture blog post is a widely-cited breakdown of why full jitter specifically outperforms fixed or exponential-only backoff under real concurrent load.
  • Circuit breakers (also covered in Automation Engineering) are a complementary pattern, once a certain fraction of recent calls to a provider have failed, stop calling it entirely for a cooldown period instead of retrying each request individually, useful when the failure is at the provider level, not the individual request level.
  • Most model providers publish explicit retry-after headers or documented retryable status codes, worth using directly instead of guessing at classification where available.

Glossary

retryable error — a failure where an identical retry has a real chance of succeeding (rate limits, timeouts, transient server faults).
non-retryable error — a failure where retrying the identical request will fail identically every time (malformed requests, auth errors).
exponential backoff — growing the delay between retries exponentially with each attempt, up to a cap.
full jitter — randomizing the actual delay uniformly between 0 and the backoff cap, to avoid synchronized retry storms.
fallback — a secondary call path (often a different model or provider) attempted once the primary path has failed.
