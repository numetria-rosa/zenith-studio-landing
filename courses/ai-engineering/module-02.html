Module 02

Context Windows & Token Economics

Every prompt has a budget, measured in tokens, not characters or "how much text feels reasonable." This module gives you the actual arithmetic for what fits, what it costs, and what to do when your content doesn't fit.

Learning objectives
  • Distinguish tokens from characters and words, and estimate token counts for planning purposes
  • Compute how much input fits in a context window given a reserved output budget
  • Explain why naive truncation silently drops information, and what a chunking strategy does instead
  • Implement a token-budget-aware chunker that preserves context across chunk boundaries
Before you start

1

A token is not a word, and not a character

Models don't process text as characters or whole words, they process tokens, sub-word chunks produced by a specific tokenizer. "Token economics" isn't jargon for its own sake, everything about what fits in a prompt, what it costs, and how fast it responds is measured in tokens, not in the units you're used to thinking in.

Definition: token

The atomic unit a model's tokenizer splits text into, roughly, but not exactly, 4 characters or three-quarters of a word in English. Punctuation, whitespace, and rare words often cost more tokens than intuition suggests.

This course uses a simplified estimate, tokens ≈ characters / 4, close enough for planning purposes and exactly what the exercises in this module use. Real tokenizers are more precise and vary by model provider, but the planning discipline is identical either way.

Practice check

A legal-contract summarizer receives a 52,000-character NDA and is about to send it to a model with a 12,000-token context window, 1,500 tokens of which are reserved for the output summary. Using this course's estimate, roughly how many tokens is the raw NDA text alone, and does it fit as plain input in a single call?

Check your answer
52,000 ÷ 4 = 13,000 tokens for the NDA text. Available input budget is 12,000 − 1,500 = 10,500 tokens. 13,000 is bigger than 10,500, so it does not fit, by about 2,500 tokens. This isn't a rare edge case for this kind of system, contracts routinely run long, and "just send the whole document" silently becomes impossible the moment the document is bigger than the math allows. The pipeline needs either a bigger-context model or a chunking strategy, not a bigger hope.

Move reserved-output up to 4000 while the context window is at its minimum, 2000. What happens to the available input budget, and why is this a realistic scenario, not an edge case someone made up?

Check your answer
The available input budget goes negative, there's no room left for input at all, the reserved output alone exceeds the whole window. The fix isn't a UI trick, it's choosing a model with enough context headroom for the task, or reducing what you're asking the output to contain.
3

Naive truncation silently destroys information

The laziest way to fit content into a budget is "cut it off at the limit." This is almost always the wrong move: it doesn't fail loudly, it succeeds while quietly discarding whatever came after the cut point, often the conclusion of a document, the most recent messages in a conversation, or the specific detail your task actually needed.

Truncation without a strategy is a silent data-loss bug. It doesn't throw an error. It doesn't log a warning by default. The system appears to work right up until someone asks a question the cut-off content would have answered.

A chunking strategy is the alternative: split content into pieces that each fit the budget, instead of throwing away everything past the first piece. Module 3 (retrieval) is what lets a system search across chunks instead of needing all of them in one prompt at once.

Practice check

A support-ticket summarizer truncates each ticket's text to the first 500 tokens before summarizing. A customer's actual complaint is in the last paragraph, after a long chronological narrative. What does the summary say, and why is "the code worked without errors" not the same as "the code worked correctly"?

Check your answer
The summary describes the chronological narrative and never mentions the actual complaint, because that paragraph was silently cut off before the model ever saw it. No exception was thrown, no log entry flagged it, the pipeline "worked" in the sense that it ran to completion and produced a plausible-looking summary. This is exactly the danger: a technically successful run that's functionally wrong, the kind of bug that survives testing because nothing in the execution path failed.
4

Why chunks overlap

If you split a document into non-overlapping chunks, a sentence or idea that spans a chunk boundary gets cut in half, in one chunk you get the setup with no conclusion, in the next you get the conclusion with no setup. Overlap, repeating the last portion of one chunk at the start of the next, keeps that boundary content readable in both directions.

Definition: chunk overlap

A deliberate repetition of content at the boundary between adjacent chunks, so no idea is split with zero context on either side. Typically 10-20% of the chunk size.

Overlap isn't free, it means the same content gets processed (and paid for) more than once. The right amount is a tradeoff between boundary-continuity and cost, not a fixed universal number.

Practice check

A meeting-transcript analyzer chunks a 3-hour transcript for action-item extraction, using 15% overlap. After a few action items turn out to have been split across chunk boundaries and missed, the team bumps overlap to 60% instead of touching chunk size. What does jumping to 60% overlap actually cost, and would increasing chunk size instead have addressed the same failure more cheaply?

Check your answer
At 60% overlap, most of each chunk is a repeat of content the previous chunk already covered, so the total tokens processed across the transcript balloons well past the transcript's actual length, more cost, more latency, for a fix that's really just papering over chunks that are too small for the unit of meaning (one action item's full context) to fit inside one. Increasing chunk size so a typical action-item discussion fits within a single chunk addresses the root cause directly, and a modest overlap (10-20%) is then enough to catch the rare item still split at a boundary. Overlap should catch the occasional edge case, not compensate for chunks sized too small for the content.
5

Cost and latency both scale with tokens

Two practical consequences follow directly from everything above: cost is (roughly) tokens × price-per-token, and latency generally grows with how many tokens the model has to read and generate. A chunking or truncation decision isn't just a correctness question, it's a cost and speed question too.

Overlap and chunk count trade off against cost. More overlap and smaller chunks mean more total chunks, which means more total tokens processed across the whole document, which means more cost and more total latency if chunks are processed sequentially.
Cross-module check

Module 1's validator rejects malformed output and (in a real system) triggers a retry with the parse error included in the next prompt. Using this module's terms, what does a retry actually cost, beyond just "trying again"?

Check your answer
A retry re-sends the original prompt tokens PLUS the new error-context tokens PLUS generates a new output, it's not free, it's close to double the token cost (and double the latency) of a single successful call. This is exactly why Module 1's repair pass tries deterministic, free fixes (stripping a fence, a trailing comma) before ever falling back to an expensive model retry, the cheap fix should always be tried first.
Practice check

A multi-document RAG ingestion pipeline chunks 200 source documents into roughly 3,000 chunks total, each embedded with its own model call. If 4% of those calls fail validation and get retried once, roughly how many total model calls does the ingestion run actually make, and why does chunk count matter just as much as retry rate when estimating a pipeline's total cost?

Check your answer
3,000 × 0.04 = 120 failed calls, each retried once, so the run makes roughly 3,000 + 120 = 3,120 total calls, about 4% more than the naive "3,000 chunks, 3,000 calls" estimate. Chunk count matters as much as retry rate because it's a multiplier sitting right next to it: the same 4% retry rate on a pipeline with smaller chunks (or heavier overlap, see the previous section) produces more total chunks, and 4% of a bigger number is a bigger number. Cost estimates for a chunking pipeline have to account for chunk count and retry rate together, not either one in isolation.

Build it: a token-budget-aware chunker

You've seen the failure mode (silent truncation) and the fix (overlapping chunks). Now implement it, and five real tests run against your actual code.

Code exercise · Python, runs in a real sandboxed Python interpreter (Pyodide)

Complete chunk_text(words, max_tokens_per_chunk, overlap_words, estimate_tokens). words is a list of word strings (already split, don't split further). estimate_tokens(word) is a function returning the token count for one word, call it per word. Return a list of chunks, each chunk a list of words. No chunk's total estimated tokens may exceed max_tokens_per_chunk, UNLESS a single word alone exceeds the budget, in which case it still gets its own chunk, never silently dropped. Each chunk (except the last) should end with the same overlap_words words that the next chunk starts with.

Stuck? Hints
Hint 1 — conceptual
Walk through the words with two pointers: build the current chunk word-by-word until adding the next word would exceed the budget, then start the next chunk a few words BACK from where you stopped, that's the overlap.
Hint 2 — specific
Track a running token total for the current chunk. Before adding a word, check if running_total + estimate_tokens(word) > max_tokens_per_chunk. If so, and the chunk already has at least one word, stop this chunk here. If the chunk is still empty, add the word anyway (that's the oversized-single-word case).
Hint 3 — near-solution
After finishing a chunk ending at word index j (exclusive), start the next chunk at index j - overlap_words (clamped to not go below 0, and not below where the current chunk started). Stop the outer loop once a chunk reaches the end of the words list.
Solution — run your code at least once first
def chunk_text(words, max_tokens_per_chunk, overlap_words, estimate_tokens):
    chunks = []
    i = 0
    while i < len(words):
        chunk = []
        tokens = 0
        j = i
        while j < len(words):
            t = estimate_tokens(words[j])
            if tokens + t > max_tokens_per_chunk and len(chunk) > 0:
                break
            chunk.append(words[j])
            tokens += t
            j += 1
        chunks.append(chunk)
        if j >= len(words):
            break
        i = max(i + 1, j - overlap_words)
    return chunks
Practice check

Test 3 feeds your chunker a single word whose own token estimate is larger than maxTokensPerChunk. If your budget check runs unconditionally, even when the current chunk is still empty, what happens to that word?

Check your answer
It gets silently dropped, exactly the failure mode this whole module is about. If the check "would this exceed the budget" applies even to an empty chunk, the word never gets added anywhere, and the chunker moves on without it, ever. The fix is the same guard used in the reference solution: only enforce the budget once the chunk already has at least one word, an oversized word still needs a home, even a chunk that technically exceeds budget by itself.

Further reading

If you want to go deeper than the browser can take you:

  • Every major model provider publishes an exact tokenizer (e.g. tiktoken-style byte-pair encoding), worth using directly in production instead of the character/4 estimate this course uses for planning.
  • "Lost in the middle" research on long-context models shows that even models with large context windows don't attend to all of it equally, position within the prompt matters, not just whether content technically fits.
  • In production, this shows up as ingestion pipelines with configurable chunk size and overlap, and as cost dashboards that break spend down by prompt tokens vs. completion tokens separately, since they're often priced differently.

Glossary

token — the atomic unit a model processes text as, roughly 4 characters in English.
context window — the maximum total tokens (input + output) a single model call can hold.
truncation — cutting content off at a limit; naive truncation silently discards whatever comes after the cut.
chunking — splitting content into budget-sized pieces instead of discarding what doesn't fit.
chunk overlap — repeating boundary content between adjacent chunks so no idea is split with zero context.
