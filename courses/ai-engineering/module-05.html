Module 05

Agent Architectures & Control Flow

One validated tool call is a single step. An agent is what happens when a model chains steps together, reasoning about each result before deciding the next action, in a loop it controls. That loop needs boundaries, or it doesn't stop on its own.

Learning objectives
  • Describe the reason-act-observe cycle and how it differs from a single prompt/response call
  • Explain why an agent loop needs a hard step limit, not just a "the model will know when to stop" assumption
  • Distinguish a legitimate termination condition from a stuck loop repeating the same failing action
  • Implement a bounded agent loop with step-limit and repeated-action guards
Before you start

What this module assumes

Module 4 made a single tool call safe to execute. This module is about what happens when a model doesn't stop after one call, it uses a tool's result to decide what to do next, calls another tool, and keeps going until it has an answer, or until something has to stop it.

What's new

Control flow you don't fully control. The model decides how many steps it takes and what each one is, your code's job is to bound that process so it can't run forever or spin on a failure.

What's assumed

Modules 1-4 completed. Comfort with loops, arrays, and functions that return different shapes depending on what happened.

How to work through it

  1. Read each definition, then run the matching interactive.

1

From one call to a loop

Every module so far has been a single request: send a prompt (with the right context, the right tools available), get a response. An agent changes the shape of the interaction, instead of one response, the model reasons about a goal, takes an action (usually a tool call), observes the result, and decides whether it's done or needs another step.

Definition: ReAct loop (reason, act, observe)

A control pattern where a model alternates between reasoning about what to do next, taking an action (typically a tool call), and observing the result, repeating until it has enough information to produce a final answer.

Nothing about this pattern is magic, it's a loop, with the model's own text as the thing that decides whether the loop continues. Which means your code, not the model, has to be the thing that guarantees the loop eventually stops.

3

Why a hard step limit is non-negotiable

"The model will know when to stop" is not a control mechanism, it's a hope. Models can reason in circles, misjudge whether they have enough information, or simply fail to emit a clean final-answer signal. Every agent loop needs an explicit, code-enforced maximum number of steps, independent of whatever the model itself thinks.

Definition: step limit

A hard maximum on how many reason-act-observe cycles a loop will execute before forcibly stopping, regardless of whether the model has produced a final answer. A circuit breaker for control flow, not a suggestion.

An unbounded loop is an unbounded bill. Every step is a model call (tokens, cost, latency) plus, often, a tool execution with its own cost or side effects. A loop with no step limit doesn't fail loudly, it just keeps running, and keeps costing, until something external kills it.
Practice check

A step limit is reached before the model produced a final answer. Is that a bug in your loop, or expected, correct behavior?

Check your answer
Expected, correct behavior, assuming the limit is reasonable for the task. Hitting the cap is the loop doing exactly its job: refusing to run forever. The right response is to surface a clear "couldn't complete within the step budget" outcome (to the caller or the user), not to silently pretend it succeeded, and not to treat reaching the limit itself as an error condition to hide.
Practice check

A customer-troubleshooting agent debugging a "can't connect" ticket runs 10 different diagnostics in a row, run_diagnostic("wifi_signal"), run_diagnostic("dns_lookup"), run_diagnostic("dhcp_lease"), and so on, each a different check, and hits the step limit with the issue still unresolved. A second agent, on a different ticket, calls run_diagnostic("dns_lookup") with the exact same argument four times in a row and also hasn't resolved anything. Should both cases be handled the same way, just as "ran out of budget"?

Check your answer
No. The first agent is legitimately working through a hard, multi-step diagnosis, each step is a different action, so it's a step-limit case, and the fix (if this pattern is common) is likely a larger step budget, not a bug. The second agent is issuing the SAME diagnostic with the SAME argument repeatedly, that's the stuck signal from earlier in this module, and it should be cut off well before step limit regardless of how large the budget is, since raising the limit would just mean more identical failed checks, not a better outcome.
4

Three ways a loop can end

A well-bounded agent loop has exactly three possible endings, and your code needs to handle all three distinctly, not collapse them into one generic "done."

Definition: termination conditions

Success: the model emits an explicit final-answer signal, distinct from an ordinary action. Step limit: the cap is reached with no final answer. Stuck: the loop detects it's repeating the same action without progress, and stops early rather than burning the rest of its step budget on a pattern that clearly isn't working.

These three need different handling downstream. A success has an answer to return. A step-limit or stuck outcome doesn't, and pretending it does (returning a partial or fabricated answer as if it were complete) is worse than clearly reporting that the loop didn't finish.

Practice check

Why distinguish "stuck" (repeated action) from "step limit" (ran out of budget) instead of just treating both as "didn't finish, same as each other"?

Check your answer
They point to different problems. Hitting the step limit on a genuinely hard, multi-step task suggests the budget itself might be too small. Getting stuck after 3 identical actions suggests something is actually broken, a tool returning an error the model doesn't know how to act on, or a reasoning dead-end, regardless of how large the step budget is. Logging and alerting on these separately gives you a much better signal for what to actually fix.
Practice check

A research-assistant agent answering "what caused the 2024 CrowdStrike outage" calls web_search with a different query each step, wire, patch, sensor, root cause, timeline, and by step 12 has gathered enough in its reasoning text to write a solid answer. But it never emits the loop's explicit final-answer signal, and step 12 is the configured step limit. Should your loop code treat this as a success, since the material for a good answer is clearly there?

Check your answer
No. Success is defined by the model emitting the explicit final-answer signal, not by whether an outside observer thinks the accumulated observations look sufficient. Your loop has no reliable way to judge "is this good enough" from the outside, that judgment is exactly what the final-answer signal is for. If the model never produces it, this is a step-limit ending: report it as such, don't fabricate a "success" by scraping the last reasoning text for something that looks like an answer.
5

The repeated-failure trap

A model that gets an error back from a tool call doesn't always adjust, sometimes it retries the exact same action, gets the exact same error, and repeats that cycle indefinitely, never making progress but never explicitly failing either. Without a guard, this looks identical to normal operation from the outside: the loop is "running," it just isn't going anywhere.

Detecting "stuck" is a pattern-match, not a guess. The simplest reliable signal is exact repetition: if the model issues the same action (same tool, same arguments) some small number of times in a row, that's a strong signal it's not reasoning its way forward, and the loop should stop rather than let the step limit be the only backstop.
Cross-module check

Module 4's idempotent executor would happily return the SAME cached result for a repeated call with the same ID. Does that make stuck-loop detection unnecessary?

Check your answer
No, they solve different problems, and a repeated call with a NEW call ID each time (which is realistic, an agent re-reasoning about the same action typically generates a fresh call) wouldn't even hit Module 4's cache, idempotency keys off the ID, not the semantic content of the call. Even if it did hit the cache every time, the loop would still be burning steps (and tokens) doing nothing productive. Idempotency protects individual calls from duplicate side effects. Stuck-loop detection protects the loop itself from spinning.
Practice check

A coding agent loops run_tests, observe a failure, apply_patch, run_tests again, six times in a row. Every step calls the tool apply_patch, but the diff argument is different each time, it's genuinely trying a new fix on each iteration. Should stuck-detection flag this as a repeated action because the tool name apply_patch keeps recurring?

Check your answer
No, not if it's matching on tool name alone. The stuck signal defined earlier in this module is exact repetition, same tool AND same arguments, not "the same tool got called again." A coding agent trying six different diffs is taking six different actions that happen to share a tool name, that's iterative debugging, not spinning. If the SAME diff (identical arguments) got submitted twice in a row, that would be the real signal, the model resubmitting a patch that already failed without changing anything. Matching on tool name only would falsely kill a lot of legitimate agent behavior.

Build it: a bounded agent loop

You've seen all three endings, success, step limit, and stuck. Now implement a loop that correctly distinguishes them, and five real tests run against your actual code.

Code exercise · Python, runs in a real sandboxed Python interpreter (Pyodide)

Complete run_agent_loop(initial_state, step, max_steps). Call step(state) each iteration, it returns either {"type": "final", "answer": ...} or {"type": "action", "action": ..., "nextState": ...}. Track actions taken in a trace list (append each action string). If step returns final, return {"status": "success", "answer": ..., "stepsUsed": ..., "trace": trace}. If the SAME action string repeats 3 times in a row, stop immediately and return {"status": "stuck", "stepsUsed": ..., "trace": trace}, don't wait for max_steps. If max_steps is reached with no final answer and no stuck detection, return {"status": "max_steps", "stepsUsed": max_steps, "trace": trace}.

Stuck? Hints
Hint 1 — conceptual
Loop up to max_steps times. Each iteration, call step(state) once. Check its type: if "final," you're done. If "action," record it and check whether it's a repeat of the last action before continuing.
Hint 2 — specific
Keep two variables outside the loop: the last action seen, and how many times in a row it's repeated. Each "action" result, compare it to the last action, if equal increment the repeat counter, if different reset the counter to 1 and update "last action."
Hint 3 — near-solution
Check the repeat counter AFTER appending the current action to trace and updating the counter, if it reaches 3, return the stuck result right there, don't keep looping. If the loop finishes all max_steps iterations without returning, that's your max_steps case, return it after the loop.
Solution — run your code at least once first
def run_agent_loop(initial_state, step, max_steps):
    state = initial_state
    trace = []
    last_action = None
    repeat_count = 0

    for i in range(max_steps):
        result = step(state)

        if result["type"] == "final":
            return {"status": "success", "answer": result["answer"], "stepsUsed": i + 1, "trace": trace}

        trace.append(result["action"])
        if result["action"] == last_action:
            repeat_count += 1
        else:
            last_action = result["action"]
            repeat_count = 1

        if repeat_count >= 3:
            return {"status": "stuck", "stepsUsed": i + 1, "trace": trace}

        state = result["nextState"]

    return {"status": "max_steps", "stepsUsed": max_steps, "trace": trace}
Practice check

Test 4 feeds your loop 4 different actions in a row before a final answer on step 5. If your repeat-detection logic doesn't reset the counter when the action CHANGES, what false failure could this test trigger?

Check your answer
Without resetting on change, an off-by-one counter bug could accumulate across DIFFERENT actions and falsely trigger the stuck condition even though nothing actually repeated, incorrectly cutting off a loop that was making real progress. The counter has to be scoped to "how many times in a row has THIS SPECIFIC action just repeated," which means it must reset to 1 (not 0) the moment a different action appears.

Looking ahead

A bounded loop stops it from running forever. It says nothing about what happens when an individual model call inside that loop fails, times out, or comes back malformed. Module 6 covers making each call itself resilient: retries, backoff, and fallback.

Further reading

If you want to go deeper than the browser can take you:

  • The original ReAct paper (Yao et al.) is the source of the reason-act-observe framing used throughout this module, worth reading directly for the reasoning traces it shows.
  • Production agent frameworks typically add richer stuck-detection than exact repetition, semantic similarity between recent actions, or explicit "no progress" signals from the model itself, at the cost of more complexity.
  • Some architectures use a planner/executor split instead of a single reasoning loop, a separate step decomposes the task into a fixed plan upfront, which sidesteps some (not all) of the unbounded-loop risk by bounding the plan length before execution starts.

Glossary

agent loop / ReAct — a cycle of reasoning, taking an action, and observing the result, repeated until a final answer or a stop condition.
step limit — a hard cap on how many loop iterations run before forcibly stopping.
termination condition — any of the defined ways a loop is allowed to end: success, step limit, or stuck.
stuck loop — a loop repeating the same action without progress, detected and stopped early rather than exhausting the step budget.
trace — the ordered record of actions (and often reasoning) an agent loop produced, used for debugging and for detecting repetition.
