Module 03

Retrieval-Augmented Generation

A model only knows what's in its prompt. Retrieval is the mechanism that decides, out of everything you could put there, which pieces actually get in, by searching, not by hoping the right chunk made the cut.

1

The gap between "in context" and "known"

A model doesn't have access to your documents, your database, or last week's conversation unless those things are physically present in the prompt you send. It has no persistent memory of anything outside that call. If your system needs the model to answer a question about a specific document, that document, or the relevant part of it, has to be in the prompt.

Module 2 assumed you already knew which chunk to include. Real systems don't, they have thousands of chunks and a few thousand tokens of budget. Retrieval is the search step that picks which chunks earn a place in that budget, before generation ever happens.

Retrieval-Augmented Generation (RAG) is exactly this pattern: retrieve the most relevant chunks for a query, then generate an answer using only those chunks as context. The model still only knows what's in the prompt, RAG just gets smarter about what goes in.
2

Embeddings turn meaning into geometry

To search by meaning instead of exact keyword matches, text first gets converted into a list of numbers, a vector, called an embedding. Texts with similar meaning end up as vectors that point in similar directions. Distance and direction in that numeric space become a stand-in for semantic similarity.

Definition: embedding

A vector (list of numbers) produced by a model that represents a piece of text's meaning, positioned so that semantically similar texts have similar vectors. This course treats embeddings as already-computed inputs, generating them is a separate model call this course doesn't need to cover to teach the retrieval logic itself.

What matters for this module isn't how embeddings are produced, it's what you do with them once you have them: measure how similar two vectors are, and rank candidates by that score.

Practice check

Document A's embedding vector is exactly [2, 0]. Document B's is [10, 0]. Both point in the same direction as a query vector [1, 0]. Which document scores higher, and why does this feel surprising if you're thinking about vector length instead of direction?

Check your answer
They score identically, both get a cosine similarity of 1.0 with the query, because cosine similarity divides out magnitude entirely, it only measures the angle between vectors. [10, 0] is five times "longer" than [2, 0], but length never enters the calculation. This is exactly why it's the standard metric for embeddings, you want "same meaning, said more emphatically" to still count as a strong match, not get penalized or rewarded for vector length, which doesn't reliably correspond to anything meaningful.
Practice check

A medical-literature search assistant embeds a query about "first-line treatment for pediatric migraine." Abstract A is a concise 150-word summary with embedding [4, 3]. Abstract B is a repetitive 900-word abstract that restates the same treatment recommendation in nearly every sentence, with embedding [12, 9], three times the magnitude of A, pointing in the exact same direction. Does Abstract B outrank Abstract A because it "says it more"?

Check your answer
No, they score identically. [12, 9] is just [4, 3] scaled by 3, same direction, same cosine similarity to the query. Repeating a claim more times inflates a document's vector length, not its direction, and direction is all cosine similarity measures. A retrieval system that let verbosity win would systematically favor padded, repetitive abstracts over well-written concise ones, exactly the failure mode magnitude-invariance is designed to prevent.

Practice check

The chunk about "resetting a router's factory settings" scores noticeably above zero, even though it's about a completely different topic. Why doesn't a "wrong topic" chunk score exactly zero, and what does that imply about picking a similarity threshold?

Check your answer
Embeddings capture broad semantic and lexical overlap, not topic identity, "reset," "settings," and general troubleshooting phrasing overlap enough to produce a modest positive score even across unrelated domains. A score of exactly 0 (or negative) is rare for ordinary text pairs. This is exactly why top-k alone isn't enough, without a minimum-relevance threshold, a retrieval system will happily return its "least bad" match even when nothing in the collection is actually relevant, and hand the model confidently irrelevant context.
Practice check

A legal case-law lookup assistant searches a small jurisdictional database for precedent on "employer liability when a subcontractor is injured by a third party's equipment on a shared job site." The highest-scoring case in the whole collection comes back at 0.38, well below the 0.6 minimum-relevance threshold the system normally applies. It's still the best match available. Should the assistant return it anyway, since something is better than nothing?

Check your answer
No. "Best available" and "relevant" are different claims, a score of 0.38 means even the top result only weakly resembles the query, likely sharing general negligence or liability language without addressing the actual fact pattern. Handing that case to the model as grounding context risks a fluent, confident answer built on precedent that doesn't really apply, which is worse for a legal-research tool than truthfully reporting that no close match exists. The threshold exists precisely to catch this: rank is not the same as relevance.
5

Top-k, and the threshold that stops junk from getting in

Once every candidate has a similarity score, retrieval is: sort by score descending, take the top k. But top-k alone has a failure mode: if nothing in the collection is actually relevant, top-k still returns something, whatever scored highest among a set of bad matches. A minimum-relevance threshold fixes this, discard anything below a score cutoff, even if that leaves fewer than k results, or none at all.

Definition: top-k retrieval

Ranking all candidates by similarity score and returning only the highest-scoring k of them.

Returning zero results is sometimes the correct answer. A system that always forces k results, even irrelevant ones, into the prompt produces confidently wrong answers grounded in context that doesn't actually apply. "I don't have relevant information for that" is a better outcome than a fluent answer built on a bad match.

Production systems often combine vector similarity with traditional keyword search, hybrid search, since exact terms (product codes, names, acronyms) can matter even when their embedding similarity to a paraphrased query is unremarkable. This course's exercise implements the vector half; the principle (score, filter, sort, limit) is the same either way.

Cross-module check

Module 2's chunker guarantees every word ends up in some chunk. Does retrieval guarantee every chunk ends up in some answer?

Check your answer
No, and it shouldn't. Chunking's job is completeness, don't silently lose content. Retrieval's job is selectivity, don't include irrelevant content just because it exists. Most chunks in a large collection are correctly never retrieved for any given query, that's the system working as intended, not a gap.
Practice check

A codebase Q&A tool retrieves from a large repo with k=3 and min_score=0.5. Five functions come back scored against the query: handleAuth 0.9, formatDate 0.3, padString 0.28, validateAuth 0.55, refreshAuthToken 0.5. An engineer's implementation sorts by score, takes the top 3 (handleAuth, formatDate, padString), then filters that slice down to scores at or above 0.5. It returns one result. What went wrong, and how many results should the query actually return?

Check your answer
It should return three: handleAuth (0.9), validateAuth (0.55), and refreshAuthToken (0.5). Filtering after slicing throws away the slots that irrelevant matches occupied before the relevant ones further down the ranking ever get a chance, formatDate and padString took two of the three available slots despite being below threshold. The fix is the order used in the exercise: filter out everything below min_score first, across the entire scored set, then sort and slice to k. Filtering an already-sliced top-k instead of the full candidate set silently under-returns even when enough relevant results exist.

Build it: cosine similarity + top-k retrieval

You've seen the metric (cosine similarity) and the ranking rule (top-k with a relevance floor). Now implement both, and five real tests run against your actual code.

Code exercise · Python, runs in a real sandboxed Python interpreter (Pyodide)

Complete retrieve_top_k(query_vector, documents, k, min_score). documents is a list of {"id":..., "vector":...} dicts. Return a list of {"id":..., "score":...} dicts, sorted by cosine similarity to query_vector descending, excluding anything with a score below min_score, limited to at most k results. A zero-length vector should score 0 against anything (never raise or produce NaN).

Stuck? Hints
Hint 1 — conceptual
Break it into two pieces: a helper that scores one query vector against one document vector, and a second step that scores every document, filters, sorts, and slices. Don't try to do all four at once in one loop.
Hint 2 — specific
Cosine similarity of vectors a and b: dot product divided by (magnitude of a times magnitude of b). Dot product is the sum of a[i] * b[i] across matching indices. Magnitude is the square root of the sum of each vector's own squared components (Python's math.sqrt).
Hint 3 — near-solution
If either magnitude is 0 (a zero vector), return a score of 0 immediately for that pair, don't divide by zero. After scoring every document, filter out anything with score < min_score, sort the rest descending by score using sorted(..., key=..., reverse=True), then slice with [:k].
Solution — run your code at least once first
import math

def cosine_similarity(a, b):
    dot = sum(a[i] * b[i] for i in range(len(a)))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(x * x for x in b))
    if norm_a == 0 or norm_b == 0:
        return 0
    return dot / (norm_a * norm_b)

def retrieve_top_k(query_vector, documents, k, min_score):
    scored = [
        {"id": doc["id"], "score": cosine_similarity(query_vector, doc["vector"])}
        for doc in documents
    ]
    filtered = [d for d in scored if d["score"] >= min_score]
    filtered.sort(key=lambda d: d["score"], reverse=True)
    return filtered[:k]
Practice check

Test 5 feeds your function a document whose vector is [0, 0]. If your cosine similarity helper divides by the magnitude without checking for zero first, what happens, and why is a crash worse here than a wrong-but-valid score?

Check your answer
Dividing by a magnitude of 0 produces NaN, not an error necessarily, but a value that then breaks every downstream comparison silently, NaN < minScore is always false, so a broken score can slip past your filter instead of being caught. Guarding for a zero magnitude and returning a defined score of 0 keeps every later comparison well-behaved, this is the same "never let a bad value propagate silently" discipline from Module 1's structured-output repair.

Further reading

If you want to go deeper than the browser can take you:

  • Real embedding models (and the vector databases built around them) use approximate nearest-neighbor search (e.g. HNSW) to find top-k matches across millions of vectors without comparing against every single one, this course's exercise does a full linear scan, which is correct but doesn't scale past a small collection.
  • Hybrid search (combining vector similarity with keyword/BM25 scoring) is standard in production RAG systems specifically because embeddings can miss exact-term matches that keyword search catches easily.
  • Re-ranking, a second, more expensive relevance pass applied only to the top-k candidates from a cheap first pass, is a common way to improve precision without paying the cost of expensive scoring on the entire collection.

Glossary

embedding — a vector representing a piece of text's meaning, positioned so similar meanings produce similar vectors.
cosine similarity — a score from -1 to 1 measuring the angle between two vectors, ignoring their length.
top-k retrieval — returning only the k highest-scoring candidates from a ranked search.
relevance threshold — a minimum similarity score below which a candidate is excluded, even if it would otherwise make the top-k.
hybrid search — combining vector similarity with keyword search to catch exact-term matches embeddings alone can miss.
