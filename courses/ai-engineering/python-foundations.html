Variables, types, and numbers

Why this matters here

Module 2 is entirely about counting: how many tokens does a piece of text cost. That's arithmetic on a variable, nothing more, but if you're not fluent with Python's basic types first, the arithmetic itself becomes the obstacle.

A variable is a name pointing at a value. Python figures out the type from the value itself, you don't declare it up front.

Concept: core types

int (whole numbers), float (decimals), str (text), bool (True/False). len(x) returns the length of a string, list, or dict. // is integer (floor) division, it drops any remainder, which matters when you're estimating a whole number of tokens.

text = "Reset your password from Settings."
char_count = len(text)          # 35
approx_tokens = char_count // 4  # 8  (floor division, no remainder)
print(approx_tokens)
Practice check

Why floor division (//) instead of regular division (/) for a token estimate?

Check your answer
A token count has to be a whole number, you can't have "7.25 tokens." Regular division would give a float; floor division gives a clean integer, matching what a real token count actually is.

Strings and basic pattern matching

Why this matters here

Module 1 opens with a real, common failure: a model wraps its JSON answer in a markdown code fence. Before you can parse that as JSON, you have to strip the fence off as a plain string operation.

Python strings support slicing, methods like .strip() and .startswith(), and the re module for pattern matching when a fixed check isn't enough.

Concept: regex for structural stripping

re.match(pattern, text) tests whether text starts with a match for pattern and gives you access to captured groups. match.group(1) returns whatever the first (...) in the pattern captured.

import re

raw = '```json\n{"status": "ok"}\n```'
m = re.match(r"^```(?:json)?\s*([\s\S]*?)\s*```$", raw)
inner = m.group(1) if m else raw.strip()
print(inner)   # {"status": "ok"}
Practice check

What should your function do if the text ISN'T wrapped in a fence at all?

Check your answer
Return the text unchanged (just stripped of surrounding whitespace). A fence-stripping function shouldn't assume every input has a fence, plenty of valid model output won't.
Code exercise · Python, runs in a real sandboxed Python interpreter (Pyodide)

Complete strip_code_fence(text). If text is wrapped in a markdown code fence (with or without a language tag like json), return only the content inside. Otherwise, return text.strip() unchanged.

Stuck? Hints
Hint 1
Use re.match(r"^```(?:\w+)?\s*([\s\S]*?)\s*```$", text.strip()). If it matches, return group(1). If not, return text.strip().
Solution — run your code at least once first
import re

def strip_code_fence(text):
    stripped = text.strip()
    m = re.match(r"^```(?:\w+)?\s*([\s\S]*?)\s*```$", stripped)
    if m:
        return m.group(1)
    return stripped

Lists and iteration

Why this matters here

Module 2's chunker splits a document into pieces that fit a token budget. Before tackling that token-aware version, get comfortable with the simpler idea underneath it: splitting a list into fixed-size groups.

A Python list is an ordered, mutable sequence. list[start:end] slices it; .append(x) adds to the end.

Concept: building a list of lists

A common pattern: start with an empty result list, loop over your input in fixed-size steps, and .append() each slice as its own sub-list.

items = [1, 2, 3, 4, 5]
size = 2
batches = []
for i in range(0, len(items), size):
    batches.append(items[i:i + size])
print(batches)   # [[1, 2], [3, 4], [5]]
Practice check

What does items[i:i+size] return when i+size goes past the end of the list?

Check your answer
Python slicing never raises an out-of-range error, it just returns whatever is left, even if that's fewer than size items (or an empty list). This is why the last batch above has only 1 item, not a crash.
Code exercise · Python, runs in a real sandboxed Python interpreter (Pyodide)

Complete batch(items, size). Split items into a list of lists, each with at most size items, preserving order. An empty input returns an empty list.

Stuck? Hints
Hint 1
Loop with for i in range(0, len(items), size), appending items[i:i+size] each time.
Solution — run your code at least once first
def batch(items, size):
    result = []
    for i in range(0, len(items), size):
        result.append(items[i:i + size])
    return result

Dictionaries

Why this matters here

Nearly everything an AI system configures, model parameters, tool schemas, retrieval settings, is a dict. A common pattern across every module ahead: start from sane defaults, then let a caller override just the parts they care about.

A dict maps keys to values. {**a, **b} builds a new dict by unpacking a first, then b, so b's keys win on any overlap, without mutating either original dict.

Concept: non-destructive merging

Mutating a shared defaults dict in place is a common bug, the next caller gets a defaults dict that's no longer default. Building a NEW dict avoids that entirely.

defaults = {"temperature": 0.7, "max_tokens": 500}
overrides = {"max_tokens": 1000}
config = {**defaults, **overrides}
print(config)          # {'temperature': 0.7, 'max_tokens': 1000}
print(defaults)         # unchanged: {'temperature': 0.7, 'max_tokens': 500}
Practice check

Why does defaults stay unchanged after building config?

Check your answer
{**defaults, **overrides} creates a brand-new dict, it reads from both inputs but writes to neither. Contrast with defaults.update(overrides), which WOULD mutate defaults in place, a common source of bugs when the same defaults dict is reused across calls.
Code exercise · Python, runs in a real sandboxed Python interpreter (Pyodide)

Complete merge_config(defaults, overrides). Return a new dict combining both, with overrides winning on any shared key. Never mutate either input dict.

Stuck? Hints
Hint 1
Return {**defaults, **overrides} directly.
Solution — run your code at least once first
def merge_config(defaults, overrides):
    return {**defaults, **overrides}

Conditionals, loops, and sorting

Why this matters here

Module 3's whole job is retrieval: score every candidate, throw out the irrelevant ones, keep only the best few. That's a filter, a sort, and a slice, the exact combination this topic builds.

sorted(iterable, key=..., reverse=True) returns a new sorted list without changing the original. A list comprehension like [x for x in items if condition] filters in one line.

Concept: filter, sort, then limit, in that order

Filtering AFTER sorting (or slicing before filtering) can silently drop a result that should have made the cut. The safe order is always: score everything, filter out what doesn't qualify, sort what's left, then take only as many as you need.

docs = [{"id": "a", "score": 0.9}, {"id": "b", "score": 0.2}, {"id": "c", "score": 0.6}]
qualified = [d for d in docs if d["score"] >= 0.4]
ranked = sorted(qualified, key=lambda d: d["score"], reverse=True)
top2 = ranked[:2]
print(top2)   # [{'id': 'a', 'score': 0.9}, {'id': 'c', 'score': 0.6}]
Practice check

Why filter by the minimum score BEFORE slicing to the limit, rather than after?

Check your answer
Slicing first (say, taking the top 2 by score, then checking if they clear the threshold) can leave you with fewer than you should have, or wrongly include a low scorer if you slice before sorting. Filtering first guarantees every candidate you keep already qualifies, however many end up in the final slice.
Code exercise · Python, runs in a real sandboxed Python interpreter (Pyodide)

Complete top_matches(docs, min_score, limit). docs is a list of {"id":..., "score":...} dicts. Return the qualifying docs (score >= min_score), sorted by score descending, limited to at most limit results.

Stuck? Hints
Hint 1
Filter with a list comprehension, sort with sorted(..., key=lambda d: d["score"], reverse=True), then slice with [:limit].
Solution — run your code at least once first
def top_matches(docs, min_score, limit):
    qualified = [d for d in docs if d["score"] >= min_score]
    ranked = sorted(qualified, key=lambda d: d["score"], reverse=True)
    return ranked[:limit]

Functions and handling failure with try/except

Why this matters here

Module 7's eval harness has one hard rule: a single broken test case can never crash the whole evaluation run. That discipline starts here, with the basic shape of a function that fails safely instead of taking the whole program down with it.

A function that might fail should say so through its return value, not by letting an exception escape uncaught. try/except catches an error and lets you decide what happens next.

Concept: try/except

try: wraps code that might raise. except Exception as e: catches it, e is the exception object, str(e) gives its message. Code inside except runs only if the try block actually raised.

def safe_score(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        return None

print(safe_score(10, 2))   # 5.0
print(safe_score(5, 0))    # None, no crash
Practice check

What would happen to a caller looping over many (a, b) pairs if safe_score DIDN'T catch the exception?

Check your answer
A single b=0 pair anywhere in the loop would raise, uncaught, and crash the ENTIRE loop, losing every result computed so far, not just the one bad pair. This is exactly the "one bad input shouldn't take down the whole batch" principle that shows up again in Module 4's tool executor and Module 7's eval harness.

Working with JSON

Why this matters here

Every model API speaks JSON. Module 1's entire premise is that a model's JSON-shaped output can't be trusted until it's actually been parsed and validated, starting with just getting json.loads() to succeed.

Python's built-in json module converts between JSON text and Python objects. json.loads(text) parses text into a dict/list/etc; json.dumps(obj) does the reverse.

Concept: json.loads() raises on invalid input

Malformed JSON doesn't return None, it raises json.JSONDecodeError. If you want a function that never crashes on bad input, you have to catch that explicitly.

import json

print(json.loads('{"status": "ok"}'))   # {'status': 'ok'}
print(json.loads('[1, 2, 3]'))          # [1, 2, 3]
try:
    json.loads("not json at all")
except json.JSONDecodeError as e:
    print("failed:", e)
Practice check

Why is returning None on failure better than letting json.JSONDecodeError propagate out of your own function?

Check your answer
A caller expecting "either parsed data or a clear signal it failed" can check if result is None and handle it gracefully. An uncaught exception instead forces every single caller to wrap every single call in its own try/except, or risk a crash, exactly the repair-then-validate discipline Module 1 builds on.
Code exercise · Python, runs in a real sandboxed Python interpreter (Pyodide)

Complete parse_or_none(text). Try json.loads(text) and return the result. If it raises, catch the exception and return None instead.

Stuck? Hints
Hint 1
Import json, wrap json.loads(text) in try/except catching Exception (broad is fine here), return None on failure.
Solution — run your code at least once first
import json

def parse_or_none(text):
    try:
        return json.loads(text)
    except Exception:
        return None

Async functions: the shape of a model API call

Why this matters here

Every real model API call is asynchronous, your code sends a request and waits for a response without freezing everything else. Module 6's entire retry-and-fallback system is built from async def functions and await. This is the minimum shape you need before that module.

async def defines a function that can be awaited. Inside an async function, await some_async_call() pauses until that call finishes, without blocking anything else.

Concept: trying calls in order until one works

A common async pattern (and the direct precursor to Module 6's fallback logic): try a list of async operations one at a time, and use the first one that succeeds, catching failures along the way instead of stopping at the first error.

async def fetch_first_success(calls):
    for call in calls:
        try:
            return await call()
        except Exception:
            continue
    return None

# calls is a list of async functions with no arguments, e.g.:
# async def primary(): raise Exception("down")
# async def backup(): return "backup result"
# await fetch_first_success([primary, backup])  ->  "backup result"
Practice check

If EVERY call in the list raises, what should fetch_first_success return, and why not let the last exception propagate?

Check your answer
It should return None (a clear, structured "nothing worked" signal), not let an exception escape. This is the exact same "never let this function raise, report failure through the return value" discipline from topics 6 and 7, now applied to async code, and it's precisely what Module 6's call_with_retry_fallback builds on directly.
