Course description

Most "AI engineering" content teaches you which library call wraps which API. This course teaches the engineering judgment underneath that call: why a model's output needs to be validated before you trust it, how to budget a context window instead of guessing, when retrieval actually helps versus when it just adds noise, how to make a tool call safe to retry, how to keep an agent loop from running forever, how to keep a flaky model API from taking your whole system down, and how to know, with a number, whether a change actually helped.

You will finish able to design, implement, and debug a small production-shaped AI system end to end, not just write a prompt that worked once in a demo.

Why this bar, not a prompt-engineering bar: a clever prompt can stop working the day a model is updated. The engineering discipline in this course, schema validation, token budgeting, relevance thresholds, idempotent execution, bounded control flow, retry logic, systematic evaluation, does not expire when the next model ships. It is what separates a prompt-tinkerer from an engineer a team trusts to build on top of a language model in production.
Prerequisite: basic programming fundamentals (variables, functions, loops, conditionals) in any language No prior Python required, Python Foundations teaches it from the ground up before Module 1 No prior agent-framework or vector-database experience required

Learning outcomes

Trustworthy output

Repair and validate model output against a schema before any downstream code acts on it, instead of assuming a requested format was actually produced.

Budget-aware context

Compute a token budget from a context window and reserved output, and chunk content without ever silently dropping it.

Relevant retrieval

Implement cosine-similarity retrieval with a minimum-relevance threshold, so "best available" doesn't get mistaken for "actually relevant."

Safe, bounded execution

Execute tool calls idempotently and run agent loops with a hard step limit and stuck-loop detection, so nothing runs, or costs, unboundedly.

Module sequence

Each module pairs a concept with an interactive you manipulate directly, and closes with a graded checkpoint plus a real, Worker-sandboxed hands-on code exercise. Module 0 and Module 1 are both open for preview.

The sequence isn't seven unrelated topics, it's one system, built up in order: control what the model says, give it real knowledge, give it real actions, keep those actions bounded, keep the whole thing running when something breaks, and prove, with a number, that it actually works.

Stage 1 · Control the model
MODULE 01

Prompting & Structured Outputs

Preview open →

A model produces text, not guaranteed data. This module covers prompt anatomy, the repair-then-validate pattern for malformed JSON, and why "asked for a schema" isn't the same as "got the schema."

You will be able to
  • Spot the specific ways model output deviates from a requested structure
  • Apply the repair-then-validate order: strip fences, fix trailing commas, parse, then validate
  • Implement a structured-output validator/repair function, tested against 5 real cases
▶ interactive: spot the malformed output
Stage 1 · Control the model
MODULE 02

Context Windows & Token Economics

Every prompt has a budget, measured in tokens. This module covers the token/character relationship, computing available input budget, why naive truncation is a silent-failure bug, and chunking with overlap.

You will be able to
  • Compute available input budget from a context window and reserved output
  • Explain why naive truncation silently discards content, and what chunking fixes
  • Implement a token-budget-aware chunker with overlap, tested against 5 real cases
▶ interactive: live token-budget calculator
Stage 2 · Give it knowledge
MODULE 03

Retrieval-Augmented Generation

A model only knows what's in its prompt. This module covers embeddings, cosine similarity, top-k retrieval, and why a minimum-relevance threshold is what stops "best available" from becoming "confidently wrong."

You will be able to
  • Explain why cosine similarity ignores vector magnitude, and why that's correct
  • Reason about when a relevance threshold should exclude a "best" match entirely
  • Implement cosine similarity and threshold-aware top-k retrieval, tested against 5 real cases
▶ interactive: cosine-similarity slider + rank-the-chunks exercise
Stage 3 · Give it tools
MODULE 04

Tool Use & Function Calling

A tool call is a proposal from the model, not an action, until your code executes it. This module covers schema validation before execution and idempotent execution that survives a retried request.

You will be able to
  • Validate a tool call's name and required arguments before the handler ever runs
  • Explain why a failed attempt must stay retryable while a success must not re-run
  • Implement an idempotent tool executor, tested against 5 real cases
▶ interactive: spot the tool call that shouldn't execute
Stage 4 · Control the agent
MODULE 05

Agent Architectures & Control Flow

An agent loop's stopping condition is not guaranteed by the model. This module covers the reason-act-observe cycle, hard step limits, and detecting a loop that's repeating itself without progress.

You will be able to
  • Distinguish success, step-limit, and stuck as three separate loop endings
  • Explain why idempotency alone doesn't bound a loop's total iterations
  • Implement a bounded agent loop with stuck-detection, tested against 5 real cases
▶ interactive: step through a real agent trace
Stage 5 · Make it reliable
MODULE 06

Reliability for LLM Systems

Model APIs fail transiently and permanently, and the correct response differs. This module covers retryable-vs-not classification, exponential backoff with full jitter, and a single bounded fallback.

You will be able to
  • Classify an error as retryable or non-retryable and explain why the distinction matters
  • Explain the retry-storm problem full jitter solves
  • Implement retry-with-bounded-fallback logic, tested against 5 real cases
▶ interactive: exponential backoff with full jitter calculator
Stage 6 · Prove it works
MODULE 07

Evaluation, Testing & Observability

"It looked fine" isn't evaluation. This module covers designing checkable test cases, deterministic checks versus LLM-as-judge, and regression detection against a recorded baseline.

You will be able to
  • Design an eval test case with an explicit, checkable criterion
  • Explain when to prefer a deterministic check over LLM-as-judge scoring
  • Implement a deterministic eval harness with regression detection, tested against 5 real cases
▶ interactive: spot the usable eval test case
Stage 7 · Build the system
MODULE 08

Capstone: A Production AI Agent

Synthesis. A client brief: a support bot that must answer from a knowledge base, act on tools safely, and survive a flaky model API. You submit a design document, a working implementation, and a debugging diagnosis, graded against a rubric, not vibes.

Deliverable
  • A written design specification applying all seven prior modules
  • A working implementation of the critical path (retrieval threshold + idempotent tool execution)
  • A diagnosis of a real reliability bug in code you didn't write
