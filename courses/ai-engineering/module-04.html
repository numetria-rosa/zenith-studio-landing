Module 04

Tool Use & Function Calling

A model can only produce text. Everything it does beyond that, looking something up, sending an email, charging a card, happens because a tool call it generated got executed by your code. That execution step is where correctness and safety actually live.

Learning objectives
  • Explain what a tool call actually is, and why the model never directly does anything itself
  • Validate a model-generated tool call against a schema before ever executing it
  • Explain why tool execution must be idempotent, and what specifically can go wrong if it isn't
  • Implement a tool executor that validates arguments, executes safely, and never double-runs a retried call
Before you start

What this module assumes

Modules 1-3 were about getting good input into a model and good context alongside it. This module is about the model taking real action, calling a function, hitting an API, running a query, and everything that can go wrong once "the model decided to do something" becomes "code actually did it."

What's new

The trust boundary flips. Modules 1-3 validated what came OUT of a model. This module validates what a model wants to DO before your code lets it happen, and handles what occurs when the same request arrives twice.

What's assumed

Modules 1-3 completed. Comfort with objects, functions as values, and try/catch.

How to work through it

  1. Read each definition, then run the matching interactive.
  2. Answer the practice check before revealing the answer.
  3. Finish with the graded checkpoint.
1

The model doesn't do anything. Your code does.

When a model "calls a tool," it doesn't execute code, send a network request, or touch a database. It produces text, a structured description of what it wants to happen: a tool name and a set of arguments. Your code reads that description, decides whether to trust it, and only then actually does the thing.

Definition: tool call

A structured request produced by a model, naming a specific tool and providing arguments for it, e.g. { name: "get_weather", arguments: { location: "Paris" } }. It's a proposal, not an action, until your code executes it.

This distinction matters because it means every tool call is, structurally, the same kind of thing as Module 1's raw model output: text that claims a certain shape, generated by a system that can be wrong, and that must be checked before you act on it.

Practice check

One of the calls above has a syntactically valid, correctly-typed amountCents that's still worth rejecting: a refund of $50,000 on an order that (per your system) never exceeds $500. Schema validation alone wouldn't catch this. What kind of check would?

Check your answer
A business-rule / bounds check, separate from schema validation. Schema validation confirms the SHAPE is right (a number is present where a number is expected), it says nothing about whether that number makes sense for this specific order. Production tool executors typically layer both: schema validation for structural correctness, then domain-specific checks (amount limits, permission checks, rate limits) before anything with real-world consequences actually runs.
3

Never execute an unvalidated call

A model can hallucinate a tool name that doesn't exist, omit a required argument, or produce the wrong type for one, the same way it can produce malformed JSON in a plain text response. The fix is the same discipline as Module 1: validate before you use it, and fail with a clear, structured error instead of letting a bad call crash your handler or silently do the wrong thing.

An unvalidated tool call is a trust boundary, not a formality. If the tool executes a database write, sends money, or calls an external API, a missing or malformed argument reaching the handler isn't a cosmetic bug, it's the difference between "the model asked for something odd" and "something odd actually happened."
Practice check

Should validation errors be silently logged and the call dropped, or reported back to the model as part of the conversation?

Check your answer
Reported back to the model, as a structured error it can read and react to, the same "surface it, don't hide it" principle from Module 1's repair pass. A model that gets a clear "missing required argument: orderId" can often correct itself and retry with a valid call. A model that gets silence, or a generic failure, has no way to know what went wrong or how to fix it.
Practice check

A CRM's update_customer_record(customerId: string, fields: object) tool has a schema that only lists customerId as required, it says nothing about what's allowed inside fields. A model-generated call arrives with fields: { plan: "enterprise", accountBalanceCents: 500000 }, and accountBalanceCents isn't something any legitimate caller of this tool should ever be able to set directly. Does "the required field is present with the correct type" mean this call is safe to execute?

Check your answer
No. A schema that only checks for required fields is validating the minimum, not the maximum, it says nothing about which extra fields are allowed to ride along. This is the same class of bug as mass-assignment vulnerabilities in web forms: an object gets passed straight through to a database write, and any key that happens to match a real column gets applied, whether or not the caller should have been able to set it. The fix is an explicit allowlist of permitted keys inside fields, checked as part of schema validation, not left for the handler to notice (or not notice) after the fact.
4

The same call can arrive twice

Networks time out. Clients retry. A model's own reasoning loop can re-emit a call it already made. Whatever the cause, your tool executor has to assume the exact same tool call, same name, same arguments, same call ID, might arrive more than once. If the tool has a side effect (charging a card, sending an email, incrementing a counter), executing it twice is a real bug, not a harmless redundancy.

Definition: idempotent execution

Guaranteeing that executing the same call (identified by a stable ID) more than once produces the same result as executing it once, by detecting the repeat and returning the original outcome instead of re-running the side effect.

This is the same core idea Automation Engineering's idempotency module covered for webhooks and retried requests, applied here to model-issued tool calls instead of external event delivery. The mechanism is the same: track which call IDs have already run, and short-circuit repeats.

Practice check

A payment tool call with ID call_88 succeeds server-side, but the response is lost to a network blip before the model receives it. The model, seeing no confirmation, retries with the same call ID. What should your executor do, and what would go wrong if call IDs weren't tracked at all?

Check your answer
It should recognize call_88 as already-executed and return the original cached result, without charging the card again. Without ID tracking, the executor has no way to distinguish "a genuinely new request" from "the same request arriving again after a lost response," and would run the handler twice, in this case, double-charging a customer for one transaction, exactly the failure mode idempotency keys exist to prevent.
Practice check

A scheduling assistant issues book_appointment(providerId, slot) with call ID call_sched_14 requesting the 2pm slot. It times out waiting for a response and retries, same call ID, but this time the arguments ask for the 3pm slot instead, the model changed its mind between the two attempts while reusing the ID. Should the executor treat this as a normal repeat and return whatever got booked the first time?

Check your answer
No, and this is a distinct failure mode from the payment example above. Idempotency assumes a repeated call ID means "the exact same request, arriving again." Here the ID is the same but the arguments aren't, that's not a retry, it's a collision, two different logical requests accidentally sharing one identifier. Silently returning the cached 2pm result would book the wrong slot without anyone knowing; silently executing the 3pm booking would defeat the point of tracking the ID at all. The correct move is to detect the mismatch and reject the second call with an error (the same call ID was reused with different arguments), the same discipline Stripe's idempotency keys enforce: an ID can only ever be bound to one specific request body.
5

A failed attempt should still be retryable

Idempotency protects against re-running something that already succeeded. It should NOT block a legitimate retry of something that failed, if the handler threw an error and no side effect happened, the model retrying with the same call ID should get a real second attempt, not a cached failure it can never recover from.

Cache successes, not failures. Only mark a call ID as "done" once the handler actually completes successfully. A failed attempt should leave the door open for exactly one more real try, that distinction is what makes an idempotent executor useful instead of just a call that permanently breaks after one transient error.
Cross-module check

Module 6 (later in this course) covers retrying failed model calls with backoff. Is a retried tool call, after a handler failure, the same kind of retry?

Check your answer
Conceptually yes, both are "the same logical operation, attempted again after a failure," and both need the same guarantee: a retry should be safe, not double the side effects. Module 6's focus is deciding WHEN and HOW MANY times to retry a failing call. This module's focus is making sure that WHEN a retry happens, whether initiated by your code or by the model, it doesn't cause harm if the original attempt actually succeeded.
Practice check

A sales-outreach agent's send_email(leadId, template) call times out waiting for the mail provider's response. The request may have reached the provider and actually sent the email, or it may have died before it got there, the executor genuinely has no way to tell which happened. Per this section's "cache successes, not failures" rule, is it automatically safe to leave this call ID retryable?

Check your answer
Not automatically, and this is the gap the rule glosses over. "Cache successes, not failures" assumes your executor KNOWS whether the side effect happened, a clean exception before any network call went out is unambiguous. A timeout on the response is a third case: the request may have landed. Marking it retryable risks a duplicate email exactly the way caching a real success would risk a duplicate charge. Production systems handle this by pushing the idempotency key down to the provider itself, most transactional email and payment APIs accept a client-generated key and deduplicate on their end, so a retry is safe even when your own executor is genuinely uncertain what happened on the first attempt.
6

Build it: an idempotent tool executor

You've seen the two failure modes: executing an invalid call, and executing a valid call twice. Now implement an executor that guards against both, and five real tests run against your actual code.

Code exercise · Python, runs in a real sandboxed Python interpreter (Pyodide)

Complete execute_tool(call, registry, seen). call is a dict {"id":..., "name":..., "arguments":...}. registry maps tool names to {"schema": {"required": [...]}, "handler": fn(args)}. seen is a plain dict you use to remember completed call IDs, mutate it directly. Return {"ok": True, "result": ...} or {"ok": False, "error": "..."}, never raise. Unknown tool names and missing required arguments must be rejected before the handler runs. A repeated call["id"] must return the cached result without calling the handler again. A handler that raises must not be cached, so a later retry with the same ID gets a real second attempt.

Stuck? Hints
Hint 1 — conceptual
There are three gates a call has to pass, in order: does the tool exist, are all required arguments present, has this exact call ID already succeeded. Only after all three does the handler actually run.
Hint 2 — specific
Look up registry[call["name"]] first, if missing, return an error immediately. Then loop over tool["schema"]["required"] and check each field exists in call["arguments"]. Then check seen[call["id"]], if it's already set, return it directly without calling the handler.
Hint 3 — near-solution
Wrap the handler call in try/except. On success, build {"ok": True, "result": ...}, store it in seen[call["id"]], then return it. On except, return {"ok": False, "error": str(e)} WITHOUT touching seen, that's what keeps a failed attempt retryable.
Solution — run your code at least once first
def execute_tool(call, registry, seen):
    tool = registry.get(call["name"])
    if not tool:
        return {"ok": False, "error": "Unknown tool: " + call["name"]}

    required = (tool.get("schema") or {}).get("required", [])
    for field in required:
        if not call.get("arguments") or field not in call["arguments"]:
            return {"ok": False, "error": "Missing required argument: " + field}

    if seen.get(call["id"]):
        return seen[call["id"]]

    try:
        outcome = {"ok": True, "result": tool["handler"](call["arguments"])}
    except Exception as e:
        return {"ok": False, "error": str(e)}

    seen[call["id"]] = outcome
    return outcome
Practice check

Test 5 calls a handler that raises on its first invocation and succeeds on its second, using the same call ID both times. If your code caches the result object BEFORE calling the handler (instead of after), what breaks?

Check your answer
Caching before calling the handler means you'd have to cache something before you know if it succeeded, which either forces you to guess, or forces a second write to overwrite it after the fact, and if that second write is skipped on the error path, a failed attempt gets permanently marked as "done" anyway. The safe order is: try the handler, and only write to seen inside the success path, after the handler has actually returned without raising.

Further reading

If you want to go deeper than the browser can take you:

  • Most model providers' tool/function-calling APIs let you supply a JSON Schema per tool directly, letting the model see the exact shape expected often reduces malformed calls before validation even runs, though it never eliminates the need for it.
  • Idempotency keys are a standard pattern in payment APIs (Stripe, for example) for exactly this reason, client-generated unique IDs that let a server safely deduplicate retried requests.
  • Beyond schema and business-rule validation, production tool executors often add permission checks (can this caller invoke this tool at all) and rate limits, both are extensions of the same "validate before executing" principle.
10

Glossary

tool call — a structured request from a model naming a tool and providing arguments; a proposal, not an executed action.
tool schema — a definition of a tool's expected arguments, used to validate a call before execution.
idempotent execution — guaranteeing a repeated call (same ID) produces the same result as the first, without re-running its side effects.
idempotency key — a stable identifier used to detect and deduplicate repeated executions of the same logical request.
business-rule validation — domain-specific checks (limits, permissions) applied after schema validation, since a structurally valid call can still be unsafe to execute.
