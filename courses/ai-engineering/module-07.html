Module 07

Evaluation, Testing & Observability

"I tried a few prompts and it looked good" isn't evaluation, it's a vibe check on a handful of lucky examples. Every system this course has built needs a systematic way to measure whether it's actually working, and whether a change made it better or worse.

Learning objectives
  • Explain why an ad hoc "looks good" check doesn't substitute for a systematic eval
  • Design labeled eval test cases with an explicit, checkable criterion each
  • Explain the tradeoffs of LLM-as-judge scoring versus deterministic, rule-based checks
  • Implement an eval harness that scores outputs against test cases and flags regressions against a baseline
Before you start

What this module assumes

Every module so far built a piece of a system: structured output, context management, retrieval, tools, an agent loop, reliability. None of them told you how to know, systematically, whether the whole thing is actually working, or whether your last change made it better or worse.

What's new

1

"It looked fine" is not an evaluation

Reading a handful of outputs and judging them by eye feels like evaluation, but it isn't systematic: it's not repeatable, it's biased toward whatever examples you happened to try, and it gives you no way to compare two versions objectively. If someone asks "is the new prompt better than the old one," a shrug and "seemed about the same" isn't an answer a production system can be built on.

Definition: evaluation (eval)

A systematic, repeatable process for scoring a system's outputs against a fixed set of test cases with defined criteria, producing a number (or set of numbers) that can be compared across versions, prompts, or models.

The point isn't to reach 100%, real tasks are often genuinely hard and some failure rate is expected. The point is having a number you trust enough to notice when it changes.

Practice check

One of the cases above has an input but no defined pass/fail criterion at all, just an implicit "and then judge if it's good." Why can't that case be scored consistently, even by a careful human?

Check your answer
Without an explicit criterion, "good" is being redefined by whoever's looking at it in the moment, one reviewer might weight brevity, another might weight completeness, and the SAME reviewer might judge it differently on a different day. A usable eval case needs the criterion decided in advance and written down, exactly what Module 1's schema validation did for structured output, define correctness before you check it, not while you're checking it.
Practice check

A team building a sales-email personalization agent writes this test case: input is a prospect's job title and company name, expected is left blank, and the criterion is "check that the email feels personalized instead of generic." Rewrite the criterion as something a script could actually check, without a second model call.

Check your answer
"Feels personalized" is exactly the implicit, undefined judgment call this section warns about, two reviewers (or the same one on two days) could disagree. A checkable version replaces the feeling with a fact: does the output CONTAIN the prospect's exact job title and company name from the input, AND does it NOT contain any phrase from a fixed list of generic openers ("I hope this finds you well", "I came across your profile"). Both halves are exact-match / substring checks a script can run identically every time, no judgment required.
3

LLM-as-judge: useful, but not free of the problem it's solving

For genuinely subjective criteria (tone, helpfulness, coherence) where no exact-match rule applies, it's tempting to use a second model call to grade the first model's output. This works, up to a point, but it inherits the same unreliability as everything else this course has covered about model output: the judge can be inconsistent, biased toward certain phrasing styles, or simply wrong, and its grading is itself an unverified model output.

A judge that scores inconsistently is worse than no automated score at all. If the same output can get a 6 or an 8 from the judge model on different runs, that noise can mask a real regression, or manufacture a fake one, defeating the entire purpose of having a repeatable number to trust.
Practice check

Given the reliability concerns, when should LLM-as-judge scoring actually be used, versus avoided in favor of something else?

Check your answer
Reserve it for criteria that genuinely have no deterministic check, subjective quality dimensions like tone or helpfulness where "correct" isn't a fixed string or structure. Anything that CAN be checked deterministically (does the output parse as valid JSON, does it contain a required field, does it match an expected value) should be, deterministic checks are consistent, cheap, and fast, exactly the properties LLM-as-judge lacks.
4

Prefer deterministic checks wherever they apply

A deterministic check, exact match, schema validation (Module 1), a numeric comparison against a known-correct value, produces the same result every time it's run against the same output. It costs nothing beyond running some code, and it's exactly reproducible, which makes it the strongest possible foundation for an eval suite wherever the task allows it.

Definition: deterministic check

A pass/fail (or scored) criterion evaluated by fixed logic, not by another model call, producing identical results on identical input every time it runs.

Most real eval suites are a mix: deterministic checks for anything with a defined correct answer or shape, LLM-as-judge only for what genuinely can't be checked any other way. Leaning as far as possible toward deterministic checks is the version of this module's discipline that costs the least and gives the most trustworthy numbers.

Cross-module check

Module 1's structured-output validator already IS a deterministic check (does the output parse and match the schema). Does that mean structured-output tasks don't need a separate eval suite?

Check your answer
They still need one, for a different reason: Module 1's validator checks a SINGLE output at the moment it's produced, in production, live. An eval suite runs that same kind of check (and others) across a whole labeled test set, repeatably, specifically to compare versions and catch regressions over time. Reusing the Module 1 validation logic AS one of the eval's deterministic checks is exactly the right move, but the eval suite is the thing that turns "this one output was valid" into "94% of our test set passes, versus 91% last week."
Practice check

A document-classification pipeline sorts inbound files into a fixed set of labels: invoice, contract, resume, other. Every test case in the eval set already has a known correct label attached. Should scoring this use a deterministic check or LLM-as-judge, and why?

Check your answer
Deterministic: exact-match the predicted label against the known correct label for each test case. There's nothing subjective to weigh here, the category set is fixed and each case already has a single correct answer, exactly the situation this section says to prefer fixed logic for. Reaching for LLM-as-judge would add cost and a new source of inconsistency to a question a one-line string comparison already answers exactly and for free.
5

Catching regressions before they ship

The real payoff of a repeatable eval score isn't the number itself, it's what it lets you compare. Running the same eval suite against the old prompt and the new prompt, the old model and a candidate replacement, tells you objectively whether a change helped, hurt, or made no measurable difference, before it ships to real users.

Definition: regression

A measurable drop in eval score after a change, compared to a known baseline score, signaling the change likely made the system worse on some dimension the eval suite covers.

A regression check is only as good as its baseline and its isolation, changing one thing at a time (one prompt, one retrieval parameter) and re-running the full eval suite tells you exactly what caused a score change. Changing several things at once and running the eval once tells you only that SOMETHING changed, not which part.

Practice check

A team changes both their system prompt (Module 1) and their retrieval top-k value (Module 3) in the same deploy, then runs the eval suite once and sees the score drop by 8 points. What's the practical cost of having changed both at once?

Check your answer
They know something regressed, but not which change caused it, or whether one change improved things while the other hurt worse. Diagnosing it now requires re-running the eval with each change isolated (prompt change alone, top-k change alone) AFTER the fact, work that would have been unnecessary if the changes had been evaluated separately from the start. Isolating variables before evaluating, not after, is what actually makes the eval score actionable.
Practice check

A content-moderation tool is switching providers. Engineer A wants to swap the provider AND tighten the confidence threshold in the same deploy, then run the eval suite once against the 0.88 baseline. Engineer B wants to swap the provider alone first, run the full eval suite, compare that to baseline, and only then adjust the threshold in a separate isolated run. Whose approach actually tells the team whether the new provider itself is a regression risk?

Check your answer
Engineer B's. Changing the provider and the threshold together and evaluating once produces a single score that reflects the combined effect of both, if it drops, there's no way to tell whether the new provider is worse, the tighter threshold is worse, or one is masking the other. Running the eval with only the provider changed, against the same baseline, isolates that one variable and gives a clean answer about the provider specifically, exactly the discipline this section describes, just applied to a provider swap instead of a prompt change.
6

Build it: a deterministic eval harness

You've seen the pieces: labeled test cases with explicit criteria, deterministic scoring, and regression detection against a baseline. Now implement an eval harness that ties them together, and five real tests run against your actual code.

Code exercise · Python, runs in a real sandboxed Python interpreter (Pyodide)

Complete evaluate_model(test_cases, model_fn, baseline_score). test_cases is a list of {"id":..., "input":..., "check":...} dicts, where check(actual) returns True/False. For each case, call model_fn(input) to get the actual output (never let a raise from model_fn OR check crash your function, treat either as a failed case instead), then run check(actual). Return {"score":..., "passCount":..., "total":..., "results":..., "regression":...}, where results is a list of {"id":..., "pass":..., "actual":...} in the same order as test_cases, score is passCount / total, and regression is True only when baseline_score is a real number AND score is lower than it.

Stuck? Hints
Hint 1 — conceptual
Loop over test_cases: for each one, get an actual output, check it, and record the result. Then reduce that list of results down to a score, a pass count, and a regression flag.
Hint 2 — specific
Wrap the model_fn(tc["input"]) call in its own try/except, if it raises, that case is a fail with actual set to something describing the error, and check() is never called for that case. Separately, wrap tc["check"](actual) in try/except too, if IT raises, treat the case as a fail as well.
Hint 3 — near-solution
After building the results list, total is len(results), passCount is how many have pass is True, score is passCount / total (guard against total being 0). regression is only True if baseline_score is not None AND score < baseline_score.
Solution — run your code at least once first
def evaluate_model(test_cases, model_fn, baseline_score):
    results = []
    for tc in test_cases:
        try:
            actual = model_fn(tc["input"])
        except Exception as e:
            results.append({"id": tc["id"], "pass": False, "actual": "ERROR: " + str(e)})
            continue

        try:
            passed = bool(tc["check"](actual))
        except Exception:
            passed = False

        results.append({"id": tc["id"], "pass": passed, "actual": actual})

    total = len(results)
    pass_count = sum(1 for r in results if r["pass"])
    score = pass_count / total if total > 0 else 0

    has_baseline = baseline_score is not None
    regression = has_baseline and score < baseline_score

    return {"score": score, "passCount": pass_count, "total": total, "results": results, "regression": regression}
Practice check

Test 5 uses a check function that raises for one specific test case. If your code only wraps model_fn in try/except but not check itself, what happens?

Check your answer
An exception from check() would propagate up out of your loop and crash the entire evaluate_model call, losing every result, not just the one problematic case. A single bad checker (a bug in the test case's own criterion) shouldn't be able to take down evaluation of every other test case, the same "one bad input shouldn't crash the whole batch" discipline that's shown up since Module 4's tool executor.

9

Further reading

If you want to go deeper than the browser can take you:

  • Beyond a single aggregate score, production eval suites often track per-category breakdowns (which KINDS of test cases are failing), a flat score can hide a specific, fixable weakness.
  • "Golden datasets," curated, hand-labeled test sets that get updated carefully and deliberately over time, are a common foundation for eval suites, since the quality of an eval is bounded by the quality and coverage of its test cases.
  • Observability in production (logging real inputs, outputs, and scores from live traffic, not just the offline eval set) closes the loop, it's how you discover the test cases your eval set is missing.
10

Glossary

eval (evaluation) — a systematic, repeatable process for scoring outputs against test cases with defined criteria.
deterministic check — a pass/fail criterion evaluated by fixed logic, producing identical results on identical input every time.
LLM-as-judge — using a model call to score another model's output, useful for subjective criteria, but inherits model unreliability.
baseline — a previously recorded eval score used as the comparison point for detecting regressions.
regression — a measurable drop in eval score after a change, compared to the baseline.
