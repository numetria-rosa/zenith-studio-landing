Module 01

Prompting & Structured Outputs

A language model produces text. Your program needs data. This module is about closing that gap reliably, not with a nicer-sounding prompt, but with validation and repair logic that doesn't trust the model to behave.

Learning objectives
  • Explain why raw model output is not a data format, and where that assumption breaks production systems
  • Design a prompt with a clear role, instructions, and few-shot examples that reduce output variance
  • Detect and repair the most common malformed-output patterns (code fences, trailing commas, extra prose)
  • Implement a real validator that checks output against a schema before your program trusts it
Before you start

1

The gap between "sounds right" and "is data"

A model that answers "The user's name is Alice and they're 30 years old" said something true and readable. It also produced zero bytes of usable data. If your program's next step is record.age + 1, that sentence is worthless until something turns it back into { name: "Alice", age: 30 }.

Definition: structured output

Model output constrained to a predictable, parseable shape, typically JSON matching a schema you define, so a program can consume it without a human or another model in the loop.

Two different failure modes hide behind "just ask it for JSON": the model can produce output that's almost valid JSON (a trailing comma, a stray code fence), or it can refuse, hedge, or add commentary around otherwise-valid JSON. Both are common. Neither is rare enough to ignore.

2

Prompt anatomy

A prompt sent to a model is usually structured in roles, not one blob of text:

The three roles

system — standing instructions that apply to the whole conversation: tone, constraints, output format. user — the actual request or input for this turn. assistant — the model's prior responses, included when there's conversation history or when you're providing few-shot examples of the response style you want.

Where the format instruction lives matters. Burying "respond only in JSON" in the middle of a long user message is far less reliable than stating it once, clearly, in the system role, and reinforcing it with an example.

The instruction is not the guarantee. Telling a model to output valid JSON measurably improves the odds. It does not make malformed output impossible. Anything that parses the response has to assume it might not parse.
3

Few-shot examples reduce variance, not risk to zero

A "few-shot" prompt includes one or more example input/output pairs before the real request, showing the model the exact shape you want rather than describing it in prose. This is usually the single highest-leverage change you can make to output consistency.

Why examples beat descriptions

"Return a JSON object with a name and age field" leaves room for interpretation (nested? array? extra fields?). Showing {"name": "Priya", "age": 41} as a worked example removes that ambiguity directly, models are strong pattern-matchers on concrete examples.

Few-shot examples reduce how often the model deviates from the shape you want. They do not eliminate deviation. A validator is still required downstream, examples change the odds, not the guarantee.

Practice check

A teammate says "I added three examples to the prompt, so we don't need a validator anymore." What's wrong with that reasoning?

Check your answer
Few-shot examples are a probabilistic improvement, not a contract. They lower the RATE of malformed output, they don't change what your program does the one time in a hundred (or a thousand) that the model still deviates, adds a caveat, or hits an edge case the examples didn't cover. Removing the validator means that one deviation now crashes or corrupts your program instead of being caught and handled. The fix for imperfect reliability is a validator, not fewer reasons to need one.
Practice check

A fintech startup's transaction categorizer prompt now includes six few-shot examples covering the common categories (groceries, rent, subscriptions, transfers...). Before this release ships, someone proposes cutting the validator: "six examples is a lot, the model barely misses now." The categorizer's output writes directly into a user's monthly spending report with no human review. What's wrong with cutting the validator here?

Check your answer
Six examples change the odds, not the guarantee, the model can still miscategorize, drop a field, or hand back a category that isn't in your allowed set. In most domains that's an annoying bug. In a spending report that a user trusts as an accurate record of their own money, a silent miscategorization isn't just wrong text, it's wrong financial data presented as fact, with no human in the loop to catch it before the user sees it. The stakes of the downstream consumer, not the example count, determine whether validation is optional. It never is, but it matters even more here, where the cost of an unvalidated deviation is a user's financial record being wrong.

5

The repair pattern

Before giving up on a response, a production system typically tries a short, deterministic repair pass: strip markdown code fences (models love wrapping JSON in ```json ... ``` even when told not to), strip a trailing comma before a closing brace or bracket, then attempt to parse. Only if that still fails do you treat it as a real failure, either retrying the model with the parse error included in the next prompt, or surfacing an error to the caller.

Repair, then validate, in that order. Fixing formatting doesn't guarantee the DATA is correct, a syntactically valid JSON object can still be missing a field your schema requires. Both checks are needed, and they check different things.
Practice check

A raw response parses as valid JSON but is missing the age field your schema requires. Is that a repair-pass problem or a validation problem?

Check your answer
Validation. The repair pass only fixes SYNTAX issues (things that stop json.loads() from succeeding at all), a missing field is a semantically incomplete but syntactically valid object, json.loads() succeeds and hands back a dict that simply doesn't have everything your schema needs. That's exactly why validation is a separate step after parsing, not folded into the repair pass, they catch different classes of failure.
Practice check

An e-commerce order-lookup assistant asks a model to return {"order_id": string, "status": string, "eta_days": number} for a customer's shipment. Two raw responses come back on two different requests. (A) {"order_id": "OD-4471", "status": "shipped", "eta_days": 3,}. (B) "I looked into it, but I don't have access to that order's tracking status." Which one belongs in the repair pass, and which should go straight to a retry or reject, and why?

Check your answer
Response A is a repair-pass case: it's JSON with exactly one syntax defect, a trailing comma before the closing brace, that's the deterministic, mechanical fix this module's repair pass exists for, strip it and parse succeeds cleanly. Response B is not malformed JSON, it's not JSON at all, it's the model declining to answer in prose. No amount of fence-stripping or comma-stripping turns a sentence into a valid order object, there's no syntax defect to repair. That's a signal to retry (maybe with a clearer instruction or more context) or reject and surface an error, not a job for the repair pass. Treating B like A, running it through the same repair regexes, just wastes a step, the failure is content-level, not formatting-level.
6

Build it: implement the validator

You've seen the failure modes. Now you write the function that catches them, and five real tests run against your actual code.

Code exercise · Python, runs in a real sandboxed Python interpreter (Pyodide)

Complete extract_structured_output(raw_text, schema). schema is a dict {"required": [...]}, the list of field names that must be present. Return {"ok": True, "data": ...} on success, or {"ok": False, "error": ...} on failure, where error is a short human-readable string. Handle: markdown code fences around the JSON, a trailing comma before } or ], and a missing required field. Never raise, always return one of the two shapes above, even for completely non-JSON input.

Stuck? Hints
Hint 1 — conceptual
Think in three passes: (1) clean up formatting noise around the JSON, (2) try to parse it, (3) check the parsed dict actually has what you need. Each pass can fail independently, and each failure should produce a useful error, not a raised exception.
Hint 2 — specific
Python's re module: re.match(r"^```(?:json)?\s*([\s\S]*?)\s*```$", text) captures the content between fences. For trailing commas, re.sub(r",\s*([}\]])", r"\1", text) before parsing. Wrap json.loads in try/except, don't let it raise out of your function.
Hint 3 — near-solution
After a successful parse, loop over schema.get("required", []) and check field in data for each one. Return a specific error naming the missing field on the first one that's absent, don't just say "invalid".
Solution — run your code at least once first
import json
import re

def extract_structured_output(raw_text, schema):
    text = str(raw_text).strip()
    fenced = re.match(r"^```(?:json)?\s*([\s\S]*?)\s*```$", text)
    if fenced:
        text = fenced.group(1).strip()
    text = re.sub(r",\s*([}\]])", r"\1", text)

    try:
        data = json.loads(text)
    except Exception as e:
        return {"ok": False, "error": "Could not parse JSON: " + str(e)}

    for field in schema.get("required", []):
        if not isinstance(data, dict) or field not in data:
            return {"ok": False, "error": "Missing required field: " + field}
    return {"ok": True, "data": data}
Practice check

Test 5 feeds your function a response like "I'm not able to help with that request.", plain prose, not JSON at all. If you forget the try/except around json.loads, what specifically breaks?

Check your answer
re.match() and re.sub() don't raise on a non-matching plain string, they simply return None or the original string unchanged. The place this scenario actually breaks is json.loads() itself, parsing "I'm not able to help..." as JSON raises a json.JSONDecodeError. Without the try/except, that exception propagates out of your function instead of becoming a clean {"ok": False, "error": ...}, exactly the "never raise" requirement in the exercise instructions.
Practice check

A legal-document extraction tool asks a model to pull {"party_names": [...], "effective_date": string, "governing_law": string} out of a scanned contract. One response parses without error, and every required field is present, but effective_date comes back as "", an empty string. Would extract_structured_output, exactly as specified in this module (checking field in data for each required field), catch this? Should it?

Check your answer
It would NOT catch it, and that's worth sitting with. field in data only checks presence, whether the key exists in the dict at all, it says nothing about whether the value is meaningful. "effective_date": "" satisfies "the key is present" just as well as a real date does, so this validator returns {"ok": True, ...} on a contract with no effective date. It should catch it, in a real production system, an empty string in a required date field is exactly the kind of defect a schema is supposed to stop, but this module's schema is deliberately simplified to a presence check. A production validator would also check type and, often, a minimum shape (non-empty string, matches a date pattern), the JSON Schema standard mentioned later in this module is what that looks like at full strength. The lesson: "the required fields are present" and "the required fields are usable" are different guarantees, know which one your validator actually gives you.

Further reading

If you want to go deeper than the browser can take you:

  • Most major model providers document a native "structured output" or "JSON mode" feature that constrains generation at the token level, worth using when available, it reduces but does not eliminate the need for your own validation.
  • JSON Schema (json-schema.org) is the standard vocabulary for describing the shape this module's toy {required:[...]} schema is a simplified stand-in for.
  • In production, this shows up as the boundary between "the model" and "the rest of your system", the validator is that boundary, and it's the same architectural role a request-validation layer plays for any external, untrusted input.
10

Glossary

structured output — model output constrained to a predictable, parseable shape, typically JSON.
few-shot prompting — including example input/output pairs in the prompt to demonstrate the desired response shape.
system / user / assistant roles — the three message roles most model APIs use to separate standing instructions, the current request, and prior responses.
repair pass — deterministic cleanup (stripping fences, trailing commas) attempted before treating a response as unparseable.
schema validation — checking that successfully-parsed data actually contains the fields a consumer requires.
