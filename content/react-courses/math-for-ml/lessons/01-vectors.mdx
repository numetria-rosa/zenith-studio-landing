## Why you're learning this

Open any machine learning system and you will find vectors everywhere: a
row of a dataset, a word turned into an "embedding," an image flattened into
pixels, the weights of a neural network layer. Before any of that makes
sense, you need one very specific piece of intuition: **a vector is not a
list of numbers, it's an arrow with a direction, and comparing two arrows'
directions is how machines decide whether two things are "similar."**

That single idea — comparing directions — is the mathematical foundation
underneath search engines, recommendation systems, and how a language model
decides which word is relevant to which. This module builds that idea from
scratch and ends with you being able to say exactly why.

## 1.1 — A vector is an arrow, not a spreadsheet row

Picture two arrows drawn from the same starting point. One points mostly
right and a little up. The other points mostly up and a little right. Even
before you measure anything, you can *see* that they point in roughly
similar directions — nowhere near opposite, not perfectly aligned either.

That visual comparison — "roughly similar direction" — is the entire idea
this module turns into mathematics you can compute.

<Callout tone="info" label="Definition">
A **vector** in two dimensions is a pair of numbers $(x, y)$ that describes
a displacement from the origin: how far to move right/left, and how far to
move up/down. Its two properties are **magnitude** (how long the arrow is)
and **direction** (which way it points). Neither number alone tells you
both — $(x, y)$ together does.
</Callout>

In machine learning, a vector is almost never literally an arrow on a page —
it's a **feature vector**: one number per measurable property of something.
A product might be represented as `(price, rating, weight)`. A sentence,
after being run through an embedding model, might be represented as 768 or
1536 numbers, each one capturing some learned aspect of its meaning. The
"arrow" framing still applies exactly the same way, just in a space with
more than 2 dimensions than you can draw — the math doesn't care how many
dimensions there are.

## 1.4 — Where this shows up in real machine learning

- **Semantic search**: a search engine turns your query into an embedding
  vector, then finds the stored documents whose embedding vectors have the
  highest cosine similarity to it — literally the exact computation you just
  ran in the lab above, just in hundreds of dimensions instead of 2.
- **Recommendation systems**: "users who liked what you liked" is, under the
  hood, "users whose preference vectors point in a similar direction to
  yours."
- **Attention in transformers** (you'll see this properly in Module 11, but
  the seed is here): a transformer decides how much one word should "pay
  attention to" another word by taking a dot product between vectors derived
  from each word. Everything in this module is the prerequisite for that.

## 1.5 — A failure mode this prevents

<Callout tone="warning" label="Common mistake: confusing dot product with cosine similarity">
The **dot product** ($\mathbf{a}\cdot\mathbf{b}$) is sensitive to
magnitude — a very long vector pointing in almost the same direction can
produce a *larger* dot product than a short vector pointing in an
*identical* direction. If you use raw dot product to compare "how similar
are these two things" without normalizing, a document that's simply longer
(more words, bigger embedding norm) can look "more similar" purely because
it's bigger, not because it's more relevant. Cosine similarity divides that
out on purpose — dividing by $\|\mathbf{a}\|\|\mathbf{b}\|$ is exactly what
removes magnitude from the comparison. This is a real, common bug in search
systems built by people who understood the code but not the math underneath
it.
</Callout>
