## Why you're learning this

Module 4 gave you the gradient - the direction that's uphill from any
point. This module turns that into an algorithm: start somewhere, take a
step downhill, repeat. That algorithm, gradient descent, is what "training"
means for essentially every model you'll ever touch. But the algorithm has
a dial - the learning rate - and this module is about what happens when
that dial is set wrong, because you will see this exact failure in real
training runs.

## 5.1 - An algorithm made of one repeated step

Gradient descent has no clever tricks in its basic form: compute the
gradient at your current point, step a small amount in the opposite
direction, and do it again. The only real decision is how big a step to
take - the learning rate.

<Callout tone="info" label="Definition">
**Gradient descent** repeatedly applies
$\mathbf{x}_{n+1} = \mathbf{x}_n - \eta \nabla f(\mathbf{x}_n)$, where
$\eta$ (the **learning rate**) controls step size. Too small, and
convergence is correct but slow. Too large, and steps can overshoot the
minimum - sometimes landing further away each time, a failure called
**divergence**.
</Callout>

<Callout tone="info" label="Worked example">
Take one gradient-descent step by hand. Start at $x = 3$, with
$f(x) = x^2$ (so $f'(x) = 2x$), and learning rate $\eta = 0.1$:
1. Compute the gradient at the current point: $f'(3) = 2(3) = 6$
2. Scale it by the learning rate: $0.1 \times 6 = 0.6$
3. Subtract from the current point: $x_{\text{new}} = 3 - 0.6 = 2.4$

One step moved $x$ from $3$ to $2.4$, closer to the minimum at $x=0$.
Repeating this same three-step process is the entire algorithm - the lab
below just does this arithmetic for you, in two dimensions, every time you
click "Step."
</Callout>

## 5.4 - Where this shows up in real machine learning

- **Every training run's learning rate hyperparameter** is exactly this
  dial - too high causes loss curves that spike or oscillate; too low
  causes training that barely moves within a reasonable time budget.
- **Learning rate schedules** (starting high, decreasing over time) exist
  precisely because the ideal learning rate can change as training
  progresses and the loss landscape's local curvature changes.
- **Adaptive optimizers** (Adam, RMSProp) exist to solve exactly the
  x-vs-y instability gap you saw in the lab - different parameters often
  need different effective step sizes, and these optimizers estimate that
  automatically instead of using one shared learning rate for everything.

## 5.5 - A failure mode this prevents

<Callout tone="warning" label="Common mistake: reading a spiking loss curve as “the model is broken”">
A loss curve that suddenly spikes after training smoothly is very often an
optimization-stability problem (learning rate too large for the current
region of the loss landscape), not evidence the model architecture or data
is fundamentally wrong. Before redesigning a model in response to unstable
training, checking (and often simply lowering) the learning rate is a
fast, frequently correct first move - and this module is exactly why that
diagnosis makes sense.
</Callout>

<Callout tone="warning" label="Common mistake: assuming a lower loss always means training is going well">
A steadily decreasing loss is a good sign, but it isn't the whole story:
a model can be decreasing its *training* loss while its performance on
new, unseen data quietly gets worse (a separate problem called
overfitting, covered more once evaluation comes up later in the course).
Gradient descent is guaranteed to decrease the loss it's actually
computing on, step by step, in the region checked here - it says nothing
about whether that loss is even the right thing to be minimizing for your
actual goal.
</Callout>
